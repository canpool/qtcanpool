## 二、M3.1 qxcore 基础设施（本次执行）

### 2.1 定位与约束

- **定位**：面向应用的基础设施层，当前提供配置与日志；后续主题、i18n 等归入本库或在其上新建库。
- **依赖**：仅 `Qt5::Core`（`PUBLIC_DEPENDS`），不引入 Widgets，保证任何进程（含无界面工具）都能用。
- **命名**：库 `qxcore`、命名空间 `QxCore`、宏族 `QX_CORE_*`（决策 K3 的 `qx*` 风格）。
- **构建**：**仅 CMake**。qmake 已冻结（决策 K2"新增内容只进 CMake"），因此刻意**未**新增 `qxcore.pri` / `.pro` 条目，qmake 构建不含本库。
- **注释**：一律英文（项目规范）。

### 2.2 API 契约

**QxSettings**（`src/libs/qxcore/qxsettings.h`）

| 分类   | 接口                                                                                | 说明                             |
| :--- | :-------------------------------------------------------------------------------- | :----------------------------- |
| 构造   | `QxSettings(organization, application)` / `QxSettings(fileName, format)`           | 后者用于测试等需要固定文件的场景               |
| 分组   | `beginGroup` / `endGroup` / `group`                                                | 转发 QSettings，键自动按组限定            |
| 读取   | `value` / `stringValue` / `intValue` / `boolValue` / `stringListValue` / `contains` / `allKeys` | 类型化读取，支持默认值                    |
| 写入   | `setValue` / `remove` / `clear` / `sync`                                           | 写入触发 `valueChanged(key, value)` 信号 |
| 迁移   | `setVersionKey` / `version` / `setVersion` / `addMigration(version, fn)` / `migrate(target)` | 版本化布局迁移，按版本升序执行                |

设计要点：

1. **迁移语义**：`migrate(target)` 只执行版本落在 `(stored, target]` 区间的步骤，执行完写入 `target`；`target <= stored` 时返回 0 且**不修改**已存版本（避免"降级"把版本号改小）。
2. **信号**：`valueChanged` 报告**组限定后**的键，与下次读取用的键一致，便于设置对话框做双向绑定。
3. **所有权**：对象自持 `QSettings`（`QObject` 父子关系），调用方只持有一个 `QxSettings`。

**QxLogger**（`src/libs/qxcore/qxlogger.h`）

| 分类   | 接口                                                       | 说明                            |
| :--- | :------------------------------------------------------- | :---------------------------- |
| 生命周期 | `init(Options)` / `shutdown` / `isEnabled` / `fileName` / `flush` | 进程级静态；`shutdown` 恢复原消息处理器    |
| 输出   | `write(Level, category, message)`                        | 绕过处理器直接写，便于第三方库适配             |
| 配置   | `Options{fileName, level, maxFileSize, maxBackups, toConsole}` | 文件名空 = 只输出控制台                 |

设计要点：

1. **分级过滤**：`Debug < Info < Warning < Critical < Fatal`，低于阈值直接丢弃。
2. **滚动**：写入前预判 `size + pending > maxFileSize` 触发滚动，滚动后 `<fileName>.1 .. .N`，超出的最旧备份删除；因此**活动文件不会长期超限**。
3. **行格式**：`yyyy-MM-dd HH:mm:ss.zzz [级别字母] category: message`。
4. **线程安全**：全局状态由 `QMutex` 保护；`init` 可重复调用以替换配置。
5. **可测试**：`shutdown()` 恢复 `qInstallMessageHandler` 的前一个处理器，测试之间互不干扰。

### 2.4 顺带修复：测试驱动吞掉失败（重要）

编写 qxcore 测试时发现 `tests/common/tst_global.cpp` 的 `UnitTest::run()` **丢弃了 `QTest::qExec()` 的返回值**，`main()` 又固定 `return 0`。后果：

- 断言失败时进程仍以 0 退出 → `ctest` 报告 **Passed** → **CI 绿灯掩盖真实失败**。

实测证据（修复前后同一份测试）：

| 状态             | 现象                                                    |
| :------------- | :---------------------------------------------------- |
| 修复前           | 注入 `QVERIFY2(false)` 后进程 `exit=0`，`ctest` 仍报 Passed  |
| 修复后           | 同一注入 → `exit=1`，`ctest` 报 **Failed**                 |

修复内容：

1. `UnitTest::run()` 返回失败对象数，`TEST_RUN_ALL()` 以该值作为 `main()` 的返回码（三个 `main.cpp` 同步清理）；
2. 顺带新增 `QTC_ONLY_TEST=<类名>` 环境变量，把一次运行限定到单个测试对象——因为 `QTest` 的命令行选择器会下发给**每个**对象，其余对象会报 `Function not found`，无法单独调试某个套件。

**暴露出的既存失败**：修复后 `tst_qxdock` 立刻变红。定位到 `tst_DockContainer::zOrder()`：

- 根因：`DockContainer::zOrderIndex()` 取值自 `dockcontainer.cpp` 的**进程级静态计数器** `s_zOrderCounter`，只增不减；而用例断言的是绝对值 `1`、`2`，等于假设该计数器从 0 开始 —— 单个套件运行成立，跟在其它创建过容器的套件之后就失败（顺序依赖）。
- 修复：改为断言**相对关系** —— 首次显示后记录 `raised`，隐藏/显示/`raise()` 均保持该值，激活后 `> raised`。库实现未改动（计数器语义符合预期）。

### 2.6 踩坑记录

1. **缺一个分号，clang-format 会把析构函数折成一行**：`QX_FINI_PRIVATE()` 未带尾部分号时，clang-format 输出了 `QxSettings::~QxSettings(){QX_FINI_PRIVATE()}`（与项目风格背离）。补上 `;`（与 `qxapp`/`qxdock` 写法一致）后恢复多行。
2. **测试二进制在本机控制台无输出**：直接运行测试程序看不到任何 stdout，需用 `-o <file>,txt` 让 QTest 写报告文件才能读取结果；用 `QTC_ONLY_TEST` 单独跑才能避免报告被最后一个对象覆盖。
3. **多对象测试的报告互相覆盖**：`UnitTest::run()` 对所有对象复用同一份 argv，因此 `-o` 报告文件最终只保留**最后执行**的对象的报告。这是新增 `QTC_ONLY_TEST` 的直接动机。

## 三、M3.2 主题引擎（本次执行）

### 3.1 定位与约束

- **定位**：把"主题"从 qxribbon 里的一个静态样式表加载函数，升级为**应用级引擎** —— 谁负责应用、选了哪套、记在哪里、系统明暗变了怎么办，从此有唯一归属。
- **依赖**：`qxcore`（持久化）+ `Qt5::Core/Gui/Widgets`。**刻意不依赖 qxribbon**（见 3.3）。
- **命名**：库 `qxtheme`、命名空间 `QxTheme`、宏族 `QX_THEME_*`。
- **构建**：仅 CMake（决策 K2）；新增 `WITH_QXTHEME` 选项，置于 `WITH_QXCORE` 之后。
- **注释**：一律英文（项目规范）。

### 3.2 现状与缺口

改造前的主题能力只有两半，且互不相干：

| 既有能力                     | 所在库       | 缺口                                        |
| :----------------------- | :-------- | :---------------------------------------- |
| `RibbonTheme::setTheme()` | qxribbon  | 只装样式表；**无调色板**；无持久化；无系统跟随；选择不跨启动保留        |
| `WindowStyleAgent`       | qxwindow  | 只**探测**系统明暗并发出信号，不负责应用主题                  |

直接后果：菜单、原生对话框、工具提示、禁用态文字等 QSS 覆盖不到的表面仍停留在平台默认色，与深色样式表明显不协调。

### 3.3 关键设计决策：与 qxribbon 解耦

样式表资源仍在 qxribbon（`:/qxribbon/res/stylesheets/*.css`），但 **qxtheme 不 `#include` 也不需要链接 qxribbon**：

- 资源在 Qt 中是**进程级**注册的 —— qxribbon 一旦被链接进进程，其 `.qrc` 内容即可被任何库按路径读取；
- 因此引擎只按路径**运行时**读取，`themeStyleSheetPath()` 的默认前缀 `:/qxribbon/res/stylesheets/` 可被 `QX_THEME_STYLESHEET_PREFIX` 覆盖；
- 资源缺失（未链接 qxribbon）时**降级为仅应用调色板并只告警一次**，而不是把样式表清空 —— 清空会静默抹掉调用方自己设置的样式表；
- 注册自己的样式表走 `setStyleSheetFile()` / `setStyleSheet()`。

这样 qxribbon **零改动**，qmake 侧（冻结）也不受影响，同时引擎对不使用 ribbon 的应用同样可用。

### 3.4 API 契约

**主题模型**（`src/libs/qxtheme/qxtheme.h`）

| 分类   | 接口                                                                  | 说明                                        |
| :--- | :------------------------------------------------------------------ | :---------------------------------------- |
| 枚举   | `enum Theme { LightYellow, LightOffice2013, LightClassic, LightFancy, DarkWps, DarkOfficePlus, Custom }` | 顺序**对齐** `RibbonTheme::ThemeStyle`，便于互相映射 |
| 标识   | `themeId` / `themeName` / `themeFromId(id, fallback)`                | id 进配置文件（稳定，不翻译）；name 供设置对话框              |
| 判定   | `isDarkTheme(theme)`                                                | 深/浅色分类                                    |
| 资源   | `themeStyleSheetPath` / `themeStyleSheet`                           | 路径与内容；`Custom` 两者皆空                        |

**调色板**（`qxthemepalette.h`）

| 接口                | 说明                                                              |
| :---------------- | :-------------------------------------------------------------- |
| `lightPalette()` / `darkPalette()` | 完整 `QPalette`：Window/Base/Text/Button/Highlight/ToolTip/`LinkVisited`/`PlaceholderText`，并单独设置 **Disabled 组** |
| `palette(theme)`  | 深色主题 → 深色板，其余 → 浅色板                                              |

设计要点：色值取自既有 QSS 的 `qtcanpool-qss` 令牌块（如深色 `#292929` 背景 / `#f0f0f0` 文字 / `#a0a0a0` 禁用），保证样式表与调色板同源；`Light`/`Mid`/`Dark`/`Shadow` 等框架阴影角色由窗口色推导，避免回落到 Qt 默认浅色。

**引擎**（`qxthememanager.h`，`QxThemeManager`）

| 分类     | 接口                                                                              | 说明                                |
| :----- | :------------------------------------------------------------------------------ | :-------------------------------- |
| 单例     | `instance()`                                                                    | 首次使用时创建；**故意不析构**（要活过 QApplication） |
| 应用     | `setTheme` / `apply` / `theme` / `isDark`                                       | `setTheme` 应用 + 持久化 + 发信号           |
| 系统跟随   | `followSystemTheme` / `setFollowSystemTheme` / `refreshSystemTheme`             | 开关持久化；跟随态下**不**持久化推导出的主题           |
| 跟随配对   | `systemLightTheme` / `systemDarkTheme` / `setSystemThemePair`                   | 默认 `LightOffice2013` / `DarkOfficePlus` |
| 持久化    | `settings()` / `setSettings(QxSettings *)`                                      | 后者接管所有权，可注入 hermetic 文件做测试         |
| 样式表来源  | `styleSheet(theme)` / `setStyleSheetFile` / `setStyleSheet`                     | 优先级：内联内容 > 文件 > 内置资源               |
| 信号     | `themeChanged(Theme)` / `followSystemThemeChanged(bool)`                        |                                   |

设计要点：

1. **持久化键**（组 `ui`）：`theme` / `followSystemTheme` / `systemLightTheme` / `systemDarkTheme`，均存 id 字符串而非枚举裸值。
2. **`apply()` 做两件事**：`qApp->setPalette(...)` + `qApp->setStyleSheet(...)`。Qt 自身会在样式表变化时向全部部件派发 `QEvent::StyleChange`，而 qxribbon / qxdock 已有该事件的既有处理（`RibbonBar::updateRibbonTheme`、`DockTab::updateStyle` …），因此**运行时切换无需引擎额外遍历控件**。
3. **跟随的语义**：`setFollowSystemTheme(true)` 立即应用配对中与当前系统色匹配的一套；系统色**变了**再切。显式 `setTheme()` **不会**自动关闭跟随（下次系统变化仍会接管）—— 这是刻意的，避免一个调用同时改两件事。
4. **系统色探测**：Qt ≥ 6.5 用 `QStyleHints::colorScheme()` 并连 `colorSchemeChanged`；其余（含 Qt 5）退化为按调色板窗口色亮度判断，**且没有自动钩子** —— 需要调用方在设置对话框等处主动调 `refreshSystemTheme()`，已在头文件注释中写明。
5. **`Custom`**：不读内置资源；`apply()` 时样式表清空（符合"自定义就自己接管"的既有语义），调色板回落浅色基线。

> 单例是进程级的，因此每个用例开头都通过 `setSettings()` 注入**全新配置文件**，从而不依赖用例执行顺序。

### 3.8 踩坑记录

1. **Qt 5.15 下 `Q_DECLARE_METATYPE` 必须显式包含 `<QtCore/QMetaType>`**：Qt 6 里该宏经传递包含即可用，Qt 5.15 里没有 —— 漏包含时编译器报的却是 Qt 自己的 `qobjectdefs_impl.h:52: expected constructor, destructor, or type conversion before 'class'`，与真实原因完全无关。定位方式：最小 TU 二分（`qglobal` → `+QFile` 正常；`qxtheme.h` → `+QFile` 失败 → 去掉 `Q_DECLARE_METATYPE` 后恢复）。
2. **跨库引用必须带命名空间前缀**：`QxSettings` 在 `QxCore` 命名空间，qxtheme 内一律写 `QX_CORE_PREPEND_NAMESPACE(QxSettings)`（等同于既有 `QX_RIBBON_PREPEND_NAMESPACE` 的用法）。
3. **`QT_NO_CAST_FROM_ASCII` 下 `const char *` 不能直接当 `QString`**：键名常量需 `QString::fromLatin1(...)` 包装（`beginGroup`/`setValue` 处）。

## 五、与决策 / 风险的关系

- **K2（qmake 冻结）**：qxcore 与 qxtheme 都只进 CMake，这是决策的直接结果。qxtheme 刻意不成为 qxribbon 的依赖，因此 qmake 侧的 qxribbon 不受影响。
- **K6（不保证二进制兼容）**：`QxThemeManager` 采用 d-pointer（`QX_DECLARE_PRIVATE`），与既有库写法一致并为演进留出空间；主题 id 字符串是**对外契约**，改动需走迁移。
- **风险 1**：`QxThemeManager::instance()` 故意不析构，退出时不释放（单例的常规取舍）；如果将来需要析构，需先确认没有连接挂在它上面。
- **风险 2**：`apply()` 会设置**应用级**样式表，若调用方此前自行 `qApp->setStyleSheet()`，会被覆盖 —— 这是"统一主题"的必然结果，调用方应改用引擎的 `setStyleSheet()` 注册。
- **风险 3**：`QxLogger`/`QxSettings` 与 `QxThemeManager` 都可能在 `QApplication` 之前被构造；引擎对 `qApp` 为空做了返回保护，但真正的应用应在 `QApplication` 之后再取单例。
- **风险 4**：`QxLogger` 接管进程级 `qInstallMessageHandler`，若调用方自行安装处理器需协调顺序（当前 `init()` 会保存并在 `shutdown()` 恢复前一个处理器）。
