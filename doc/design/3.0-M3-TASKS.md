## 二、M3.1 qxcore 基础设施（本次执行）

### 2.1 定位与约束

- **定位**：面向应用的基础设施层，当前提供配置与日志；后续主题、i18n 等归入本库或在其上新建库。
- **依赖**：仅 `Qt5::Core`（`PUBLIC_DEPENDS`），不引入 Widgets，保证任何进程（含无界面工具）都能用。
- **命名**：库 `qxcore`、命名空间 `QxCore`、宏族 `QX_CORE_*`（决策 K3 的 `qx*` 风格）。
- **构建**：**仅 CMake**。qmake 已冻结（决策 K2"新增内容只进 CMake"），因此刻意**未**新增 `qxcore.pri` / `.pro` 条目，qmake 构建不含本库。
- **注释**：一律英文（项目规范）。

### 2.2 API 契约

**QxSettings**（`src/libs/qxcore/qxsettings.h`）

| 分类   | 接口                                                                                | 说明                             |
| :--- | :-------------------------------------------------------------------------------- | :----------------------------- |
| 构造   | `QxSettings(organization, application)` / `QxSettings(fileName, format)`           | 后者用于测试等需要固定文件的场景               |
| 分组   | `beginGroup` / `endGroup` / `group`                                                | 转发 QSettings，键自动按组限定            |
| 读取   | `value` / `stringValue` / `intValue` / `boolValue` / `stringListValue` / `contains` / `allKeys` | 类型化读取，支持默认值                    |
| 写入   | `setValue` / `remove` / `clear` / `sync`                                           | 写入触发 `valueChanged(key, value)` 信号 |
| 迁移   | `setVersionKey` / `version` / `setVersion` / `addMigration(version, fn)` / `migrate(target)` | 版本化布局迁移，按版本升序执行                |

设计要点：

1. **迁移语义**：`migrate(target)` 只执行版本落在 `(stored, target]` 区间的步骤，执行完写入 `target`；`target <= stored` 时返回 0 且**不修改**已存版本（避免"降级"把版本号改小）。
2. **信号**：`valueChanged` 报告**组限定后**的键，与下次读取用的键一致，便于设置对话框做双向绑定。
3. **所有权**：对象自持 `QSettings`（`QObject` 父子关系），调用方只持有一个 `QxSettings`。

**QxLogger**（`src/libs/qxcore/qxlogger.h`）

| 分类   | 接口                                                       | 说明                            |
| :--- | :------------------------------------------------------- | :---------------------------- |
| 生命周期 | `init(Options)` / `shutdown` / `isEnabled` / `fileName` / `flush` | 进程级静态；`shutdown` 恢复原消息处理器    |
| 输出   | `write(Level, category, message)`                        | 绕过处理器直接写，便于第三方库适配             |
| 配置   | `Options{fileName, level, maxFileSize, maxBackups, toConsole}` | 文件名空 = 只输出控制台                 |

设计要点：

1. **分级过滤**：`Debug < Info < Warning < Critical < Fatal`，低于阈值直接丢弃。
2. **滚动**：写入前预判 `size + pending > maxFileSize` 触发滚动，滚动后 `<fileName>.1 .. .N`，超出的最旧备份删除；因此**活动文件不会长期超限**。
3. **行格式**：`yyyy-MM-dd HH:mm:ss.zzz [级别字母] category: message`。
4. **线程安全**：全局状态由 `QMutex` 保护；`init` 可重复调用以替换配置。
5. **可测试**：`shutdown()` 恢复 `qInstallMessageHandler` 的前一个处理器，测试之间互不干扰。

### 2.4 顺带修复：测试驱动吞掉失败（重要）

编写 qxcore 测试时发现 `tests/common/tst_global.cpp` 的 `UnitTest::run()` **丢弃了 `QTest::qExec()` 的返回值**，`main()` 又固定 `return 0`。后果：

- 断言失败时进程仍以 0 退出 → `ctest` 报告 **Passed** → **CI 绿灯掩盖真实失败**。

实测证据（修复前后同一份测试）：

| 状态             | 现象                                                    |
| :------------- | :---------------------------------------------------- |
| 修复前           | 注入 `QVERIFY2(false)` 后进程 `exit=0`，`ctest` 仍报 Passed  |
| 修复后           | 同一注入 → `exit=1`，`ctest` 报 **Failed**                 |

修复内容：

1. `UnitTest::run()` 返回失败对象数，`TEST_RUN_ALL()` 以该值作为 `main()` 的返回码（三个 `main.cpp` 同步清理）；
2. 顺带新增 `QTC_ONLY_TEST=<类名>` 环境变量，把一次运行限定到单个测试对象——因为 `QTest` 的命令行选择器会下发给**每个**对象，其余对象会报 `Function not found`，无法单独调试某个套件。

**暴露出的既存失败**：修复后 `tst_qxdock` 立刻变红。定位到 `tst_DockContainer::zOrder()`：

- 根因：`DockContainer::zOrderIndex()` 取值自 `dockcontainer.cpp` 的**进程级静态计数器** `s_zOrderCounter`，只增不减；而用例断言的是绝对值 `1`、`2`，等于假设该计数器从 0 开始 —— 单个套件运行成立，跟在其它创建过容器的套件之后就失败（顺序依赖）。
- 修复：改为断言**相对关系** —— 首次显示后记录 `raised`，隐藏/显示/`raise()` 均保持该值，激活后 `> raised`。库实现未改动（计数器语义符合预期）。

### 2.5 验证（Qt 6.8.3 + MinGW GCC 13.1.0 + CMake 4.2.1）

- ✅ 配置 / 构建：`CFG=0`、`BUILD=0`、**0 告警 / 0 错误**
- ✅ `ctest`：**5/5 通过**（`tst_qxcore` 2.13s / `tst_qxribbon` / `tst_qxdock` / `tst_qstring` / `tst_qlineedit`）
- ✅ 用例统计（`QTC_ONLY_TEST` 单独运行取报告）：`tst_QxSettings` 8 passed、`tst_QxLogger` 8 passed、`tst_DockContainer` 7 passed
- ✅ 退出码传播：注入失败断言 → `exit=1` + `ctest` Failed（探针验证后移除）
- ✅ clang-format 门禁：**343 文件** `--dry-run --Werror` 通过
- ✅ 换行符：改动文件无 MIXED；新增 qxcore 文件为 LF（与 `qxapp`/`qxwindow`/`qxdock` 一致）

### 2.6 踩坑记录

1. **缺一个分号，clang-format 会把析构函数折成一行**：`QX_FINI_PRIVATE()` 未带尾部分号时，clang-format 输出了 `QxSettings::~QxSettings(){QX_FINI_PRIVATE()}`（与项目风格背离）。补上 `;`（与 `qxapp`/`qxdock` 写法一致）后恢复多行。
2. **测试二进制在本机控制台无输出**：直接运行测试程序看不到任何 stdout，需用 `-o <file>,txt` 让 QTest 写报告文件才能读取结果；用 `QTC_ONLY_TEST` 单独跑才能避免报告被最后一个对象覆盖。
3. **多对象测试的报告互相覆盖**：`UnitTest::run()` 对所有对象复用同一份 argv，因此 `-o` 报告文件最终只保留**最后执行**的对象的报告。这是新增 `QTC_ONLY_TEST` 的直接动机。

## 四、与决策 / 风险的关系

- **K2（qmake 冻结）**：qxcore 只进 CMake，这是决策的直接结果；如果后续需要在 qmake 构建中使用 qxcore，需要先重新决策。
- **K6（不保证二进制兼容）**：`QxSettings`/`QxLogger` 采用 d-pointer（`QX_DECLARE_PRIVATE`）以保持与既有库一致的写法，同时为后续演进留出空间。
- **风险**：`QxLogger` 接管进程级 `qInstallMessageHandler`，若调用方自行安装处理器需协调顺序（当前 `init()` 会保存并在 `shutdown()` 恢复前一个处理器）。
