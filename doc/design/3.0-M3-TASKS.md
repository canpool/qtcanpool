## 二、M3.1 qxcore 基础设施（本次执行）

### 2.1 定位与约束

- **定位**：面向应用的基础设施层，当前提供配置与日志；后续主题、i18n 等归入本库或在其上新建库。
- **依赖**：仅 `Qt5::Core`（`PUBLIC_DEPENDS`），不引入 Widgets，保证任何进程（含无界面工具）都能用。
- **命名**：库 `qxcore`、命名空间 `QxCore`、宏族 `QX_CORE_*`（决策 K3 的 `qx*` 风格）。
- **构建**：**仅 CMake**。qmake 已冻结（决策 K2"新增内容只进 CMake"），因此刻意**未**新增 `qxcore.pri` / `.pro` 条目，qmake 构建不含本库。
- **注释**：一律英文（项目规范）。

### 2.2 API 契约

**QxSettings**（`src/libs/qxcore/qxsettings.h`）

| 分类   | 接口                                                                                | 说明                             |
| :--- | :-------------------------------------------------------------------------------- | :----------------------------- |
| 构造   | `QxSettings(organization, application)` / `QxSettings(fileName, format)`           | 后者用于测试等需要固定文件的场景               |
| 分组   | `beginGroup` / `endGroup` / `group`                                                | 转发 QSettings，键自动按组限定            |
| 读取   | `value` / `stringValue` / `intValue` / `boolValue` / `stringListValue` / `contains` / `allKeys` | 类型化读取，支持默认值                    |
| 写入   | `setValue` / `remove` / `clear` / `sync`                                           | 写入触发 `valueChanged(key, value)` 信号 |
| 迁移   | `setVersionKey` / `version` / `setVersion` / `addMigration(version, fn)` / `migrate(target)` | 版本化布局迁移，按版本升序执行                |

设计要点：

1. **迁移语义**：`migrate(target)` 只执行版本落在 `(stored, target]` 区间的步骤，执行完写入 `target`；`target <= stored` 时返回 0 且**不修改**已存版本（避免"降级"把版本号改小）。
2. **信号**：`valueChanged` 报告**组限定后**的键，与下次读取用的键一致，便于设置对话框做双向绑定。
3. **所有权**：对象自持 `QSettings`（`QObject` 父子关系），调用方只持有一个 `QxSettings`。

**QxLogger**（`src/libs/qxcore/qxlogger.h`）

| 分类   | 接口                                                       | 说明                            |
| :--- | :------------------------------------------------------- | :---------------------------- |
| 生命周期 | `init(Options)` / `shutdown` / `isEnabled` / `fileName` / `flush` | 进程级静态；`shutdown` 恢复原消息处理器    |
| 输出   | `write(Level, category, message)`                        | 绕过处理器直接写，便于第三方库适配             |
| 配置   | `Options{fileName, level, maxFileSize, maxBackups, toConsole}` | 文件名空 = 只输出控制台                 |

设计要点：

1. **分级过滤**：`Debug < Info < Warning < Critical < Fatal`，低于阈值直接丢弃。
2. **滚动**：写入前预判 `size + pending > maxFileSize` 触发滚动，滚动后 `<fileName>.1 .. .N`，超出的最旧备份删除；因此**活动文件不会长期超限**。
3. **行格式**：`yyyy-MM-dd HH:mm:ss.zzz [级别字母] category: message`。
4. **线程安全**：全局状态由 `QMutex` 保护；`init` 可重复调用以替换配置。
5. **可测试**：`shutdown()` 恢复 `qInstallMessageHandler` 的前一个处理器，测试之间互不干扰。

### 2.4 顺带修复：测试驱动吞掉失败（重要）

编写 qxcore 测试时发现 `tests/common/tst_global.cpp` 的 `UnitTest::run()` **丢弃了 `QTest::qExec()` 的返回值**，`main()` 又固定 `return 0`。后果：

- 断言失败时进程仍以 0 退出 → `ctest` 报告 **Passed** → **CI 绿灯掩盖真实失败**。

实测证据（修复前后同一份测试）：

| 状态             | 现象                                                    |
| :------------- | :---------------------------------------------------- |
| 修复前           | 注入 `QVERIFY2(false)` 后进程 `exit=0`，`ctest` 仍报 Passed  |
| 修复后           | 同一注入 → `exit=1`，`ctest` 报 **Failed**                 |

修复内容：

1. `UnitTest::run()` 返回失败对象数，`TEST_RUN_ALL()` 以该值作为 `main()` 的返回码（三个 `main.cpp` 同步清理）；
2. 顺带新增 `QTC_ONLY_TEST=<类名>` 环境变量，把一次运行限定到单个测试对象——因为 `QTest` 的命令行选择器会下发给**每个**对象，其余对象会报 `Function not found`，无法单独调试某个套件。

**暴露出的既存失败**：修复后 `tst_qxdock` 立刻变红。定位到 `tst_DockContainer::zOrder()`：

- 根因：`DockContainer::zOrderIndex()` 取值自 `dockcontainer.cpp` 的**进程级静态计数器** `s_zOrderCounter`，只增不减；而用例断言的是绝对值 `1`、`2`，等于假设该计数器从 0 开始 —— 单个套件运行成立，跟在其它创建过容器的套件之后就失败（顺序依赖）。
- 修复：改为断言**相对关系** —— 首次显示后记录 `raised`，隐藏/显示/`raise()` 均保持该值，激活后 `> raised`。库实现未改动（计数器语义符合预期）。

### 2.6 踩坑记录

1. **缺一个分号，clang-format 会把析构函数折成一行**：`QX_FINI_PRIVATE()` 未带尾部分号时，clang-format 输出了 `QxSettings::~QxSettings(){QX_FINI_PRIVATE()}`（与项目风格背离）。补上 `;`（与 `qxapp`/`qxdock` 写法一致）后恢复多行。
2. **测试二进制在本机控制台无输出**：直接运行测试程序看不到任何 stdout，需用 `-o <file>,txt` 让 QTest 写报告文件才能读取结果；用 `QTC_ONLY_TEST` 单独跑才能避免报告被最后一个对象覆盖。
3. **多对象测试的报告互相覆盖**：`UnitTest::run()` 对所有对象复用同一份 argv，因此 `-o` 报告文件最终只保留**最后执行**的对象的报告。这是新增 `QTC_ONLY_TEST` 的直接动机。

## 三、M3.2 主题引擎（本次执行）

### 3.1 定位与约束

- **定位**：把"主题"从 qxribbon 里的一个静态样式表加载函数，升级为**应用级引擎** —— 谁负责应用、选了哪套、记在哪里、系统明暗变了怎么办，从此有唯一归属。
- **依赖**：`qxcore`（持久化）+ `Qt5::Core/Gui/Widgets`。**刻意不依赖 qxribbon**（见 3.3）。
- **命名**：库 `qxtheme`、命名空间 `QxTheme`、宏族 `QX_THEME_*`。
- **构建**：仅 CMake（决策 K2）；新增 `WITH_QXTHEME` 选项，置于 `WITH_QXCORE` 之后。
- **注释**：一律英文（项目规范）。

### 3.2 现状与缺口

改造前的主题能力只有两半，且互不相干：

| 既有能力                     | 所在库       | 缺口                                        |
| :----------------------- | :-------- | :---------------------------------------- |
| `RibbonTheme::setTheme()` | qxribbon  | 只装样式表；**无调色板**；无持久化；无系统跟随；选择不跨启动保留        |
| `WindowStyleAgent`       | qxwindow  | 只**探测**系统明暗并发出信号，不负责应用主题                  |

直接后果：菜单、原生对话框、工具提示、禁用态文字等 QSS 覆盖不到的表面仍停留在平台默认色，与深色样式表明显不协调。

### 3.3 关键设计决策：与 qxribbon 解耦

样式表资源仍在 qxribbon（`:/qxribbon/res/stylesheets/*.css`），但 **qxtheme 不 `#include` 也不需要链接 qxribbon**：

- 资源在 Qt 中是**进程级**注册的 —— qxribbon 一旦被链接进进程，其 `.qrc` 内容即可被任何库按路径读取；
- 因此引擎只按路径**运行时**读取，`themeStyleSheetPath()` 的默认前缀 `:/qxribbon/res/stylesheets/` 可被 `QX_THEME_STYLESHEET_PREFIX` 覆盖；
- 资源缺失（未链接 qxribbon）时**降级为仅应用调色板并只告警一次**，而不是把样式表清空 —— 清空会静默抹掉调用方自己设置的样式表；
- 注册自己的样式表走 `setStyleSheetFile()` / `setStyleSheet()`。

这样 qxribbon **零改动**，qmake 侧（冻结）也不受影响，同时引擎对不使用 ribbon 的应用同样可用。

### 3.4 API 契约

**主题模型**（`src/libs/qxtheme/qxtheme.h`）

| 分类   | 接口                                                                  | 说明                                        |
| :--- | :------------------------------------------------------------------ | :---------------------------------------- |
| 枚举   | `enum Theme { LightYellow, LightOffice2013, LightClassic, LightFancy, DarkWps, DarkOfficePlus, Custom }` | 顺序**对齐** `RibbonTheme::ThemeStyle`，便于互相映射 |
| 标识   | `themeId` / `themeName` / `themeFromId(id, fallback)`                | id 进配置文件（稳定，不翻译）；name 供设置对话框              |
| 判定   | `isDarkTheme(theme)`                                                | 深/浅色分类                                    |
| 资源   | `themeStyleSheetPath` / `themeStyleSheet`                           | 路径与内容；`Custom` 两者皆空                        |

**调色板**（`qxthemepalette.h`）

| 接口                | 说明                                                              |
| :---------------- | :-------------------------------------------------------------- |
| `lightPalette()` / `darkPalette()` | 完整 `QPalette`：Window/Base/Text/Button/Highlight/ToolTip/`LinkVisited`/`PlaceholderText`，并单独设置 **Disabled 组** |
| `palette(theme)`  | 深色主题 → 深色板，其余 → 浅色板                                              |

设计要点：色值取自既有 QSS 的 `qtcanpool-qss` 令牌块（如深色 `#292929` 背景 / `#f0f0f0` 文字 / `#a0a0a0` 禁用），保证样式表与调色板同源；`Light`/`Mid`/`Dark`/`Shadow` 等框架阴影角色由窗口色推导，避免回落到 Qt 默认浅色。

**引擎**（`qxthememanager.h`，`QxThemeManager`）

| 分类     | 接口                                                                              | 说明                                |
| :----- | :------------------------------------------------------------------------------ | :-------------------------------- |
| 单例     | `instance()`                                                                    | 首次使用时创建；**故意不析构**（要活过 QApplication） |
| 应用     | `setTheme` / `apply` / `theme` / `isDark`                                       | `setTheme` 应用 + 持久化 + 发信号           |
| 系统跟随   | `followSystemTheme` / `setFollowSystemTheme` / `refreshSystemTheme`             | 开关持久化；跟随态下**不**持久化推导出的主题           |
| 跟随配对   | `systemLightTheme` / `systemDarkTheme` / `setSystemThemePair`                   | 默认 `LightOffice2013` / `DarkOfficePlus` |
| 持久化    | `settings()` / `setSettings(QxSettings *)`                                      | 后者接管所有权，可注入 hermetic 文件做测试         |
| 样式表来源  | `styleSheet(theme)` / `setStyleSheetFile` / `setStyleSheet`                     | 优先级：内联内容 > 文件 > 内置资源               |
| 信号     | `themeChanged(Theme)` / `followSystemThemeChanged(bool)`                        |                                   |

设计要点：

1. **持久化键**（组 `ui`）：`theme` / `followSystemTheme` / `systemLightTheme` / `systemDarkTheme`，均存 id 字符串而非枚举裸值。
2. **`apply()` 做两件事**：`qApp->setPalette(...)` + `qApp->setStyleSheet(...)`。Qt 自身会在样式表变化时向全部部件派发 `QEvent::StyleChange`，而 qxribbon / qxdock 已有该事件的既有处理（`RibbonBar::updateRibbonTheme`、`DockTab::updateStyle` …），因此**运行时切换无需引擎额外遍历控件**。
3. **跟随的语义**：`setFollowSystemTheme(true)` 立即应用配对中与当前系统色匹配的一套；系统色**变了**再切。显式 `setTheme()` **不会**自动关闭跟随（下次系统变化仍会接管）—— 这是刻意的，避免一个调用同时改两件事。
4. **系统色探测**：Qt ≥ 6.5 用 `QStyleHints::colorScheme()` 并连 `colorSchemeChanged`；其余（含 Qt 5）退化为按调色板窗口色亮度判断，**且没有自动钩子** —— 需要调用方在设置对话框等处主动调 `refreshSystemTheme()`，已在头文件注释中写明。
5. **`Custom`**：不读内置资源；`apply()` 时样式表清空（符合"自定义就自己接管"的既有语义），调色板回落浅色基线。

### 3.8 踩坑记录

1. **Qt 5.15 下 `Q_DECLARE_METATYPE` 必须显式包含 `<QtCore/QMetaType>`**：Qt 6 里该宏经传递包含即可用，Qt 5.15 里没有 —— 漏包含时编译器报的却是 Qt 自己的 `qobjectdefs_impl.h:52: expected constructor, destructor, or type conversion before 'class'`，与真实原因完全无关。定位方式：最小 TU 二分（`qglobal` → `+QFile` 正常；`qxtheme.h` → `+QFile` 失败 → 去掉 `Q_DECLARE_METATYPE` 后恢复）。
2. **跨库引用必须带命名空间前缀**：`QxSettings` 在 `QxCore` 命名空间，qxtheme 内一律写 `QX_CORE_PREPEND_NAMESPACE(QxSettings)`（等同于既有 `QX_RIBBON_PREPEND_NAMESPACE` 的用法）。
3. **`QT_NO_CAST_FROM_ASCII` 下 `const char *` 不能直接当 `QString`**：键名常量需 `QString::fromLatin1(...)` 包装（`beginGroup`/`setValue` 处）。

## 四、M3.3 AppShell 骨架（本次执行）

### 4.1 定位与约束

- **定位**：应用外壳 —— 把一个 ribbon 应用每次都要手搭的部分（导航、页面切换、停靠区、状态栏、启动屏、布局持久化）收拢成一个可继承的窗口基类。
- **落点**：**放进 `qxapp`，不新建库**。路线图已明确 `qxapp` 就是"承载 `RibbonAppWindow`、主题切换、设置、状态栏、启动流程"的应用框架库（`doc/ROADMAP-3.0.md` 目标结构图与决策 A3），AppShell 正是它的内容。
- **依赖**：新增 `qxdock`（停靠区）、`qxtheme`（主题）、`qxcore`（配置）为 `PUBLIC_DEPENDS`——公开头里出现了这些类型（`DockWindow*`、`QxSettings*`、`Qx::DockWidgetArea`），必须是公开依赖。
- **命名**：沿用 `QxApp` 命名空间与 `QX_APP_*` 宏族。
- **构建**：仅 CMake。**qxapp 的 qmake 描述文件（`qxapp-lib.pri` / `header.list`）刻意不动**（K2 冻结、只读），qmake 侧仍只编译 `ribbonappwindow.cpp`，因此不引入任何 qxcore/qxtheme/qxdock 依赖；新文件只进 CMake 的 `SOURCES`。
- **注释**：一律英文（项目规范）。

### 4.2 现状与缺口

`QxApp::RibbonAppWindow` 已经给了 ribbon + 窗口代理（无边框、系统按钮、拖拽/缩放），但：

| 应用还要自己做的事        | 后果                                        |
| :---------------- | :---------------------------------------- |
| 建 DockWindow 并 `setCentralWidget` | 每个应用重复一遍，且踩 `qxdock` 的"中央 dock 必须第一个加入"约束 |
| 侧边导航 + 页面切换       | 无现成控件；各应用各写一套                             |
| 状态栏消息/忙碌指示        | 重复实现                                      |
| 窗口几何 / 停靠布局 / 当前页  | 各写各的 `QSettings` 键，格式不统一                   |
| 启动屏               | `QSplashScreen` 只有消息行，没有进度                 |

### 4.3 关键设计决策

1. **页面是页面，不是 dock**。页面放在中央 `QStackedWidget` 里（作为 DockWindow 的**中央 dock widget**），停靠区围绕其外。这样页面是固定的工作区，而 docks 依旧可拖动/浮动/关闭——两者职责不混。
2. **中央 dock 在构造时安装**。`qxdock` 规定中央 widget 必须是第一个加入的 dock widget，所以 `QxAppShell` 构造里就把它装好（隐藏标题栏），此后 `addDock()` 自然环绕，调用方不必关心顺序。
3. **页面用稳定 id 持久化**，不用索引也不用标题：插入页面会让索引平移，标题会被翻译，只有 id 是配置契约。`addPage`/`insertPage` 拒绝空 id 与重复 id。
4. **`setSettings()` 不自动恢复布局**（与 `QxThemeManager::setSettings()` 的行为**故意不同**）：布局依赖页面与 docks 已经存在，因此必须由调用方在构建完成后显式调用 `restoreLayout()`，头文件已写明。
5. **`currentPageChanged(index, id)` 报告"可见页的 (索引, id) 对"**：因此插入/删除导致的**纯索引平移**也会发信号（载荷里的索引确实变了），只比较 id 会漏掉这种情况。
6. **启动屏补的是进度而不是消息**：`QSplashScreen` 已有消息行，`QxSplashScreen` 加 `step(percent, message)`（重绘 + `processEvents(ExcludeUserInputEvents)`，因为启动工作是阻塞主线程的），并在 `drawContents` 里把应用名/版本/消息/进度条画在图像底部——一张 logo 就够。空 logo 由纯色板兜底，测试与"还没有美术资源"的应用都能用。

### 4.8 踩坑记录

1. **`QAction` 在 Qt 5 / Qt 6 分属不同模块**：Qt 6 是 `QtGui/QAction`、Qt 5.15 是 `QtWidgets/QAction`，而且**各自都不存在另一个**（已在本机两个安装里核对）。写死任一路径都会在某个版本上编译失败。项目既有约定是用**无模块前缀**的 `#include <QAction>` —— Qt 的模块包含目录都在搜索路径上，两版本都能解析且无歧义。这是 Qt 5.15 交叉校验抓到的第一个问题。
2. **`QSignalSpy` / `QTemporaryDir` 属于 QtTest，不在 QtCore**：`#include <QtCore/QSignalSpy>` 必然编译失败；`tests/common/tst_global.h` 已经包含 `<QtTest/QtTest>`，直接用即可。
3. **对 `statusBar()` 的返回值调用成员函数要显式包含 `QStatusBar`**：`QMainWindow` 只前向声明它，`QLabel(statusBar())` / `statusBar()->findChild<...>()` 都会报 "invalid use of incomplete type"。
4. **跨库前向声明必须带该库的宏头**：在 `qxappshell.h` 里用 `QX_CORE_BEGIN_NAMESPACE` 前置声明 `QxSettings` 会报 "`QX_CORE_BEGIN_NAMESPACE` does not name a type"——因为没包含 `qxcore_global.h`。公开 API 本来就要用到这个类型，直接 `#include "qxcore/qxsettings.h"` 最省事。
5. **`Q_DECLARE_PRIVATE` 的 `d_ptr` 会被派生类遮蔽**：`QxAppShell` 与基类 `RibbonAppWindow` 各有一份 `d_ptr`（项目既有写法就是如此）。派生类的 `d_func()` 会隐藏基类的同名重载，因此派生类里只能用自己的 `Q_D`；基类方法仍解析到基类那份。无需特殊处理，但要清楚不是同一块内存。

### 4.9 后续修复：`autoSaveOnClose` 在 Linux 上失败（M3.4 期间发现）

M3.3 推送后 CI 在 `ubuntu-latest / Qt 6.8.1` 上变红：`tst_QxAppShell::autoSaveOnClose()` 读回 `ui/currentPage` 为空（同一份代码在 Windows Qt 6.8.1 与 Ubuntu Qt 5.15.2 上都是绿的）。

根因（读 Qt 6.8.1 源码确认）：`QWidget::close()` 自 Qt 6 起改为两段式——

```cpp
bool QWidget::close()
{
    return d_func()->close();
}

bool QWidgetPrivate::close()
{
    if (QWindow *widgetWindow = windowHandle()) {
        if (widgetWindow->isTopLevel())
            return widgetWindow->close();
    }
    return handleClose(QWidgetPrivate::CloseWithEvent);
}
```

只要部件已经拥有 `QWindow` 且它是顶层窗口，`close()` 就**转调 `QWindow::close()`**；而 `QWindow::close()` 在**没有平台窗口**时直接 `return true`，**一个 `QCloseEvent` 都不会发出**：

```cpp
    if (!d->platformWindow) {
        // dock widgets can transition back and forth to being popups;
        // avoid getting stuck
        if (QGuiApplicationPrivate::activePopupWindow() == this)
            QGuiApplicationPrivate::closePopup(this);
        return true;                       // 静默返回，无关闭事件
    }
    ...
    return d->platformWindow->close();
```

测试从未 `show()` 过窗口，正好落在「有 `QWindow`、还没有平台窗口」这个状态 → `QxAppShell::closeEvent` 不执行 → 不保存。平台窗口存在时走的是 `QPlatformWindow::close()`，它是 `SynchronousDelivery`，关闭事件在 `close()` 返回前同步送达（`QWidgetWindow::closeEvent()` → `handleClose()`）。

修复（只动测试，未动库）：

1. 先 `show()` 再 `close()`，与真实应用一致，并追加 `QVERIFY(shell.close())` 把这个契约钉住；
2. 写入方放进独立作用域，读回前先析构 `QxSettings`，与 `persistence()` 的写法一致（不依赖"写入方还活着时另一个 `QSettings` 能否立刻看到"）。

## 五、M3.4 文档站点（本次执行）

### 5.1 定位与约束

- **定位**：把"注释即文档"变成"可访问的文档"——C++ API 从公开头文件生成，指南复用 `doc/` 的 Markdown，两者合并成一个静态站点。
- **技术选型**：**Doxygen**，而不是仓库里继承自 Qt Creator 的 qdoc 助手（`cmake/QtCanpoolDocumentation.cmake`）。理由见 5.2。
- **构建**：仅 CMake（决策 K2）。文档**既不需要 Qt 也不需要编译器**——Doxygen 只读文件，所以 `doc/CMakeLists.txt` 用 `project(... LANGUAGES NONE)`，一台只有 Doxygen 的机器也能构建。
- **注释**：`src/libs` 下早已全为英文（项目规范），Doxygen 直接可用，无需为出文档而改注释。
- **发布**：GitHub Pages；`.github/workflows/docs.yml` 在 `release-*` 上发布站点，`master`/`develop` 只构建不发布（否则任何开发分支的推送都会覆盖线上站点）。

### 5.2 关键设计决策

1. **为什么不复用随仓库的 qdoc**：`cmake/QtCanpoolDocumentation.cmake` 是随 Qt Creator 一起搬过来的助手（`add_qtc_documentation`），依赖 `qtbase` 的 qdoc 与 `*.qdocconf`，且**在 3.0 里从未被调用过**。它要求 Qt 构建树、只能文档 Qt 自己那套 `\class` 结构与大量 Qt 宏，代价远大于收益。Doxygen 反过来：单二进制、读头文件、对 `QX_*` 宏友好。既有文件保留不动（不删别人代码），只是在 `doc/` 下走自己的路线。
2. **既独立、又能并入主构建**：`doc/` 既是可独立配置的 CMake 工程（`cmake -S doc -B build-docs`），也是主构建的子目录（`-DWITH_DOCS=ON`）。两种模式共用同一份 `doc/CMakeLists.txt`，靠 `CMAKE_SOURCE_DIR STREQUAL CMAKE_CURRENT_SOURCE_DIR` 分流；Doxygen 缺失时，独立模式是 `FATAL_ERROR`（找不到 Doxygen 就是这次调用的全部意义），主构建模式只告警并 `return()`（不该因为没装 Doxygen 就让整个构建失败）。
3. **`EXPAND_ONLY_PREDEF = NO`（关键）**：项目用 `QX_CORE_BEGIN_NAMESPACE` 之类的宏开命名空间。若只展开 PREDEFINED 里列出的宏，这些宏就**不会被展开**，于是所有类都落在全局命名空间里，`\ref QxCore` 之类的引用也解析不了。改为 `NO` 后宏从它们的真实定义展开，命名空间页面正确出现 `QxCore` / `QxApp` / `QxTheme` / `QxDock` / `QxWindow` / `QxRibbon`。
4. **`INCLUDE_PATH = src/libs`**：公开头之间用 `#include "qxapp/qxapp_global.h"` 这种带库前缀的相对路径。不让 Doxygen 在 `src/libs` 下解析它们，`QX_DOCK_PREPEND_NAMESPACE(...)` 之类的**返回类型就不会被展开**，声明与定义对不上，于是刷出一批莫名其妙的警告。
5. **指南用 Markdown 链接而不是 `@ref`**：`doc/pages/*.md` 之间互相跳转用 `[构建与安装](build.md)`。`@ref` 后紧跟中文标点（如 `@ref QxCore、`）会被 Doxygen 当成引用名的一部分而解析失败。
6. **站点样式只做薄覆盖，且刻意不叫 `doxygen.css`**：样式表在 `doc/qtcanpool-doxygen.css`，通过 `HTML_EXTRA_STYLESHEET` 追加，只改字体（中文优先 Microsoft YaHei / PingFang）、标题与强调色（沿用 qxribbon 的 `#2aa84a`）、Markdown 表格边框、`img{max-width:100%}`；主题本身仍是 Doxygen 自带的（`HTML_COLORSTYLE = TOGGLE`，带深浅色切换）。**名字必须是自己的**——`doxygen.css` 恰好是 Doxygen 自己生成的那张表的名字（详见 5.5.5）。

### 5.5 踩坑记录

1. **Doxygen 1.18 删掉了几个老配置项**：`HTML_TIMESTAMP` / `DOT_FONTSIZE` / `DOT_TRANSPARENT` 已废弃，写进 Doxyfile 会刷警告，直接删掉。
2. **`EXPAND_ONLY_PREDEF = YES` 会把"没在 PREDEFINED 里"的宏原样留着**——包括项目的命名空间宏，结果所有类都跑到全局命名空间去了（详见 5.2.3）。
3. **`<fileName>` 不是合法 HTML 标签**：`qxlogger.h` 的注释里写了 `<fileName>`，Doxygen 生成时告警"`<fileName>` 不是受支持的 HTML 标签"，改写为纯文字。
4. **本地没有 `gh`，CI 日志要自己想办法拿**：仓库是公开的，但 job 日志接口仍需授权（`Must have admin rights`，403）。用 git 凭据管理器里已有的令牌（`git credential fill`）加 `Authorization` 头即可下载日志——这是本次能定位到 Linux 失败根因的前提。
5. **样式表不能叫 `doxygen.css`（构建绿 ≠ 定制生效）**：这是 Doxygen 自己生成的那张表的名字。1.9.8 直接报
   `error: Style sheet doxygen.css specified by HTML_EXTRA_STYLESHEET is already a built-in stylesheet. Please use a different name`，
   于是**自定义样式被静默丢弃**——`build` 作业仍是绿的（`DOXYGEN_WARN_AS_ERROR = NO`），线上站点用的是 Doxygen 自带样式。1.18.0 不报错，但输出目录里两张同名表，谁赢取决于顺序，**本机实测同样没生效**。改名为 `qtcanpool-doxygen.css` 后两种版本都正确。教训：**构建不报错不等于定制生效，必须去产物里查**（`grep 标记 build/docs-int/doc/html/*.css`）。
6. **注释里写 `..._PREPEND_NAMESPACE(RibbonTheme)::ThemeStyle` 会触发 "explicit link request"**：Doxygen 把紧跟在 `)` 后面的 `::ThemeStyle` 当作显式链接请求（`::name` 语义，指向全局作用域），而该名字在文档里不存在，1.9.8 于是报 `explicit link request to 'ThemeStyle' could not be resolved`（1.18.0 不报）。改成纯文字描述（"the ThemeStyle enumeration of the ribbon theme"）即可。

## 七、与决策 / 风险的关系

- **K2（qmake 冻结）**：qxcore / qxtheme 只进 CMake；`qxapp` 虽然同时有 qmake 与 CMake 构建，但本次**只改 CMake 的 `SOURCES`/依赖**，`.pri` 与 `header.list` 一字未动，所以 qmake 侧行为不变（也就不含 AppShell）——这是决策的直接结果，不是遗漏。
- **K6（不保证二进制兼容）**：`QxAppShell` / `QxNavigationBar` / `QxSplashScreen` 都用 d-pointer（`QX_DECLARE_PRIVATE`），与既有库写法一致并为演进留出空间；页面 id 与持久化键字符串是**对外契约**，改动需走迁移。
- **风险 1**：`QxThemeManager::instance()` 与 `QxAppShell` 默认都会按 `organizationName`/`applicationName` 各建一个 `QxSettings`。两者写的是**同一个文件的不同键**，但 QSettings 多实例各有缓存，理论上存在后写覆盖先写的窗口期。实践上应在应用启动时**建一个 `QxSettings` 并同时交给 `QxThemeManager::setSettings()` 与 `QxAppShell::setSettings()`**；`saveLayout()` 末尾的 `sync()` 也降低了风险。
- **风险 2**：`apply()` 会设置**应用级**样式表，若调用方此前自行 `qApp->setStyleSheet()`，会被覆盖 —— 这是"统一主题"的必然结果，调用方应改用引擎的 `setStyleSheet()` 注册。
- **风险 3**：`QxLogger`/`QxSettings`/`QxThemeManager`/`QxAppShell` 都可能在 `QApplication` 之前被构造；引擎对 `qApp` 为空做了返回保护，但真正的应用应在 `QApplication` 之后再取单例、再建窗口。
- **风险 4**：`QxLogger` 接管进程级 `qInstallMessageHandler`，若调用方自行安装处理器需协调顺序（当前 `init()` 会保存并在 `shutdown()` 恢复前一个处理器）。
- **风险 5**：`removePage()` 只把页面移出 shell 并 `setParent(nullptr)` **交还**给调用方，不负责删除；调用方若既不删除也不重新 `addPage`，就是一次泄漏。这是"所有权交还"的常规取舍，已在头文件写明。
- **风险 1**：`QxThemeManager::instance()` 故意不析构，退出时不释放（单例的常规取舍）；如果将来需要析构，需先确认没有连接挂在它上面。
- **风险 2**：`apply()` 会设置**应用级**样式表，若调用方此前自行 `qApp->setStyleSheet()`，会被覆盖 —— 这是"统一主题"的必然结果，调用方应改用引擎的 `setStyleSheet()` 注册。
- **风险 3**：`QxLogger`/`QxSettings` 与 `QxThemeManager` 都可能在 `QApplication` 之前被构造；引擎对 `qApp` 为空做了返回保护，但真正的应用应在 `QApplication` 之后再取单例。
- **风险 4**：`QxLogger` 接管进程级 `qInstallMessageHandler`，若调用方自行安装处理器需协调顺序（当前 `init()` 会保存并在 `shutdown()` 恢复前一个处理器）。
