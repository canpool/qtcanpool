# QtCanpool 4.6 任务规划（草稿 v1）

> 状态：**刚立项**（2026-10-18，4.5.0 发版当日开始规划）。本文件是 4.6 的权威任务分解。
> 定位由作者 2026-10-18 拍定；任务组为初稿，**按 4.5 的规矩持续追加**（新任务按所属组序号续编）。

## 一、版本定位与约束

- **定位：体验与基建收口，只做加法**（作者 2026-10-18 定）。
  4.5 是「允许破坏 API」的功能升级（K26），一口气改了主题 id、`qxtheme` 全接口、
  `RibbonBar::RibbonStyle` 四值改名、`QxNavBar` → `QxNavTabBar`。紧接着再破一轮对下游不友好，
  故 **4.6 只新增类/函数，不移除、不改签名**。
  ⇒ 若某项在开发中被证明不得不破坏，**不顺手破**——顺延到下一个允许破坏的 minor（K26）。
- 双支持：保留 Qt 5 / Qt 6（K30）；Qt 6.12 验证腿继续作为门禁（K31），4.6 复用不重建。
- 进号：本期**有新增 API** 的库进 minor，只有修复的进 patch（K11 / 附录 B）；
  构建接线不进号（4.5 已确立的判据）。
- ⚠️ **台账动态追加**：本文件在开发期内持续追加——已有组一律保留、新任务按所属组序号续编
  （A4、B4、C4…）。不存在「某组已封闭」或「整版做完」的中间状态，只有发版结算时一次性汇总。
  ⇒ 各组进度一律记为「当前已完成」。
- ⚠️ **台账只装本版要做的事**：不做的事（长期蓝图、别版的候选、选型勘察）**一律不写进本文件**，
  每个版本保持干净、不携带别的东西（作者 2026-10-18 定）。

### 「做深」的判据（C 组选题的唯一依据）

⚠️ 先定义再立项，否则「做深」会退化成「顺手加东西」。**做深 ≠ 做宽**：

| | 做深（本版要的） | 做宽（本版不要的） |
| :--- | :--- | :--- |
| 对象 | **已经存在**的能力 | 还没有的件 |
| 方向 | 补完备度、补健壮度、补可验证性 | 加新类 / 新控件 / 新库 |
| 验收 | 有明确的「做完」状态与回归通道 | 做到哪儿算完说不清 |

三条可验收的形态，C 组每条任务必须能归到其中一类，并写明验收通道：

1. **补完备度**：同一件事只做了一半 / 只在一条路径上成立（例：着色有单点、无整树；
   布局能存成明文了、另一条路还是黑盒 blob）。
2. **补可验证性**：从「只能靠真机手点」变成「离屏可断言」——**没有验收通道的项不进 4.6**。
3. **补健壮度**：边界与异常路径（损坏的布局文件、非法的样式表、大数据量）有确定行为。

反例（**不算做深，不得进 C 组**）：加新控件、加新库、为了「别人有」而补功能。

**对标参照：Qt Creator**（作者 2026-10-18 定）。本项目的定位原话就是「总结自 Qt Creator
源码结构」——同源、开源、已被真实应用证明，不必另找参照物。
⚠️ **对标的是「完备度的定义」，不是「功能清单」**：拿别人的功能清单当目标，做深立刻变成做宽。
⇒ 用法：选一个已有能力，列出它的完整生命周期逐格打分（有没有 / 可不可测 / 平不平台无关），
**只补「参照物做完了而我们做了一半」的格**，不补「别人有我们没有」的格（后者是做宽）。
⚠️ 不得用商用组件的功能清单当对标目标（合规）。

## 二、任务分解

### A 组 · 图标随主题（基建）

**A1 图标能力归位 `qxtheme`**（作者 2026-10-18 定：收进 `qxtheme`，不新建库）

⚠️ **硬约束——依赖图不允许「一份代码全库共用」**（2026-10-18 勘察）：

| 库 | 依赖 |
| :--- | :--- |
| `qxcore` | `Qt5::Core` |
| `qxtheme` | `qxcore` + Qt Core/Gui/Widgets |
| `qxwindow` | Qt Core/Gui/Widgets |
| **`qxribbon`** | **Qt Core/Gui/Widgets（不依赖 `qxtheme`，连 `qxcore` 都不依赖）** |
| **`qxdock`** | **Qt Core/Widgets + `Qt5::Svg`（不依赖 `qxtheme`）** |
| `qxplugin` | `qxcore` |
| `qxapp` | `qxwindow` `qxribbon` `qxdock` `qxtheme` `qxcore` `qxplugin` |

只有 `qxapp` 同时看得见三个库。因此「收进 `qxtheme`」的含义**只能是应用层统一**，不能是
「让 qxribbon/qxdock 去调 qxtheme」——那会引入两条新的库间依赖，把当前「三个外观库互不依赖」
的结构打破（该结构是 4.5 E7 刻意达成的：`qxtheme` 不依赖 `qxribbon`，`qxribbon` 也不反向依赖它）。

据此 A1 的范围定为：

- `qxtheme` 新增**主题感知图标的公共入口**：按调色板角色把单色图标染成当前主题色；
  对外是应用与 `qxapp` 用的那一层。
- `qxribbon` 的 `tintedIcon()` / `tintedPixmap()`（`ribbonutils.h`）与
  `qxdock` 的 `applyDockIcons()` / `refreshDockIcons()`（`dockiconprovider.h`）**保留不动**——
  两个库必须能脱离 `qxtheme` 独立使用。
- **一致性由规范 + 门禁保证，不由共用一份代码保证**（见 A2）。
- `qxapp` 提供「一键重染全应用」的编排（它唯一能同时调三者）。

**落地情况（2026-10-18）**：新增 `src/libs/qxtheme/qxthemeicon.h` / `.cpp`，四个入口——
`tintedPixmap()` / `tintedIcon()`（给一个明确颜色）与 `themedPixmap()` / `themedIcon()`
（给一个调色板角色，颜色取自当前 `QGuiApplication` 的调色板，也就是主题装进去的那一份）。
做法是**先光栅化、再按 alpha 重染**（与 qxribbon 同族）：与文件格式无关，
文件里原来是什么颜色都被替换掉，抗锯齿边缘的覆盖率保留；没有 QGuiApplication 时不染色、
把原图原样返回（没有调色板可问，但一个没染色的图标仍然是图标）。

- ⚠️ 这是**第三份实现**（qxribbon 一份、qxdock 一份、qxtheme 一份），但不是「双轨」问题：
  那两个库必须能脱离 `qxtheme` 独立使用，让它们反过来依赖它就把「三个外观库互不依赖」的结构打破了。
  三者的一致性由 `doc/pages/icons.md` 的规范 + `scripts/check-icons.py` 对齐，不由共用代码对齐。
- 未做：**A3**（切主题后自动重染的编排）。`themedIcon()` 已经把「按角色取色」这一步做掉了，
  A3 缺的是「主题变了以后由谁再来问一遍」。

**A2 图标资源规范 + 门禁**

⚠️ **先纠正规范草案里押错的一点：不要规定「必须写 `currentColor`」**（2026-10-18 核实）。
两套现有着色机制**都不靠它**，而且 Qt SVG 对 `currentColor` 的支持不可靠，规范不该押在上面。
实测两个实现的语义根本不同，这才是 A1「一致性靠规范 + 门禁」真正要覆盖的痛点：

| 机制 | 做法 | 与源颜色的关系 | 对多色图标 |
| :--- | :--- | :--- | :--- |
| `qxribbon::tintedPixmap()` | 光栅化后 `CompositionMode_SourceIn` + `fillRect` | **完全无关**——只保留 alpha，整幅换成目标色 | 被压成**纯色剪影**（配色信息丢失） |
| `qxdock::applyDockIcons()` | 替换 SVG 文本里的 `#ffffff` / `#fff` / `#a0a0a0` / `#000000` 四个**字面值**（`dockiconprovider.cpp:102-105`） | **强相关** | 只替换命中的那几个，**剩下的保持原色** ⇒ 颜色错乱 |

据此 A2 定为：

- 规范只规定**分类**：**单色**（可染）/ **多色**（豁免）。单色 = 字形只用一种颜色，
  **`fill` 还是 `stroke` 无所谓**——qxribbon 的 alpha mask 对两者一视同仁。
- **多色图标明确豁免**：qxribbon 会把它压成剪影、qxdock 会只替换一部分 ⇒ 两种结果都不对。
  豁免清单进仓库，门禁据此放行。
- 门禁（仿 `tools/themes/build_themes.py` 的对比度闸门）要报三类：
  ① 单色图标却混了多种颜色；② 未登记的彩色图标；
  ③ **要走 qxdock 着色却不含那四个字面值**（换图标集后最容易整片失效的一类）。

**落地情况（2026-10-18）**：规范落在 `doc/pages/icons.md`，门禁落在 `scripts/check-icons.py`，
登记表落在 `scripts/icons-policy.txt`，CI 在 `format` 作业的静态文本检查里加了一步
（与 `check-template-sync.py` / `check-encoding.py` 同列，都不需要工具链）。
当前 **99 枚受管图标、0 问题**。三类登记与规范色的定义只写在规范页，本文件不重复。

- ⚠️ **B2 期间怎么用**：`demos/qxapp/ribbondemo/res` 现按目录登记为 `plain`（存量旧图标不判颜色）。
  新图标落一枚就给它加一条**文件级** `tinted` 条目（文件级压过目录级），那一枚立刻受判定；
  等旧图标删完，再把目录级翻成 `tinted` + `alpha` 并删掉文件级条目。
  **中途不要把目录级一次性翻过去**——尚未替换的旧图标会同时不合格、CI 变红。

**A3 主题/调色板切换自动重染**

现状：染一次要靠应用自己监听 `ApplicationPaletteChange` 再调 `refreshDockIcons()`，
`qxribbon` 侧连整树重染的入口都没有。本项把「切主题 → 重染」做成 `qxtheme` 提供的编排能力
（应用 opt-in，库不强制外观——与 4.5 C10 的 opt-in 原则一致）。

**落地情况（2026-10-18）**：`QxThemeIcons`（同在 `qxthemeicon.h`）——应用把 action 交给它，
它**立刻**按角色染一次并记住「文件 + 角色 + 尺寸」，之后**应用调色板被换掉时自动重染**
（在 `QCoreApplication` 实例上装事件过滤器接 `ApplicationPaletteChange`；另外留 `refresh()`
给「换调色板没走 Qt 通告」或「图标文件本身变了」的情形）。`add()` 同一 action 覆盖而不重复绑定；
action 被销毁时在下一次重染时顺手剔除，不往野指针上画。
⚠️ **排在 B2 之前做**：否则 B2 换上去的新图标只在启动时正确、切主题时不跟着变——那正是本次要解决的痛点。
- 未做：应用侧「一键重染全应用」的编排（台账 A1 里归 `qxapp` 的那一层）——A3 只提供能力，
  谁来调由 `qxapp` / demo 决定；`qxapp` 那条不在 A 组，等 B2 推进到要用时再立。

  `#EAEAEA` `#434854` `#B9D2E2` `#024089`…），单色多色混杂；文件头带 `t="1662129827340"`、

- **选型已定**（作者 2026-10-18）：**单色 stroke 型开源集**。

- **入库要求**：带上游 LICENSE 声明；**只取用到的那几个**，不整包搬；
  **一律归一化**（见下）。

  ⚠️ **入库必须归一化**：Tabler / Lucide 的 SVG 默认是 `stroke="currentColor"`，
  入库时**一律改写成具体字面值**。这不是权宜之计，是两条机制的必然结论：
  `qxribbon` 那只认 alpha ⇒ 改成什么色都无所谓；`qxdock` 那只认 `#ffffff` / `#fff` /
  `#a0a0a0` / `#000000` 四个字面值 ⇒ **必须是具体值，否则整片失效**。
  约定单色字形的规范色为 `#000000`；`qxdock` 自带图标维持现状不动。
  ⇒ 结论与「Qt 是否解析 `currentColor`」**无关**，故不去押注它（本机探针未能跑起来，未实测）。

  **落地情况（2026-10-18，许可先行）**：许可已确认并入库——Tabler Icons **3.49.0**、MIT、
  Copyright 2020-2026 Pawel Kuna。许可全文收在 `demos/qxapp/ribbondemo/res/tabler/LICENSE.txt`
  （含来源、版本、施加了什么改动），并在根 `LICENSE.NOTES.md` 的 MIT 段登记。
  ⚠️ **只带用到的那几枚，不整包搬**；取图标随 B2 逐页进行，不在本条一次性铺开。

**第 6 页（Home）**——`homepage.h/.cpp` 的 `HomePage : RibbonPage`，14 枚新图标（ribbon 自身的
开关面板，也是旧实现里最长的一页）：
ribbon 自身开关（最小化、最小化按钮、应用按钮、四种 ribbon style、QAB 左/右、tab 居中、组标题、
全屏、窗口可最大化）、toolbutton 全谱（四种 popup 模式 + 图标/文字/长文本 + color button +
option action）全部页内闭环——够得着 `ribbonBar()` 或 `window()` 的都不出页。
出页的只有 4 个信号：`contextPageVisibleRequested` / `context2VisibleRequested` /
`contextPageDestroyRequested`（context tab 归窗口所有，且可**销毁后再显隐** ⇒ 窗口侧负责惰性重建）
与 `messageRequested`（写入主窗口编辑器）。

- ⚠️ **页面被 bar 收养之前 `ribbonBar()` 是空的**：`RibbonPage` 在构造函数里还没 `setRibbonBar()`，
  所以任何「构造时就要碰 bar」的接线都会拿到空指针。正解是等 `RibbonBar::insertPage()` 把页
  reparent 进 stack 时的 `ParentChange`（此时反向指针已设好），在 `attachToBar()` 里一次做完；
  **不要用 `QTimer::singleShot(0)`** 绕时序——那是靠事件循环顺序蒙对，不是确定时机。
- ⚠️ **small widget 必须 `setWindowTitle()`**：`ribboncustomizewidget.cpp` 拿
  `grpItem->widget()->windowTitle()` 当定制对话框里的条目名，**空名直接跳过**（该控件不会出现在
  定制列表里）。radio / checkbox 这些不是 action 的部件，`text()` 不算数。
- 全屏勾选的同步改为在顶层窗口装事件过滤器看 `WindowStateChange`（原来连
  `MainWindow::windowStateChanged`）：页面不必知道窗口的具体类型。

### C 组 · 库做深

**C1 `qxwindow`：把「只能真机手点」变成「离屏可断言」**（形态 2 · 补可验证性）

证据（2026-10-18 核实）：

- `qxwindow` 主体是 Windows 原生后端（`QX_WINDOW_CONFIG_NATIVE`），Linux / macOS 走 Qt 分支；
  CI 三条腿里**只有 Windows 会真正链接私有模块** ⇒ 另外两条腿对它「只编不验」，
  跨平台腿照不到它（同一事实也是 F1 要补 Windows 腿的动因）。
- `WindowAgent` / `WindowAgentBase` 里**没有任何 cursor 相关 API**（grep 零命中）⇒
  D1 要加的「边框不接管光标」开关若直接接进原生命中测试，**本机与 CI 都验不了**，
  只能真机手点——那等于给项目加一个没有回归网的开关。

深法：把命中测试里**不依赖原生后端**的那部分（边框 / 标题栏 / 可缩放区域的矩形划分与判定）
剥成纯函数，离屏可断言；D1 的开关接在它上面。

- 验收：`tst_qxwindow` 新增针对区域判定的断言，`offscreen` 下可跑 ⇒ **三条腿都覆盖**。
- ⚠️ 它是 **D1 的前置**（没有它，D1 没有回归通道），故与 D 组同批排，不单独计期。
- 反例提醒：**不得**为了可测把原生后端换成模拟后端——那会改变被测对象本身。

**C1b 待定区**：其余「做深」候选（如 `qxdock` 布局持久化三条路的收敛、`qxribbon` 新类的
最小 API 是否够用）**先不写进本文件**——它们需要先定对标口径（见 §一 判据表），

**C1c `qxribbon`：`RibbonPageContext::addPage(RibbonPage *)` 补齐对偶重载**（形态 1 · 补完备）
