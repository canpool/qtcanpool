# QtCanpool 4.6 任务规划（草稿 v1）

> 状态：**刚立项**（2026-10-18，4.5.0 发版当日开始规划）。本文件是 4.6 的权威任务分解。
> 定位由作者 2026-10-18 拍定；任务组为初稿，**按 4.5 的规矩持续追加**（新任务按所属组序号续编）。

## 一、版本定位与约束

- **定位：体验与基建收口，只做加法**（作者 2026-10-18 定）。
  4.5 是「允许破坏 API」的功能升级（K26），一口气改了主题 id、`qxtheme` 全接口、
  `RibbonBar::RibbonStyle` 四值改名、`QxNavBar` → `QxNavTabBar`。紧接着再破一轮对下游不友好，
  故 **4.6 只新增类/函数，不移除、不改签名**。
  ⇒ 若某项在开发中被证明不得不破坏，**不顺手破**——顺延到下一个允许破坏的 minor（K26）。
- 双支持：保留 Qt 5 / Qt 6（K30）；Qt 6.12 验证腿继续作为门禁（K31），4.6 复用不重建。
- 进号：本期**有新增 API** 的库进 minor，只有修复的进 patch（K11 / 附录 B）；
  构建接线不进号（4.5 已确立的判据）。
- ⚠️ **台账动态追加**：本文件在开发期内持续追加——已有组一律保留、新任务按所属组序号续编
  （A4、B4、C4…）。不存在「某组已封闭」或「整版做完」的中间状态，只有发版结算时一次性汇总。
  ⇒ 各组进度一律记为「当前已完成」。
- ⚠️ **台账只装本版要做的事**：不做的事（长期蓝图、别版的候选、选型勘察）**一律不写进本文件**，
  每个版本保持干净、不携带别的东西（作者 2026-10-18 定）。

### 「做深」的判据（C 组选题的唯一依据）

⚠️ 先定义再立项，否则「做深」会退化成「顺手加东西」。**做深 ≠ 做宽**：

| | 做深（本版要的） | 做宽（本版不要的） |
| :--- | :--- | :--- |
| 对象 | **已经存在**的能力 | 还没有的件 |
| 方向 | 补完备度、补健壮度、补可验证性 | 加新类 / 新控件 / 新库 |
| 验收 | 有明确的「做完」状态与回归通道 | 做到哪儿算完说不清 |

三条可验收的形态，C 组每条任务必须能归到其中一类，并写明验收通道：

1. **补完备度**：同一件事只做了一半 / 只在一条路径上成立（例：着色有单点、无整树；
   布局能存成明文了、另一条路还是黑盒 blob）。
2. **补可验证性**：从「只能靠真机手点」变成「离屏可断言」——**没有验收通道的项不进 4.6**。
3. **补健壮度**：边界与异常路径（损坏的布局文件、非法的样式表、大数据量）有确定行为。

反例（**不算做深，不得进 C 组**）：加新控件、加新库、为了「别人有」而补功能。

**对标参照：Qt Creator**（作者 2026-10-18 定）。本项目的定位原话就是「总结自 Qt Creator
源码结构」——同源、开源、已被真实应用证明，不必另找参照物。
⚠️ **对标的是「完备度的定义」，不是「功能清单」**：拿别人的功能清单当目标，做深立刻变成做宽。
⇒ 用法：选一个已有能力，列出它的完整生命周期逐格打分（有没有 / 可不可测 / 平不平台无关），
**只补「参照物做完了而我们做了一半」的格**，不补「别人有我们没有」的格（后者是做宽）。
⚠️ 不得用商用组件的功能清单当对标目标（合规）。

## 二、任务分解

### A 组 · 图标随主题（基建）

**A1 图标能力归位 `qxtheme`**（作者 2026-10-18 定：收进 `qxtheme`，不新建库）

⚠️ **硬约束——依赖图不允许「一份代码全库共用」**（2026-10-18 勘察）：

| 库 | 依赖 |
| :--- | :--- |
| `qxcore` | `Qt5::Core` |
| `qxtheme` | `qxcore` + Qt Core/Gui/Widgets |
| `qxwindow` | Qt Core/Gui/Widgets |
| **`qxribbon`** | **Qt Core/Gui/Widgets（不依赖 `qxtheme`，连 `qxcore` 都不依赖）** |
| **`qxdock`** | **Qt Core/Widgets + `Qt5::Svg`（不依赖 `qxtheme`）** |
| `qxplugin` | `qxcore` |
| `qxapp` | `qxwindow` `qxribbon` `qxdock` `qxtheme` `qxcore` `qxplugin` |

只有 `qxapp` 同时看得见三个库。因此「收进 `qxtheme`」的含义**只能是应用层统一**，不能是
「让 qxribbon/qxdock 去调 qxtheme」——那会引入两条新的库间依赖，把当前「三个外观库互不依赖」
的结构打破（该结构是 4.5 E7 刻意达成的：`qxtheme` 不依赖 `qxribbon`，`qxribbon` 也不反向依赖它）。

据此 A1 的范围定为：

- `qxtheme` 新增**主题感知图标的公共入口**：按调色板角色把单色图标染成当前主题色；
  对外是应用与 `qxapp` 用的那一层。
- `qxribbon` 的 `tintedIcon()` / `tintedPixmap()`（`ribbonutils.h`）与
  `qxdock` 的 `applyDockIcons()` / `refreshDockIcons()`（`dockiconprovider.h`）**保留不动**——
  两个库必须能脱离 `qxtheme` 独立使用。
- **一致性由规范 + 门禁保证，不由共用一份代码保证**（见 A2）。
- `qxapp` 提供「一键重染全应用」的编排（它唯一能同时调三者）。

**落地情况（2026-10-18）**：新增 `src/libs/qxtheme/qxthemeicon.h` / `.cpp`，四个入口——
`tintedPixmap()` / `tintedIcon()`（给一个明确颜色）与 `themedPixmap()` / `themedIcon()`
（给一个调色板角色，颜色取自当前 `QGuiApplication` 的调色板，也就是主题装进去的那一份）。
做法是**先光栅化、再按 alpha 重染**（与 qxribbon 同族）：与文件格式无关，
文件里原来是什么颜色都被替换掉，抗锯齿边缘的覆盖率保留；没有 QGuiApplication 时不染色、
把原图原样返回（没有调色板可问，但一个没染色的图标仍然是图标）。

- ⚠️ 这是**第三份实现**（qxribbon 一份、qxdock 一份、qxtheme 一份），但不是「双轨」问题：
  那两个库必须能脱离 `qxtheme` 独立使用，让它们反过来依赖它就把「三个外观库互不依赖」的结构打破了。
  三者的一致性由 `doc/pages/icons.md` 的规范 + `scripts/check-icons.py` 对齐，不由共用代码对齐。
- 未做：**A3**（切主题后自动重染的编排）。`themedIcon()` 已经把「按角色取色」这一步做掉了，
  A3 缺的是「主题变了以后由谁再来问一遍」。

**A2 图标资源规范 + 门禁**

⚠️ **先纠正规范草案里押错的一点：不要规定「必须写 `currentColor`」**（2026-10-18 核实）。
两套现有着色机制**都不靠它**，而且 Qt SVG 对 `currentColor` 的支持不可靠，规范不该押在上面。
实测两个实现的语义根本不同，这才是 A1「一致性靠规范 + 门禁」真正要覆盖的痛点：

| 机制 | 做法 | 与源颜色的关系 | 对多色图标 |
| :--- | :--- | :--- | :--- |
| `qxribbon::tintedPixmap()` | 光栅化后 `CompositionMode_SourceIn` + `fillRect` | **完全无关**——只保留 alpha，整幅换成目标色 | 被压成**纯色剪影**（配色信息丢失） |
| `qxdock::applyDockIcons()` | 替换 SVG 文本里的 `#ffffff` / `#fff` / `#a0a0a0` / `#000000` 四个**字面值**（`dockiconprovider.cpp:102-105`） | **强相关** | 只替换命中的那几个，**剩下的保持原色** ⇒ 颜色错乱 |

据此 A2 定为：

- 规范只规定**分类**：**单色**（可染）/ **多色**（豁免）。单色 = 字形只用一种颜色，
  **`fill` 还是 `stroke` 无所谓**——qxribbon 的 alpha mask 对两者一视同仁。
- **多色图标明确豁免**：qxribbon 会把它压成剪影、qxdock 会只替换一部分 ⇒ 两种结果都不对。
  豁免清单进仓库，门禁据此放行。
- 门禁（仿 `tools/themes/build_themes.py` 的对比度闸门）要报三类：
  ① 单色图标却混了多种颜色；② 未登记的彩色图标；
  ③ **要走 qxdock 着色却不含那四个字面值**（换图标集后最容易整片失效的一类）。

**落地情况（2026-10-18）**：规范落在 `doc/pages/icons.md`，门禁落在 `scripts/check-icons.py`，
登记表落在 `scripts/icons-policy.txt`，CI 在 `format` 作业的静态文本检查里加了一步
（与 `check-template-sync.py` / `check-encoding.py` 同列，都不需要工具链）。
当前 **99 枚受管图标、0 问题**。三类登记与规范色的定义只写在规范页，本文件不重复。

- ⚠️ **B2 期间怎么用**：`demos/qxapp/ribbondemo/res` 现按目录登记为 `plain`（存量旧图标不判颜色）。
  新图标落一枚就给它加一条**文件级** `tinted` 条目（文件级压过目录级），那一枚立刻受判定；
  等旧图标删完，再把目录级翻成 `tinted` + `alpha` 并删掉文件级条目。
  **中途不要把目录级一次性翻过去**——尚未替换的旧图标会同时不合格、CI 变红。

**A3 主题/调色板切换自动重染**

现状：染一次要靠应用自己监听 `ApplicationPaletteChange` 再调 `refreshDockIcons()`，
`qxribbon` 侧连整树重染的入口都没有。本项把「切主题 → 重染」做成 `qxtheme` 提供的编排能力
（应用 opt-in，库不强制外观——与 4.5 C10 的 opt-in 原则一致）。

**落地情况（2026-10-18）**：`QxThemeIcons`（同在 `qxthemeicon.h`）——应用把 action 交给它，
它**立刻**按角色染一次并记住「文件 + 角色 + 尺寸」，之后**应用调色板被换掉时自动重染**
（在 `QCoreApplication` 实例上装事件过滤器接 `ApplicationPaletteChange`；另外留 `refresh()`
给「换调色板没走 Qt 通告」或「图标文件本身变了」的情形）。`add()` 同一 action 覆盖而不重复绑定；
action 被销毁时在下一次重染时顺手剔除，不往野指针上画。
⚠️ **排在 B2 之前做**：否则 B2 换上去的新图标只在启动时正确、切主题时不跟着变——那正是本次要解决的痛点。
- 未做：应用侧「一键重染全应用」的编排（台账 A1 里归 `qxapp` 的那一层）——A3 只提供能力，
  谁来调由 `qxapp` / demo 决定；`qxapp` 那条不在 A 组，等 B2 推进到要用时再立。

- **入库要求**：带上游 LICENSE 声明；**只取用到的那几个**，不整包搬；
  **一律归一化**（见下）。

  ⚠️ **入库必须归一化**：Tabler / Lucide 的 SVG 默认是 `stroke="currentColor"`，

  `qxribbon` 那只认 alpha ⇒ 改成什么色都无所谓；`qxdock` 那只认 `#ffffff` / `#fff` /
  `#a0a0a0` / `#000000` 四个字面值 ⇒ **必须是具体值，否则整片失效**。
  约定单色字形的规范色为 `#000000`；`qxdock` 自带图标维持现状不动。
  ⇒ 结论与「Qt 是否解析 `currentColor`」**无关**，故不去押注它（本机探针未能跑起来，未实测）。

  **落地情况（2026-10-18，许可先行）**：许可已确认并入库——Tabler Icons **3.49.0**、MIT、

  （含来源、版本、施加了什么改动），并在根 `LICENSE.NOTES.md` 的 MIT 段登记。
  ⚠️ **只带用到的那几枚，不整包搬**；取图标随 B2 逐页进行，不在本条一次性铺开。

**第 6 页（Home）**——`homepage.h/.cpp` 的 `HomePage : RibbonPage`，14 枚新图标（ribbon 自身的
开关面板，也是旧实现里最长的一页）：
ribbon 自身开关（最小化、最小化按钮、应用按钮、四种 ribbon style、QAB 左/右、tab 居中、组标题、
全屏、窗口可最大化）、toolbutton 全谱（四种 popup 模式 + 图标/文字/长文本 + color button +
option action）全部页内闭环——够得着 `ribbonBar()` 或 `window()` 的都不出页。
出页的只有 4 个信号：`contextPageVisibleRequested` / `context2VisibleRequested` /
`contextPageDestroyRequested`（context tab 归窗口所有，且可**销毁后再显隐** ⇒ 窗口侧负责惰性重建）
与 `messageRequested`（写入主窗口编辑器）。

- ⚠️ **页面被 bar 收养之前 `ribbonBar()` 是空的**：`RibbonPage` 在构造函数里还没 `setRibbonBar()`，
  所以任何「构造时就要碰 bar」的接线都会拿到空指针。正解是等 `RibbonBar::insertPage()` 把页
  reparent 进 stack 时的 `ParentChange`（此时反向指针已设好），在 `attachToBar()` 里一次做完；
  **不要用 `QTimer::singleShot(0)`** 绕时序——那是靠事件循环顺序蒙对，不是确定时机。
- ⚠️ **small widget 必须 `setWindowTitle()`**：`ribboncustomizewidget.cpp` 拿
  `grpItem->widget()->windowTitle()` 当定制对话框里的条目名，**空名直接跳过**（该控件不会出现在
  定制列表里）。radio / checkbox 这些不是 action 的部件，`text()` 不算数。
- 全屏勾选的同步改为在顶层窗口装事件过滤器看 `WindowStateChange`（原来连
  `MainWindow::windowStateChanged`）：页面不必知道窗口的具体类型。

### C 组 · 库做深

**C1 `qxwindow`：把「只能真机手点」变成「离屏可断言」**（形态 2 · 补可验证性）

证据（2026-10-18 核实）：

- `qxwindow` 主体是 Windows 原生后端（`QX_WINDOW_CONFIG_NATIVE`），Linux / macOS 走 Qt 分支；
  CI 三条腿里**只有 Windows 会真正链接私有模块** ⇒ 另外两条腿对它「只编不验」，
  跨平台腿照不到它（同一事实也是 F1 要补 Windows 腿的动因）。
- `WindowAgent` / `WindowAgentBase` 里**没有任何 cursor 相关 API**（grep 零命中）⇒
  D1 要加的「边框不接管光标」开关若直接接进原生命中测试，**本机与 CI 都验不了**，
  只能真机手点——那等于给项目加一个没有回归网的开关。

深法：把命中测试里**不依赖原生后端**的那部分（边框 / 标题栏 / 可缩放区域的矩形划分与判定）
剥成纯函数，离屏可断言；D1 的开关接在它上面。

- 验收：`tst_qxwindow` 新增针对区域判定的断言，`offscreen` 下可跑 ⇒ **三条腿都覆盖**。
- ⚠️ 它是 **D1 的前置**（没有它，D1 没有回归通道），故与 D 组同批排，不单独计期。
- 反例提醒：**不得**为了可测把原生后端换成模拟后端——那会改变被测对象本身。

**C1b 待定区**：其余「做深」候选（如 `qxdock` 布局持久化三条路的收敛、`qxribbon` 新类的
最小 API 是否够用）**先不写进本文件**——它们需要先定对标口径（见 §一 判据表），
定了才进台账，避免本版携带没决定的东西。

**C1c `qxribbon`：`RibbonPageContext::addPage(RibbonPage *)` 补齐对偶重载**（形态 1 · 补完备）

B2 第 3 页（Context2）暴露的缺口：`RibbonBar::addPage(RibbonPage *)` 有两个重载
（自建 / 接收现成页），`RibbonPageContext::addPage` 只有 `addPage(title)` 一个——
context 页只能装「现造的裸页」，自带状态的 `RibbonPage` 子类进不去。
补 `addPage(RibbonPage *)`（不做所有权转移，调用方仍决定页面生死），
做 `addPage(title)` 对页面做的一切（`markIsPageContext(true)` + 登记 + 装事件过滤 +
`pageAdded`），只是不建造。验收：`tst_RibbonPageContext::builtPage`。

**C1d `qxribbon`：corner widget 的摆放补齐 + 回归**（形态 2 · 补可验证性）

作者 2026-10-18 提出的历史缺口：`resizeInTabBarBelowStyle` / `resizeInTabBarInlineStyle`
两处**都**为 `cornerWidget()` 算了几何，`minimumWidthInTabBar*Style()` 也把它算进最小宽度，
但仓库里**没有任何东西使用它**——旧 `ribbondemo` 的 `QMdiArea` 分支（`QXRIBBON_TEST_MDIAREA`）
在 4.4 被当死代码删掉后，这条路径连"跑一次"的机会都没有，更谈不上验证。

勘察结论（2026-10-18）：它其实**一直在用**，只是用的人不是本仓库——MDI 子窗口最大化时，
Qt 的 `QMdiArea` 会把子窗口的图标（`TopLeftCorner`）与最小/还原/关闭三个按钮
（`TopRightCorner`）装到宿主窗口的菜单栏上（`QMenuBar::setCornerWidget`）；ribbon 窗口里那个
菜单栏就是 `RibbonBar`，所以这正是那两个函数存在的理由（代码里那条
`LayoutRequest` + `ShowToParent`/`MouseButtonRelease` 的注释也是为它写的）。

顺带查出四处真缺陷，均已修：

- **运行中设置不生效**：`QMenuBar::setCornerWidget()` 非虚、也不请求重排，而新控件若没有父对象
  则一直是隐藏的（隐藏控件按 `takesPartInLayout()` 不参与布局）⇒ 控件停在出生位置 100x30。
  新增 `RibbonBar::setCornerWidget()`（同名影子方法）负责 `show()` + 请求重排。
- **尺寸变化后不重排**：布局给角控件的是 `sizeHint()` 的宽度，而它的尺寸由自己内容/字体/样式
  决定，变长后 bar 不重排（旧宽度 29、新 hint 129 也照旧）。`LayoutRequest` 闸门补一条
  `cornerWidgetsNeedLayout()`（宽度 ≠ hint 即重排）——这也是唯一一块"不由本类决定尺寸"的子控件，
  闸门的解释一并改写。
- **Qt 自己摆的角控件抢不回位**：`QMenuBar::setCornerWidget()` 非虚 ⇒ MDI 装的角控件走基类，而基类
  **自己也会摆**角控件（Qt 5/6 `QMenuBarPrivate::updateGeometries()`：左角在整条 bar 的高度里垂直
  居中、右角贴 `PM_MenuBarVMargin` 顶对齐）。那是菜单栏的摆法、不是 ribbon 的（ribbon 的行比 bar
  矮），而且它发生在本类上一次布局**之后**（Qt 是在角控件 `ShowToParent` 之后才摆的）。偏偏它给的
  宽度正好是 `sizeHint()` 宽度 ⇒ 只看宽度的闸门答"没问题"：实测 MDI 图标停在 `y=59`
  （`titleH=24`，即标题行下方）、右边三个按钮停在 `y=0`。闸门因此改成"宽度**或所在带**不符即重排"，
  垂直规则与 `placeCornerWidget()` 共用一份（`cornerBandGeometry()`），不重写第二遍；
  `LayoutRequest` 是此刻唯一的信号（Qt 摆完自己会 `updateGeometry()`），也正是本类唯一收得到的那次。
- **eventFilter 那条路从来没通**：`m_layoutRequest` 只由 `eventFilter` 里的角落分支置位，而全仓库
  没有把 bar 装成角控件的事件过滤器 ⇒ 闸门永远不开、`LayoutRequest` 分支等于死代码。既然宽度条件
  已经把"角控件该重排了"表达清楚，该分支与 `m_layoutRequest` 成员**一并删除**（不留一条不可达的
  路）；`doc/pages/limitations.md` 那条「LayoutRequest 可能带来多余的 resize 轮次」据此更正。

验收：`tst_RibbonBar::cornerWidgetTakesItsRoom`（两种样式 × 两个角，宽度/行位置/不压 tab 条）、
`cornerWidgetArrivesAfterTheBarIsUp`（运行中设置 + 变大）、`cornerWidgetInstalledThroughTheMenuBar`
（经 `QMenuBar*` 装，即 Qt 走的那条路：必须落回标题行，而不是被摆在 ribbon 中部）、
`maximizedMdiChildUsesTheCorners`（真的最大化一个 MDI 子窗口，断言 Qt 装的角控件在各自的行上、
还原后归零）。前两条挡缺陷①②，后两条挡缺陷③（把闸门退回只看宽度，后两条立刻红）。
实测：Qt 5 与 Qt 6 各 18/18（含 init/cleanup）。

⚠️ 附带记录一条 Qt 5 事实（不改代码）：Qt 5 + 主题样式表下，这三个按钮的**字形**会被裁掉
（`QMdi::ControllerWidget` 用字体算 sizeHint=67x23，而 `QStyleSheetStyle` 的
`PM_TitleBarHeight`=30，样式按后者把字形画在矩形底部）；高分屏下偏差翻倍，表现为"图标没显示"。
Qt 6 不复现。成因/证据/为什么不自绘已写进 `doc/pages/limitations.md`。

**C1e `qxtheme`：装主题时同时告知平台色方案**（形态 1 · 补完备）

作者 2026-10-18 提出的问题：`ribbondemo` 的 `main.cpp` 把样式固定成 `windowsvista`，理由是
Win11 + Qt 6.8 下界面跟着**系统**深浅色走（作者的机器是暗色），而 demo 起手是一套浅色主题，
两边不一致。

勘察（本机 Win11 暗色 + Qt 6.8.3 实测）：`windows11` 样式的配色**不读调色板**——它按
`QStyleHints::colorScheme()` 从自己的明/暗两张表取色（`WINUI3ColorsDark`），窗口边框也跟着色方案
（`QWindowsWindow::setDarkBorder`）。所以「装一套浅色调色板」对它一点用也没有，这与「暗色主题额外
把标准控件也重画」是同一条事实的两面。Qt 6.8 起可 `setColorScheme()` 覆盖系统值；6.7 及更早没有
这个口子，只能整条样式换掉（`windowsvista` 按调色板画）——那行 `setStyle()` 就是这么来的。

深法：引擎本来就负责回答「这个应用是亮是暗」（注册项的 `dark`），缺的是把同一句话**也说给平台**。
新增 `QxTheme::applyColorScheme(bool)` / `followSystemColorScheme()`，`QxThemeManager::apply()`
在 `setPalette()` 之前下发；**跟随系统时反过来交还平台**——钉死色方案会让 `colorSchemeChanged`
不再触发，跟随就断了。6.8 以下与不支持该请求的平台上是空实现。

- 验收：`tst_QxTheme::colorSchemeHintLeavesThePaletteAlone`（色方案是提示，不是第二套调色板）。
- demo 侧：6.8+ 不再改样式，改由主题决定色方案；6.7 仍留 `windowsvista`（无覆盖口子）。
- 附带修一处布局时序：默认主题从「事件循环第一轮」改到构造期装上。原来既会先闪一帧系统色，
  又会让 Ribbon 用**装表之前**的 hint 摆完就不再重排——`windows11` 下实测 QAB 因此窄 3 px
  （容器 173 / hint 176，内层 153 / hint 156），最后一个按钮（customize and save）被父控件裁掉，
  图上直接少一个图标。

**C1f `themes`：亮暗两套骨架对齐到同一份状态集**（形态 2 · 补可验证性）

作者 2026-10-18 看过 `ribbondemo` 的亮暗截图后指出两处：暗色下勾选项的选中底是
`#235A85`、亮色下同一位置是 `#EFF6FC`；以及 `skeleton_dark.css` 有
`QCheckBox:checked { color: text-on-fill }` 而 `skeleton_light.css` 没有这条。要求统一。

勘察（按选择器做全量差集，先扣掉 chrome 已覆盖的 30 条）：骨架真正负责的 ribbon 选择器
亮色 52 条、暗色 67 条，其中 **19 条只有暗色有、4 条只有亮色有**。但那 4 条
（`RibbonComboBox` 系列）不是缺失——暗色要重画标准控件，用通用 `QComboBox`/`QLineEdit`
覆盖，亮色则交给平台样式，这正是两份骨架长度不同的原因。暗色多出的 19 条里，一部分是
颜色角色（`state-hover` vs `accent-faint`），属于明暗反转的语言；**另一部分与明暗无关，
却只写了一侧**。

改法：

- **亮色补 6 处**：`RibbonGroup QAbstractButton` 与 `RibbonButtonGroup QAbstractButton`
  的 `padding: 0`、`RibbonButton[popupMode="1"]` 的 `padding-right: 0`、
  `RibbonQuickAccessBar` 下的 `QLabel` 底色与 `QToolButton` 的 20×20 /
  `QAbstractButton` 的 `padding: 0`；以及 `RibbonGroupOptionButton` 的
  `:focus` / `:pressed` / `:checked` —— 该控件在亮色下选中时此前**毫无反馈**（暗色一直是
  实心强调色）。前三组是布局：padding 与尺寸决定了 ribbon 量出来的大小，只在一侧写，同一个
  窗口在两种主题下就会量出不同的宽度与行高。
- **暗色删 4 处**：`QCheckBox:checked, QRadioButton:checked { color: text-on-fill }`
  ——勾选框的 checked 只该换指示器，不该改标签颜色；而且这条在暗色下等于没有效果
  （`text-on-fill` 是 `#ffffff`，`text` 是 `#f3f2f1`）。另外 `RibbonTabBar`、
  `::tab`、`::tab:selected` 三处 `font-weight`：字重会改变 tab 的文本宽度，而 tab 宽度
  参与 `calcMinTabBarWidth()`，加粗只在一侧就等于同一窗口在亮暗下最小宽度不同。
- **不动的部分**（并在骨架里写明为什么）：tab 造型（亮色是抬高的卡片、暗色是底部强调线）、
  文件按钮（亮色实心方块、暗色透明+底线）、各状态的填充角色（亮色浅洗、暗色实心）—— 这是
  两份文件开头那段「a light scheme keeps every state fill light … the dark skeleton does
  the opposite」的既定设计，不是漂移。`tools/themes/README.md` 补了一节把这个判据写下来。

验收：10 张 sheet 过生成器门禁；soft / classic / accent / flat / slate 五族亮暗截图并排
复核（同一控件的同一状态在两套里位置一致、只有深浅不同）；`qt5` / `qt6` 各 18/18。

**C1g `res/dockstyle`：dock 样式表里只对亮色成立的四条规则**（形态 1 · 补完备）

B4a 给 `dockdemo` 接上主题，一开暗色就四处露馅（作者同批报出第 2、3 条）。逐条查角色才发现
四条表里有**四类规则只在亮色下成立**，而它们此前从未被暗色检视过——因为**这个 demo 之前根本
没有主题**，四张表只被一套配色看过：

- **未选中标签的标题看不见**：`QxDock--DockTab QLabel { color: palette(dark) }`。
  `QPalette::Dark` 由窗口色派生（`window.darker(150)`），暗色下 `#292929` 再压暗成一抹近黑，
  标签标题直接沉进标签里。改 `palette(placeholder)`——Qt 给「同一段文字、但更安静」的角色，
  qxtheme 把它设成 `textDisabled`（两套配色都是 `#a0a0a0`）。亮色下由 `#7a` 变 `#a0`，
  仍明显弱于激活标签的正文色。
- **暗色下每个标签中间一条更深的板**：`QxDock--DockTab QLabel` 命中即意味着样式表会**画这个
  控件的盒子**，而规则里没有背景可画 ⇒ 退回**样式自己的**窗口色（`windows11` 暗色 `#1f1f1f`），
  既不是标签的也不是面板的（实测标签行：标签内 31 / 标签外 41）。加 `background: transparent`
  把像素还给标签即可，亮色零变化（改前后同为 `#f5f5f5`）。
- **亮色下选中标签黑字压蓝底**：`QxDock--DockTab[focused="true"] QLabel` 与上面的
  `[activeTab="true"] QLabel` **特异性相同**（各一个属性 + 同样两个类型选择器），而 Qt 在两条
  等特异性规则里**保留先声明的那条** ⇒ `[focused]` 那条从来没生效，标签拿到的是
  `palette(foreground)`（亮色 `#0f0f0f` 压在 `#0078d4` 上）。改成同时带两个属性的选择器即可压过它；
  ⚠️ **写成逗号并列的两个选择器不行**——列表按其中最不具体的那个计权，等于又退回原位（实测：
  组合选择器单独写 → 品红生效；与 `[focused]` 并列写 → 品红不生效）。
- **压在强调色上的文字**（聚焦标签 / 自动隐藏标题 / 活动浮动窗标题）原本写 `palette(light)`，
  它描述的是**表面**不是填充：暗色下变成 `#353535` 的深灰压在蓝底上。改 `#ffffff`——**只能
  是字面量**：本该说这句话的角色是 `palette(highlightedtext)`（`palette(brighttext)` 同值），
  而这两个名字**不在样式表 `palette()` 查找支持的名单里**（实测：换成它们声明被丢弃、标签保持
  原色；换成 `palette(light)` / `palette(placeholder)` / `palette(midlight)` 都生效）。
  强调色两套配色都是 `#0078d4`，所以白字在两边都对，ribbon 主题写 text-on-fill 也是同一个路子。
- **图标按钮的 hover / pressed**：`rgba(0, 0, 0, 16/24/48)` 是一层黑纱——压在暗色标签上是
  9% 的黑、4 级色差，等于没有反馈；压在亮色上是一坨灰。改 `palette(midlight)`（hover）与
  `palette(light)`（pressed），两者都由窗口色派生，表不需要知道自己服务的是哪套配色。

⚠️ **验收通道**：`demos/qxapp/dockdemo --theme soft-light|soft-dark` 两张截图并排
（`dockdemo` 的金标只覆盖默认那一张，明暗两张要看图）；qt5 / qt6 各 18/18。
⚠️ 这条同时更正 4.5 C9/C10 的结论「dock 外观随 `palette(...)` 跟随明暗，**唯一不跟随的是内置
单色 SVG 图标**」——不跟随的还有这四类规则，背景类规则确实跟随。
⚠️ 顺带记一条 Qt 事实（值得单独记住）：**样式表里等特异性的规则，先声明的赢**（与 CSS「后者
赢」相反）；逗号并列的选择器按其中**最不具体**的那个计权。两条都是这次靠"把颜色换成
rgb 字面量看它生不生效"试出来的，不是查文档得来的。

- **dock 现代化（B4）的下一批候选**（2026-10-18 勘察，均**未立项**，先做完再定）：

  ② **持久化三路收敛**：`saveState()`（blob）/ `saveStateToFile()`（明文 XML）/ `QSettings`
     三条路与内存态是否等价；顺带定 `XmlAutoFormattingEnabled` 等表示形式选项的口径

     （压深）与 `rgba(255,255,255,92/96)`（提亮）。压深在暗色表面上算下来只有 3 级色差
     （`#292929` 上叠 9% 黑），等于没有反馈；提亮那几处压在强调色上，两套配色都成立。
     要治得让叠色跟着表面走（`palette(mid)` 之类「比窗口色深一档」的角色两边都成立），
     或者给 dock 表也来一套明暗两份——后者是 `res/themes/` 的做法，但四张表会变八张。
     **卡点**：hover / pressed 状态**静态截图拍不到**，验收通道要先想清楚。
  ④ **主题切换等价测试**：`tst_demoscreenshot::themeSwitchMatchesAFreshStart` 现在只跑
     `ribbondemo`（内部变量就叫 `m_ribbonScreenshot`）。`dockdemo` 有了 `--theme` 之后
     同样能进这条断言——切过去与直接启动应逐像素一致，谁没跟上一次换主题就现形。
  ⑤ **引擎在「注册之前」先 apply 了一次**：`QxThemeManager::instance()` 的 `start()` 会
     从配置里读回上次的主题并立刻 `apply()`，而注册主题的调用（`registerBundledThemes()`
     或应用自己的 `registerTheme()`）只能发生在 `instance()` **之后**——于是第二次启动
     必然先装一次「谁都没注册」的主题：`apply()` 找不到该 id ⇒ 一条
     `QxThemeManager: no theme registered under '...'` 警告（实测 `dockdemo` 第二次运行必现），
     且那一帧用的是 Qt 起来时的调色板。修法是让首次 `apply()` 等到第一次注册之后
     （`start()` 只读 id 不装），属行为变更而非加法 ⇒ 要不要动、怎么动由作者定。
