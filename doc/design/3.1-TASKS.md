### A1 迁入 `qxapp`（通用控件）

| 来源                                                          | 去向（`QxApp::`）              | 备注                        |
| :---------------------------------------------------------- | :------------------------- | :------------------------ |
| `FancyToolButton`                                           | `QxToolButton`             | 通用按钮外观                    |
| `ExtensionButton`、`MenuButton`、`MenuAccessButton`            | `QxExtensionButton`、`QxMenuButton`、`QxMenuAccessButton` | 通用小控件  |
| `TinyTabBar`、`TinyTabWidget`、`TinyNavBar`                    | `QxTabBar`、`QxTabWidget`、`QxNavBar` | 轻量 Tab / 导航（通用性高）         |

**规则**：迁入时**改名入 `QxApp` 命名空间**（去掉 `Fancy`/`Tiny` 前缀），并在 `qcanpool` 保留同名转发类
（继承 + 构造转发）一个版本，避免二次破坏。

> **与原计划的差异**：原表把 `FancyWindow`/`FancyDialog` 列为"迁入 `qxapp`，与 AppShell 能力合并"。
> 落地时结论是**迁不动**——它们不是独立窗口，而是 `FancyWindow` chrome 家族的根：`FancyTitleBar`、
> `WindowLogo`、`WindowToolBar`、`MiniTabBar` 都由它装配。只搬走根节点、把装配方留在原处，
> 等于在 `qxapp` 里复制一套半截的窗口框架，而 `qxwindow` 已经提供了完整且更现代的实现。
> 因此二者改判为 A2 一并下线（见下表），`qxwindow` / `QxAppShell` 就是它们的替代。

### A2 下线（与 `qx*` 重叠、无独立价值）

| 控件                                              | 理由                                         |
| :---------------------------------------------- | :----------------------------------------- |
| `QuickAccessBar`                                | 已被 `RibbonQuickAccessBar` 取代                |
| `FancyTitleBar`、`WindowLogo`、`WindowToolBar`     | 与 `qxwindow` / `qxribbon` 窗口方案重叠           |
| `MiniTabBar`、`MiniTabWidget`                    | 与 `Tiny*` 系列重叠                             |
| `FancyBar`、`FancyTabBar`、`FancyTabWidget`        | 与 `Tiny`/`Mini` 重叠（原计划"三选一"，落定为全部下线）        |
| `FancyWindow`、`FancyDialog`                     | 见 A1 注；无法在不牵连整个 chrome 家族的前提下迁入 `qxapp`    |

**落地形态**：11 个类连同它们的 demo / example / manual test 一起物理删除，`doc/design/3.0-MIGRATION.md`
给出逐一替代对照。删除后 `qcanpool` **不再含任何翻译单元**，只剩 A1 的 7 个转发头（外加 `qcanpool.h`
与资源文件）。

### A4 补 `deprecated` 标注

**目标**：使「编译告警即迁移点」成立——用旧名的每一处都应该是**编译期可见**的迁移提示。

**结果**：A2 删掉了原来"18 个 `fancy*`/`tiny*`/`mini*`/`menu*`/`window*` 头一个字都没标"里的 11 个，
剩下的 7 个转发头在 A1 就是按 `QCANPOOL_DEPRECATED_X` 写的——**A4 因此随 A1 一并完成**，
无需再逐头补标。当前状态：

| 头                        | 标注                                            |
| :----------------------- | :-------------------------------------------- |
| `extensionbutton.h`      | `use QxApp::QxExtensionButton instead`        |
| `fancytoolbutton.h`      | `use QxApp::QxToolButton instead`             |
| `menuaccessbutton.h`     | `use QxApp::QxMenuAccessButton instead`       |
| `menubutton.h`           | `use QxApp::QxMenuButton instead`             |
| `tinynavbar.h`           | `use QxApp::QxNavBar instead`                 |
| `tinytabbar.h`           | `use QxApp::QxTabBar instead`                 |
| `tinytabwidget.h`        | `use QxApp::QxTabWidget instead`              |

**验证方式（库外实测）**：告警宏在**编译库自身时是空宏**，所以必须在库外翻译单元里验证。用一个临时
探针 TU（`#include "qcanpool/<name>.h"` + 逐个具名化）以 `-fsyntax-only -Wdeprecated-declarations` 编译：

```
7 条 warning: '<Name>' is deprecated: use QxApp::<New> instead [-Wdeprecated-declarations]
```

并进一步加 `-Werror=deprecated-declarations` → **退出码 1**，证明它可以直接当门禁用，
而不只是"看起来会报"。

## 四、B 组 · 质量门禁补齐

### B1 覆盖率报告

- CMake 新增 `option(WITH_COVERAGE)`：GCC/Clang 下加 `--coverage`，链接加 `--coverage`；**不要**污染 Release 默认配置。
- CI：在 `ubuntu-latest / Qt 6.8.1` 腿追加覆盖率构建 + `lcov` 生成 HTML，产物上传为 artifact。
- **K8 决策**：**先出报告、不设阈值**；连续 1~2 个版本稳定后再议是否设门禁。

### B2 clang-tidy + 消毒器

- 新增 CI 作业 `clang-tidy`：只跑 `src/libs`（`compile_commands.json` 由 CMake 导出，需 `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`）。
- 起步策略：**先只报新增告警**（或对既有告警设 `--line-filter` / 基线文件），避免一次性引入上百条噪声。
- 把仓库已有的 `WITH_SANITIZE` 真正用起来：CI 增加一条 `ASan+UBSan` 的 Linux Debug 构建腿（可只构建不跑测试，或跑 `ctest`）。

### B3 `qxwindow` 自动化测试

- 新建 `tests/qxwindow/auto/`（`main.cpp` + `tst_*.cpp`），在 `tests/CMakeLists.txt` 用 `add_qtc_test(tst_qxwindow DEPENDS qxwindow ...)` 注册。
- 优先覆盖**平台无关逻辑**：窗口上下文选择、尺寸/命中几何计算、`QX_WINDOW_CONFIG_NATIVE` 开关下的降级路径。
- 原生后端（Win/macOS/X11）只做"能构造、不崩"级别冒烟，避免 CI 平台差异导致脆断。

### B4 demo 截图回归（可选）

- `QT_QPA_PLATFORM=offscreen` 下启动 `RibbonDemo`/`DockDemo`，截图与 golden image 比对。
- **易碎**，建议置于 3.1 末尾且**允许失败不阻塞**；先只做 1 个 demo 验证可行性。

### A1 · legacy 通用控件迁入 `qxapp`（已完成）

提交 `d54a5d52`（`refactor(qcanpool)!`），31 文件，**+766/−486**（改名保留：`git diff -M` 仍识别为
rename，说明只是改名而非重写）。

**7 个类换名换家**（`qcanpool/Fancy*`·`Tiny*` → `qxapp/Qx*`）：`FancyToolButton`→`QxToolButton`、
`ExtensionButton`→`QxExtensionButton`、`MenuButton`→`QxMenuButton`、`MenuAccessButton`→`QxMenuAccessButton`、
`TinyTabBar`→`QxTabBar`、`TinyTabWidget`→`QxTabWidget`、`TinyNavBar`→`QxNavBar`。同步改：头文件守卫宏、
`QCANPOOL_*`→`QX_APP_*`、`QCP_*`→`QX_*`、`#include "qcanpool.h"`→`"qxapp_global.h"`、私有类名、
所有 `qrc`/`setObjectName` 字符串（`qtc_*` 前缀）、CMake `SOURCES`、`qxapp-lib.pri`、`header.list`。

**兼容层**：`qcanpool` 保留 7 个同名转发头——**继承新类 + 转发全部构造函数 + `QCANPOOL_DEPRECATED_X`**。
之所以用"真子类"而不是 `using Alias = QxApp::QxX`：别名会让旧名**静默**通过（没有告警，没有迁移点），
而子类在保留源码兼容的同时一定会响。代价是 `TinyTabBar` 从此是**另一个类型**——凡是把旧类型
互相混用或接收 `TinyTabWidget::tabBar()` 返回值的代码需要改（`examples/qcanpool/tinytabwidget`
就是一处，已改 `auto*`）。这个代价是刻意的，也是 A4 想要的东西。

**命名决策（K3 的延伸）**：新名一律含 `Qx`，因为 qcanpool 必须在不硬编码命名空间的前提下称呼它们
——统一走 `QX_APP_PREPEND_NAMESPACE(name)`，库里展开为真实类名，库外展开为 `QxApp::name`。

**验证（本机实测）**：`CFG_RC=0` / `BUILD_RC=0` / `ctest` **8/8** / clang-format 门禁 **351 文件**
通过；构建日志里能看到告警端到端生效（当时的使用者是 `demos/qcanpool/fancydemo`）：

```
demos/qcanpool/fancydemo/mainwindow.cpp:59:31: warning: 'FancyToolButton' is deprecated:
  use QxApp::QxToolButton instead [-Wdeprecated-declarations]
```

**踩到的坑**：批量改名脚本误伤了**同前缀的 Qt 枚举**——
`QStyle::SP_ToolBarHorizontalExtensionButton` 被改成了 `SP_ToolBarHorizontalQxExtensionButton`，
构建直接报 `is not a member of 'QStyle'`。改用"只改独立标识符"的边界匹配（`grep -nE '[A-Za-z0-9_]Qx[A-Z]'`
复查）后归零。另一处是 `qxtabwidget.*` 里裸的 `TinyTabBar` 标识符没被头名规则覆盖，需二次替换。

**行尾事故（值得记）**：15 个搬迁文件里实际只有 2 个原是 CRLF，其余是 LF；而 `sed` 输出一律是 LF，
于是 `git ls-files --eol` 报出 `i/crlf w/lf` 这种自相矛盾的状态。**地面真相只能取自索引**
（`git cat-file -p $(git rev-parse :<path>)`）与 `od -c`。按 2 CRLF / 13 LF 还原后，
rename 的 delta 从 1558/1278 行降到 766/486 行——**delta 大小本身就是行尾是否被误改的探针**。
另：`core.autocrlf=input` 下要让工作区的 CRLF 原样进索引，必须 `git -c core.autocrlf=false add`。

### B2 后续 · 消毒器抓到的第一处真实 UB（已完成修复）

`quality` 作业首次上线（`8bcb6c7d`）即失败，正是消毒器在工作：

```
dockcontainer.cpp:950: runtime error: member call on address 0x… which does
not point to an object of type 'DockWindow'; object is of type 'QxDock::DockContainer'
  #0 QxDock::DockContainer::~DockContainer()  dockcontainer.cpp:950
  #1 QxDock::DockWindow::~DockWindow()        dockwindow.cpp:393   ← 基类析构调用点
```

**根因**：`DockWindow::DockWindow()` 用 `DockContainer{this, parent}` 把**自己**登记为窗口。
`~DockContainer()` 里 `d->m_window != nullptr` 恒成立，于是这一行会**从基类析构回调派生类**：
此时 `~DockWindow()` 的函数体（含 `QX_FINI_PRIVATE()`）已经执行完，对象动态类型已退化为
`DockContainer`，私有数据也已释放。当前之所以"能跑"，只是因为
`DockWindow::removeDockContainer()` 恰好有 `this != container` 自反守卫提前返回；但按标准这仍是
UB，且离 null 解引用只差一个条件（`d` 已是空指针）。

**修复**（保持原语义，仅去掉 UB）：

- `dockcontainer.cpp`：析构里改为 `if (d->m_window && d->m_window != this)`——沿用构造函数里
  **同一个**自反判定，真正需要反注册的子容器不受影响；
- `dockwindow.cpp`：`removeDockContainer()` 增加 `d` 非空判定——容器若是本窗口的子部件，
  会由 `~QWidget()` 在私有数据释放**之后**销毁，此时"从即将消失的列表里摘掉自己"应是空操作
  而不是崩溃。

**验证**：本机 MinGW 的 GCC 13.1 **不随附 `libubsan`/`libasan`**（`cannot find -lubsan`），
无法本地复现，最终以 CI 的 `quality / ubuntu` 腿为准；本机侧仍完成 `CFG_RC=0` / `BUILD_RC=0` /
`ctest` 8/8 / clang-format 351 文件通过。

### B2 后续 · 第二处：侧边栏对空指针的成员调用（已完成修复）

修完第一处后复跑，`quality` 又红——但**报的是另一处**（`halt_on_error=1` 一次只报第一条，
所以这是"修一处、露一处"的正常节奏）：

```
docksidebar.cpp:152: runtime error: member call on null pointer of type
'struct DockFocusController'
  #0 QxDock::DockSideBar::insertDockWidget()          docksidebar.cpp:152
  #1 QxDock::DockContainer::createAndSetupAutoHideContainer()
  #2 QxDock::DockWindow::addAutoHideDockWidgetToContainer()
  #3 tst_DockContainer::autohide()
```

**根因**：`DockWindowPrivate::m_focusController` **只在 `DockManager::FocusHighlighting` 打开时
才创建**（`dockwindow.cpp:93`），而该标志**默认关闭**。`DockWindow` 里所有其他使用者都写了
`if (d->m_focusController)`，`docktab.cpp` 的四处也都前置了 `testConfigFlag(FocusHighlighting)`
——**只有 `DockSideBar::insertDockWidget()` 这一处漏了守卫**，于是默认配置下走自动隐藏就会对空
指针发起成员调用。之所以一直没炸，是因为 `clearDockWidgetFocus()` 的 `this` 恰好没被用到
（其调用的 `updateDockWidgetFocusStyle` 是文件级 static 自由函数）；一旦有人往它里面加一句
用到 `this` 的代码，立刻变成崩溃。

**修复**：按仓库既有风格补上守卫——

```cpp
if (auto *focusController = w->dockWindow()->dockFocusController()) {
    focusController->clearDockWidgetFocus(w);
}
```

并顺带**全仓审计**了所有 `dockFocusController()` 调用点，确认再无遗漏（`docktab.cpp` ×4、
`docktitlebar.cpp` ×1 均已前置判断）。

> 两处都不是新引入的回归，而是 3.0 之前就埋着的**既存缺陷**——这正是 B2 想让 CI 长期承担的角色：
> 这类缺陷不会在功能测试里显形，只有消毒器会说话。
