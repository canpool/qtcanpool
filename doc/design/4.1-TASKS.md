## 一、背景与现状（2026-10-11 勘察）

### 1.1 4.0 刚交付的是什么

4.0 换掉的是**骨架**：全树 qmake 归零（88 个文件）→ 构建方式只剩 CMake；新增 `qxplugin`（契约 /
发现 / 依赖 / 隔离 / 对象池）→ 应用可以按元数据长出模块；`src/modules` + `IdeShellDemo` 证明这条路
走得通；行尾归一为 LF（K20）。换句话说，4.0 动的是**别人怎么用它**。

### 1.2 为什么下一版不接着做插件

4.0 已经把插件的边界写进了非目标，而且是**刻意**的：

> 不做热插拔 / 运行时安装插件（启用或停用后重启生效，Qt Creator 亦如此）；不做插件市场；
> 不做脚本化插件；不做进程隔离；不做异步生命周期。

这些不是"没来得及"，是"想清楚了不做"。继续在插件线上加码只会把 4.0 刚划下的边界又抹糊。
真正没被照顾到的是另一半：**用户每天盯着的那个窗口**。

### 1.3 勘察：源码里自己写下的欠账

`src/libs/**` 里带 `TODO` / `FIXME` / `XXX` 的注释共 **25 条**，分布如下：

| 库 | 条数 | 说明 |
| :--- | :--- | :--- |
| `qxribbon` | 11 | 无边框（DPI、Linux 拖拽）、`RibbonBar` 布局请求、定制对话框的"应用/缓冲" |
| `qxwindow` | 9 | **几乎全是继承来的**：`windowcontext_win.cpp` / `windowsystem_p.h` 源自 Qt 自己的 `qwindowswindow.cpp`，连标记写法（`### FIXME FIXME FIXME`、`### TODO: How to handle touch events?`）都一样 |
| `qxdock` | 4 | 标签栏的"滚动到可见"、`toggleView()` 的显示顺序、手柄父子关系、分割条性能 |
| `qxapp` | 1 | `WpsLiteStyle` 下右侧按钮组的短暂重叠 |

两个值得记下来的观察：

1. **4.0 新写的代码一条都没有**（`qxplugin` / `src/modules` / `QxPluginManagerDialog` / `IdeShellDemo`
   全部 0 条）。欠账全在**老库**里——这不是巧合，是因为老库是"用出来"的，新库是"设计出来"的。
2. `qxwindow` 那 9 条里，本仓库自己写下的只有 **1 条**：`windowcontext_win.cpp:80` 要求把 Qt 6.5.3
   纳入实测（附两个 Gitee issue 号 `#I8SPBC` / `#I8SPC8`）——那是**测试**欠账，不是代码欠账。
   其余 8 条（含 `### FIXME FIXME FIXME` 那三行，是同一个注释块）跟着 Qt 一起继承，本轮**不认领**
   （认领只会让"清账"这件事变成假动作）。

因此 **4.1 要处置的是 16 条**：`qxribbon` 11 + `qxdock` 4 + `qxapp` 1。

### 1.4 其中哪些是真缺陷，哪些只是"想更好"

不需要读代码就能分出来的，至少有这三条：

- **`qxdock/docktabbar.cpp:72`** —— `DockTabBar` 把"把当前标签滚进可见区域"整段**注释掉了**，
  原因是它"会让程序意外结束"（issue #520 的同款写法，那段 `QTimer::singleShot(0, q, [&, tab]{...})`
  按引用捕获 `this` 悬垂）。也就是说：**症状没解决，解法被禁用**。
- **`qxribbon/framelesshelper.cpp:146`** —— DPI 硬编码 `96`，而注释里已经点名了正确 API
  （`GetDpiForWindow` / `GetDpiForMonitor` / `GetDpiForSystem`）。高 DPI 屏上是真会画错的。
- **`qxdock/dockwidget.cpp:1183`** —— `toggleView(true)` 会把侧边栏标签排在主窗口前面显示，
  是个能看见的顺序错误。

其余的（布局请求次数、定制对话框缺缓冲区、分割条没缓存）是"能用但知道不够好"，
处置方式与上面三条**不同**——见 K21。

## 二、目标与非目标

### 目标

1. **看得见的部分不再有"已知但不管"的毛病**：`qxdock` / `qxribbon` / `qxapp` 里自己写下的
   16 条欠账，**每一条都有结论**；
2. 结论是"修好了"的那些，**带回归测试**，且在 CI 门禁内跑；
3. 结论是"改不了/不值得改"的那些，**变成文档里的已知限制**，而不是继续躺在注释里；
4. 顺带把 K8（覆盖率是否设阈值）复核掉——它从 3.1 挂到现在，已经过了三个版本。

### 非目标

- **不加控件、不加库**（延续 K10：能力项只收"真实应用反复手写"的件）；
- **不接着扩插件体系**：4.0 的非目标一条不改（热插拔、市场、脚本、进程隔离、异步生命周期）；
- **不认领从 Qt 继承来的注释**（`qxwindow` 那 8 条）——只把"我们自己的那 1 条"处置掉；
- **不为消灭注释而消灭**：修不了就写清楚它为什么修不了，不假装修好；
- **不做 QML/Quick**（延续 3.0）。

### A1 · `DockTabBar` 的"滚动到可见"

现状（`docktabbar.cpp:72`）：那段"同步算矩形有时会失败，所以用 `QTimer::singleShot` 挪到事件循环里"
的写法**被整段注释掉**，理由是"会让程序意外结束"。症状与 `issue #520` 同源：当前标签被切到
滚动区外时不会自动滚回来，用户看不到自己点的那个标签。

要弄清的是**为什么它会结束进程**，而不是再把它注释一次：

- `QTimer::singleShot(0, q, [&, tab] { q->ensureWidgetVisible(tab); })` 里 `[&]` 把**局部变量**
  `q`（`Q_Q(DockTabBar)` 展开出来的 `DockTabBar *const q`）**按引用**捕获了。定时器是"0 毫秒"，
  但**不是在调用点执行**——等事件循环跑到它时，`updateTabs()` 的栈帧早就没了，
  lambda 体里的 `q` 读的是一格已被复用的栈内存。**这就是进程意外结束的直接原因**
  （已实测复现，见执行记录）。
- 次要的一层：`tab` 是按值捕获的裸指针，而标签（以及它的 `DockWidget`）可能在事件循环跑到之前
  就被销毁——`DockTab` 是 `DockWidget` 的子对象，`deleteDockWidget()` 会连它一起删。
- 第三层：`ensureWidgetVisible()` 会触发布局，而 `updateTabs()` 本身常常**就在布局过程中被调用**，
  从事件循环里再回去改布局是重入。

**实际落法**：把这段从循环里提出来，落到 `DockTabBarPrivate::scrollTabIntoView(DockTab*)`，
一次 `updateTabs()` 只可能排一次（`m_scrollPending`）；延迟调用同时上两道保险——
`QPointer<DockTab>` 守目标对象，`q` **按值**捕获并作为定时器的 context object 守调用方。
细节见 `4.1-TASKS.md` 执行记录 A1 与 `docktabbar.cpp` 的函数注释。

### A2 · `DockWidget::toggleView()` 的显示顺序

`toggleViewInternal()` 里有一段被禁用的调用：`d->m_panel->autoHideContainer()->toggleView(open)`，
注释写的是"`toggleView(true)` 会让 sidTab 排在主窗口前面显示"。查下来这段**不需要**：

- 用户点来唤回固定（auto-hide）控件的那张标签属于**侧边栏**，
  侧边栏自己管它的显示——`DockSideBar::insertTab()` 里 `show()`，
  `DockSideBar::removeTab()` 在最后一个标签移除后 `hide()`；
- `DockAutoHideContainer::toggleView()` 在库内**没有任何调用者**（本次 grep 过全库），
  也就是说它是被这段注释吊着的一段死路径；
- 那个"顺序问题"是真的，但成因正是从 `toggleViewInternal()` 去显示标签：
  `restoreState` 期间控件会 `toggleView(true)`，而那时主窗口还没 show，
  于是标签先冒出来。

**按 K21 第 ③ 条处置**：删掉注释掉的调用与 FIXME，改成一句说明"侧边栏拥有标签的可见性"。

**顺带补了一个把它钉住的测试**（`tst_dockwidget.cpp::autoHideSideTab()`）：
固定一个控件后关闭再打开，**侧边栏标签数不变、标签对象不变、pin 不丢**，
`saveState()` / `restoreState()` 往返之后同样如此——即那条被删的注释后面并没有藏着一个活着的 bug。

### A3 · `DockResizeHandle` 的父子关系

`setHandlePosition()` 里 `parentWidget()->width()` 那行上面的 FIXME 问"该用 `parentWidget()`
还是 `m_target->parentWidget()`"。**两个写法指的是同一个对象**：构造函数 `DockResizeHandle(edge, parent)`
里 `Super(parent)` 定下父子关系，紧接着 `d->m_target = parent`，而 `m_target` 没有 setter——
它被钉死在构造参数上。所以这不是"没说清"，是"不存在分歧"。**按第 ③ 条处置**：删掉 FIXME，
改用 `m_target`（与文件其余部分一致，且它直接说明了"在量谁"），并补一句说明：
这里算出的上限只是构造时刻的初值，真正的上限由
`DockAutoHideContainerPrivate::updateResizeHandleSizeLimitMax()` 从 dock container 的 `contentRect()`
重新算——那才是拖拽时实际遵守的值。

### A4 · `DockSplitter::hasVisibleContent()` 的缓存

TODO 想缓存这次遍历，**按第 ③ 条处置：不缓存，并写明理由**。遍历在第一个可见子控件处就返回，
而 splitter 的子控件是**个位数**；调用频率是"每个布局周期一次"
（`hideEmptyParentSplitters()` 沿 splitter 树向上爬，`DockContainer::contentRect()` 问根 splitter）。
而缓存要正确就得在每次子控件 show/hide/增删时失效——**失效的代价比省下的遍历大**，
这也正是 K21 第 ③ 条要挡住的那种"为清账而清账"。

### B4 · 定制对话框的"无缓冲 / 缺应用按钮"

`ribboncustomizedialog.cpp:91/93` 与 `ribboncustomizewidget.cpp:1123/1169/1172` 五条其实是
**同一个**毛病：定制数据没有"草稿态"，改了就直接生效，于是"应用 / 取消"无从谈起，
`apply` 按钮被暂时摘掉。要么给 `RibbonCustomizeWidget` 加一层草稿（做大），
要么把"定制的语义就是即时生效、没有撤销"写成明确设计并撤掉那两处 `TODO`（做小）。
**按 K21 的第 ③ 条办**——先判断哪一种是这个控件真正要的行为，再决定。

### B2 · Linux 无边框（K23 已定，结论与初版建议相反）

`FramelessHelper` 在 Linux 上是"实验性路径"，这一点没变；变的只是**要不要因为它是实验性的
就把默认关掉**。初版建议是关（Linux 默认走系统边框），定案是**不关**，理由三条：

1. **触发条件很窄**：Unity 的 `normalGeometry()` 不对、GNOME 的闪烁与拖不动，两处都是
   "**最大化之后再去拖**" 这一个动作；普通拖动、缩放、关闭都不受影响；
2. **翻默认换来的是更宽的问题**：`RibbonBar` 并不会因为 `isFrameless()` 为假就不画自己那条标题行
   （`setFrameless(false)` 只是拆掉 helper 并清掉窗口标志，见 `ribbonwindow.cpp:83-85`），
   于是窗口上会同时出现**系统标题栏**和 **ribbon 标题行**——所有 Linux 应用的外观都变差；
3. **代价不对称**：真正的修法是"最大化 → 拖拽还原"这条路径本身（平台相关的窗口管理代码），
   而翻默认只需要改一行（`RibbonWindowPrivate` 的 `m_frameless(true)`，`ribbonwindow.cpp:30`）
   ——既然只值一行，就留给作者将来按真实需要翻，不在这版替他决定观感。

### C2 · K8 复核（K22）

复核的结论是**维持不设阈值**，但把两处"报告"从"报了了事"改成"报得准"：

| 落点 | 改动 | 为什么是"更便宜的门禁"的替代品 |
| :--- | :--- | :--- |
| 覆盖率 | `lcov --list` 的结果同时写进**作业摘要页**（原先只有 artifact） | 设阈值需要先有可比的数字；artifact 要下载，摘要不用。数字随手可见，"逐版本对比"才有人做 |
| clang-tidy | 范围从**改动的文件**收严到**改动的行**（`scripts/tidy_line_filter.py` 由 diff hunk 生成 `-line-filter`） | 门禁要门的是"本次引入"，按文件会把同文件的历史告警算到本次头上。**过滤后仍不门禁**：先把测量做准，阈值留到有数字可谈的版本 |

**实测（本机 clang-tidy 21.1.2 + Qt 6.8.3 + MinGW，只跑 `bugprone-*`/`performance-*`）**：
`src/libs` 现有 **183** 条告警（另有 25 条 `clang-diagnostic-error`，全部是本机未编译时的
平台假象——比如把 `_mac.cpp` 拿到 Windows 上分析）。按 check 排前几位：

| check | 条数 |
| :--- | ---: |
| `bugprone-narrowing-conversions` | 81 |
| `performance-no-int-to-ptr` | 21 |
| `performance-for-range-copy` | 15 |
| `bugprone-macro-parentheses` | 15 |
| `bugprone-easily-swappable-parameters` | 13 |

**这个数字本身就是"不能按文件门禁"的证据**：随便改一个 `.cpp` 都可能被同文件里的历史告警拦住。
按行筛之后，"本次引入"才是一个能用来谈阈值的量。

**机制验证**（`-line-filter` 能不能真的过滤，本机实测）：

| 动作 | 结果 |
| :--- | :--- |
| `windowcontext_win.cpp` 不过滤 | 26 条 |
| 同一文件，过滤到 diff 给出的改动行 `[[80,88]]` | **0 条**（存量告警确实都不在改动行上） |
| 同一文件，手工过滤到 `[[530,535]]` | **1 条**——正好是 533 行那条 `performance-no-int-to-ptr` |
| 同一文件，手工过滤到 `[[1,100]]` | 0 条 |

⚠️ **格式细节**：`-line-filter` 的 `name` 匹配的是 **basename**（文档示例就是 `"file1.cpp"`，
不是路径）。写到一半踩过：用全路径 `D:/.../qxsettings.cpp` 会**一条都不匹配**——因为列表存在时
clang-tidy 只报列表内的文件，不匹配等于全过滤掉，看起来像"告警消失了"，很能骗人。
`scripts/tidy_line_filter.py` 因此按 basename 聚合（本树 `src/libs` 下 93 个 basename 无重名；
真有重名时区间会合并，只会**放宽**过滤而不会漏报）。

⚠️ **头文件改动不加过滤**：头能波到每个翻译单元，而被它引起的告警会落在某个 `.cpp` 的**未改动行**上，
按行过滤恰好会把这份波漏掉。所以那条分支仍是"整棵树、不设过滤"（与改动前一致），
代价是噪声，收益是不漏。

⚠️ **跳过空过滤**：改动没给 `src/libs` 添任何一行时过滤表是 `[]`，而 clang-tidy 把空表读作
"全部过滤掉"——即跑几分钟报零条。所以这种情况直接跳过分析并在摘要里说明原因。

⚠️ **过滤被拒时必须吵**：万一 CI 上的 clang-tidy 不认这个选项，每个文件都会"没有发现"，
而"0 findings"**正好是一次干净运行的样子**——两者在摘要里完全一样，看起来都是好消息。
所以作业收尾时会在日志里找 `unknown argument.*line-filter`，命中就发 `::error::`
（步骤变红，但因为 `continue-on-error` 不阻塞流水线）。这条判断本身也有桩测试覆盖。

### A1 · `DockTabBar` 的"滚动到可见"（2026-10-11）

**改动**：`src/libs/qxdock/docktabbar.cpp`——`updateTabs()` 不再在循环里为当前标签排定时器，
改为在出口调 `DockTabBarPrivate::scrollTabIntoView()`；新增该函数（80 行注释 + 实现）与两个成员
（`QPointer<DockTab> m_pendingScrollTab`、`bool m_scrollPending`）。

**核心是那条注释掉的 lambda 为什么会杀进程**，而不是"换个写法试试"。实测复现（把旧代码原样放回去）：

```
1/1 Test #7: tst_qxdock .......***Exception: SegFault  0.46 sec
```

**SegFault**——即 `[&, tab]` 里按引用捕获的局部 `q`：定时器回调跑到时 `updateTabs()` 的栈帧已失效，
lambda 体读到的是一格被复用的栈内存。这条已被写进 `docktabbar.cpp` 的函数注释（英文），
因为它正是"为什么这段代码曾经必须注释掉"的答案。

**三道保险**（对应 §四 A1 列的三层风险）：

| 风险 | 处置 |
| :--- | :--- |
| 局部 `q` 被按引用捕获 → 悬垂栈引用 | `q` **按值**捕获；且 `q` 作为定时器的 context object，宿主先死则回调不投递 |
| 标签在延迟回调前被销毁（`DockTab` 是 `DockWidget` 的子对象） | `QPointer<DockTab>` 守卫，判空后再用 |
| 一次 `updateTabs()` 排一次 → 一串索引变化堆出一串布局 | `m_scrollPending` 去重：pending 期间只更新目标，不新增定时器 |

**回归测试**：新增 `tests/qxdock/auto/tst_docktabbar.cpp`（被 `tests/CMakeLists.txt` 的
`file(GLOB ... auto/tst_*.cpp)` 自动收进 `tst_qxdock`），两个用例：

- `scrollsCurrentTabIntoView()`——**功能**：把标签最小宽度设成 200 逼出溢出（否则"看不见"取决于
  字体，测试会时灵时不灵），断言切到最后一个标签后它**完整落在 viewport 内**，再切回第 0 个后
  `x == 0`；

  紧接着 `deleteDockWidget()`（标签随之销毁），再让事件循环跑完：**不得崩溃**，
  且 `count()` 减 1、`currentTab()` 非空且不是被删的那个。

**验证**：`tst_qxdock` 通过；qt6 全量构建 0 warning、`ctest` **12/12**；`clang-format 21.1.8 --style=file` 干净。

#### 顺带修掉：新增源文件后 AUTOMOC 不重新扫描（`build:` 那笔）

第一次给 qxdock 加测试文件时踩到的：`#include "tst_docktabbar.moc"` 报
`No such file or directory`。查下去是**两个独立的问题叠在一起**，都修了：

- **列表进不去构建系统**：`file(GLOB ...)` 的结果是 configure 时定下的，新文件不会自己进去。
  修法：三处收集源文件的 glob 加 `CONFIGURE_DEPENDS`（`tests/CMakeLists.txt` 的 8 个、
  `src/libs/qxdock/CMakeLists.txt` 的 3 个、`examples/CMakeLists.txt` 的 1 个）。
  ⚠️ 位置有讲究：必须写成 `file(GLOB <变量> CONFIGURE_DEPENDS <表达式>)`，
  **写在表达式后面** CMake 4 会直接报错（"requires a glob expression after CONFIGURE_DEPENDS"）；
  而**写在最前面**更糟——它不报错，只是把 `CONFIGURE_DEPENDS` 当成输出变量、把变量名当成 glob，
  于是 glob 结果为空（本次实测：`examples` 里 6 个样例的 `mainwindow.cpp` 凭空消失，
  链接报 `undefined reference to MainWindow::MainWindow`，和"源文件没写"长得一模一样）。
  判断是否真的生效有一招：configure 后看 `<build>/CMakeFiles/VerifyGlobs.cmake` 在不在。
- **AUTOMOC 不重扫**：AUTOMOC 把上次扫过的文件清单写进**它自己生成的依赖文件**，
  而 `<target>_autogen/timestamp` 这条规则依赖的是那个文件、不是目标的源文件列表。
  于是新加的文件永远进不了扫描范围，moc 不跑，编译就卡在缺 `.moc` 上。
  修法：新增 `qtc_autogen_rescan()`（`cmake/QtCanpoolAPI.cmake`），在
  `add_qtc_library` / `add_qtc_plugin` / `add_qtc_executable` / `add_qtc_test` 四个入口各调一次，
  configure 时删掉 `<target>_autogen/timestamp`，逼 AUTOMOC 重扫一次。
  代价是每次 configure 多一次扫描（moc 本身仍只重跑变化了的文件）；路径是 CMake 的布局不是我们的，
  所以用 `EXISTS` 探一下再删，将来 CMake 挪了位置只会退化成"没帮上忙"，不会把能跑的构建弄坏。

**验证**：新增一个 `tst_*.cpp` 后**不手动重跑 configure**、直接 `cmake --build` ——
`configuring done` → `Automatic MOC and UIC for target tst_qxdock` → 编译链接通过；
删掉该文件后再构建同样干净。qt6 与 qt5 全量构建各 0 warning、`ctest` 各 **12/12**、clang-format 绿。

### B1 · `FramelessHelper` 的 DPI（2026-10-11）

`FramelessWidgetDataNativeWin` 用一个两格的 DPI 对（`m_dpi[0]` 旧 / `m_dpi[1]` 新）当"DPI 变过没有？"
的旗标，而两格都被**硬编码成 96**。根因不是"数字不对"，是**旗标的语义被破坏了**：

- 正常的初始状态是"两格相等 ⇒ 没变过"，此时随后的 `WM_SIZE` / `WM_MOVE` 会走 `setFrameChanged()`
  （`SetWindowPos(..., SWP_FRAMECHANGED)`），把丢掉的非客户区补回来；
- 在缩放屏幕上，窗口刚创建时真实 DPI 就不是 96。第一个 `WM_DPICHANGED` 把两格错开，
  而**两格不等正是跳过 `setFrameChanged()` 的条件**——于是"刚发生 DPI 变化"这个最需要补帧的时刻，
  补帧被自己的旗标按住了。上层表现就是注释里写的"窗口变小、非客户区没了"。

**修法**：从窗口拿真实值——`GetDpiForWindow()`（Windows 10 1607+，**运行时解析**，
这样既不用新 SDK 也能在老 Windows 上加载）；拿不到就退到桌面 DC 的 `GetDeviceCaps(LOGPIXELSY)`
（那是系统 DPI，即主屏的，多屏不同缩放时不准，但比常量强得多）；再不行才回落到 96。

**没有测试**：这需要**真窗口 + 两块不同缩放的屏幕之间拖动**。DPI 对只决定"要不要补帧"，
离屏测试能断言的只是这个判断的算术，不是它保护的行为——写一个"测旗标算术"的测试只会让人误以为覆盖到了。
