## 一、背景与现状（2026-10-11 勘察）

### 1.1 4.0 刚交付的是什么

4.0 换掉的是**骨架**：全树 qmake 归零（88 个文件）→ 构建方式只剩 CMake；新增 `qxplugin`（契约 /
发现 / 依赖 / 隔离 / 对象池）→ 应用可以按元数据长出模块；`src/modules` + `IdeShellDemo` 证明这条路
走得通；行尾归一为 LF（K20）。换句话说，4.0 动的是**别人怎么用它**。

### 1.2 为什么下一版不接着做插件

4.0 已经把插件的边界写进了非目标，而且是**刻意**的：

> 不做热插拔 / 运行时安装插件（启用或停用后重启生效，Qt Creator 亦如此）；不做插件市场；
> 不做脚本化插件；不做进程隔离；不做异步生命周期。

这些不是"没来得及"，是"想清楚了不做"。继续在插件线上加码只会把 4.0 刚划下的边界又抹糊。
真正没被照顾到的是另一半：**用户每天盯着的那个窗口**。

### 1.3 勘察：源码里自己写下的欠账

`src/libs/**` 里带 `TODO` / `FIXME` / `XXX` 的注释共 **25 条**，分布如下：

| 库 | 条数 | 说明 |
| :--- | :--- | :--- |
| `qxribbon` | 11 | 无边框（DPI、Linux 拖拽）、`RibbonBar` 布局请求、定制对话框的"应用/缓冲" |
| `qxwindow` | 9 | **几乎全是继承来的**：`windowcontext_win.cpp` / `windowsystem_p.h` 源自 Qt 自己的 `qwindowswindow.cpp`，连标记写法（`### FIXME FIXME FIXME`、`### TODO: How to handle touch events?`）都一样 |
| `qxdock` | 4 | 标签栏的"滚动到可见"、`toggleView()` 的显示顺序、手柄父子关系、分割条性能 |

两个值得记下来的观察：

1. **4.0 新写的代码一条都没有**（`qxplugin` / `src/modules` / `QxPluginManagerDialog` / `IdeShellDemo`
   全部 0 条）。欠账全在**老库**里——这不是巧合，是因为老库是"用出来"的，新库是"设计出来"的。
2. `qxwindow` 那 9 条里，本仓库自己写下的只有 **1 条**：`windowcontext_win.cpp:80` 要求把 Qt 6.5.3
   纳入实测（附两个 Gitee issue 号 `#I8SPBC` / `#I8SPC8`）——那是**测试**欠账，不是代码欠账。
   其余 8 条（含 `### FIXME FIXME FIXME` 那三行，是同一个注释块）跟着 Qt 一起继承，本轮**不认领**
   （认领只会让"清账"这件事变成假动作）。

因此 **4.1 要处置的是 16 条**：`qxribbon` 11 + `qxdock` 4 + `qxapp` 1。

### 1.4 其中哪些是真缺陷，哪些只是"想更好"

不需要读代码就能分出来的，至少有这三条：

- **`qxdock/docktabbar.cpp:72`** —— `DockTabBar` 把"把当前标签滚进可见区域"整段**注释掉了**，
  原因是它"会让程序意外结束"（issue #520 的同款写法，那段 `QTimer::singleShot(0, q, [&, tab]{...})`

## 二、目标与非目标

### 目标

1. **看得见的部分不再有"已知但不管"的毛病**：`qxdock` / `qxribbon` / `qxapp` 里自己写下的
   16 条欠账，**每一条都有结论**；
2. 结论是"修好了"的那些，**带回归测试**，且在 CI 门禁内跑；
3. 结论是"改不了/不值得改"的那些，**变成文档里的已知限制**，而不是继续躺在注释里；
4. 顺带把 K8（覆盖率是否设阈值）复核掉——它从 3.1 挂到现在，已经过了三个版本。

### 非目标

- **不加控件、不加库**（延续 K10：能力项只收"真实应用反复手写"的件）；
- **不接着扩插件体系**：4.0 的非目标一条不改（热插拔、市场、脚本、进程隔离、异步生命周期）；
- **不认领从 Qt 继承来的注释**（`qxwindow` 那 8 条）——只把"我们自己的那 1 条"处置掉；
- **不为消灭注释而消灭**：修不了就写清楚它为什么修不了，不假装修好；
- **不做 QML/Quick**（延续 3.0）。

### A1 · `DockTabBar` 的"滚动到可见"

现状（`docktabbar.cpp:72`）：那段"同步算矩形有时会失败，所以用 `QTimer::singleShot` 挪到事件循环里"
的写法**被整段注释掉**，理由是"会让程序意外结束"。症状与 `issue #520` 同源：当前标签被切到
滚动区外时不会自动滚回来，用户看不到自己点的那个标签。

要弄清的是**为什么它会结束进程**，而不是再把它注释一次：

- `QTimer::singleShot(0, q, [&, tab] { q->ensureWidgetVisible(tab); })` 里 `[&]` 把**局部变量**
  `q`（`Q_Q(DockTabBar)` 展开出来的 `DockTabBar *const q`）**按引用**捕获了。定时器是"0 毫秒"，
  但**不是在调用点执行**——等事件循环跑到它时，`updateTabs()` 的栈帧早就没了，
  lambda 体里的 `q` 读的是一格已被复用的栈内存。**这就是进程意外结束的直接原因**
  （已实测复现，见执行记录）。
- 次要的一层：`tab` 是按值捕获的裸指针，而标签（以及它的 `DockWidget`）可能在事件循环跑到之前
  就被销毁——`DockTab` 是 `DockWidget` 的子对象，`deleteDockWidget()` 会连它一起删。
- 第三层：`ensureWidgetVisible()` 会触发布局，而 `updateTabs()` 本身常常**就在布局过程中被调用**，
  从事件循环里再回去改布局是重入。

**实际落法**：把这段从循环里提出来，落到 `DockTabBarPrivate::scrollTabIntoView(DockTab*)`，
一次 `updateTabs()` 只可能排一次（`m_scrollPending`）；延迟调用同时上两道保险——
`QPointer<DockTab>` 守目标对象，`q` **按值**捕获并作为定时器的 context object 守调用方。
细节见 `4.1-TASKS.md` 执行记录 A1 与 `docktabbar.cpp` 的函数注释。

### B4 · 定制对话框的"无缓冲 / 缺应用按钮"

`ribboncustomizedialog.cpp:91/93` 与 `ribboncustomizewidget.cpp:1123/1169/1172` 五条其实是
**同一个**毛病：定制数据没有"草稿态"，改了就直接生效，于是"应用 / 取消"无从谈起，
`apply` 按钮被暂时摘掉。要么给 `RibbonCustomizeWidget` 加一层草稿（做大），
要么把"定制的语义就是即时生效、没有撤销"写成明确设计并撤掉那两处 `TODO`（做小）。
**按 K21 的第 ③ 条办**——先判断哪一种是这个控件真正要的行为，再决定。

### A1 · `DockTabBar` 的"滚动到可见"（2026-10-11）

**改动**：`src/libs/qxdock/docktabbar.cpp`——`updateTabs()` 不再在循环里为当前标签排定时器，
改为在出口调 `DockTabBarPrivate::scrollTabIntoView()`；新增该函数（80 行注释 + 实现）与两个成员
（`QPointer<DockTab> m_pendingScrollTab`、`bool m_scrollPending`）。

**核心是那条注释掉的 lambda 为什么会杀进程**，而不是"换个写法试试"。实测复现（把旧代码原样放回去）：

```
1/1 Test #7: tst_qxdock .......***Exception: SegFault  0.46 sec
```

**SegFault**——即 `[&, tab]` 里按引用捕获的局部 `q`：定时器回调跑到时 `updateTabs()` 的栈帧已失效，
lambda 体读到的是一格被复用的栈内存。这条已被写进 `docktabbar.cpp` 的函数注释（英文），
因为它正是"为什么这段代码曾经必须注释掉"的答案。

**三道保险**（对应 §四 A1 列的三层风险）：

| 风险 | 处置 |
| :--- | :--- |
| 局部 `q` 被按引用捕获 → 悬垂栈引用 | `q` **按值**捕获；且 `q` 作为定时器的 context object，宿主先死则回调不投递 |
| 标签在延迟回调前被销毁（`DockTab` 是 `DockWidget` 的子对象） | `QPointer<DockTab>` 守卫，判空后再用 |
| 一次 `updateTabs()` 排一次 → 一串索引变化堆出一串布局 | `m_scrollPending` 去重：pending 期间只更新目标，不新增定时器 |

**回归测试**：新增 `tests/qxdock/auto/tst_docktabbar.cpp`（被 `tests/CMakeLists.txt` 的
`file(GLOB ... auto/tst_*.cpp)` 自动收进 `tst_qxdock`），两个用例：

- `scrollsCurrentTabIntoView()`——**功能**：把标签最小宽度设成 200 逼出溢出（否则"看不见"取决于
  字体，测试会时灵时不灵），断言切到最后一个标签后它**完整落在 viewport 内**，再切回第 0 个后
  `x == 0`；
- `scrollSurvivesTabDeletion()`——**回归**：`setCurrentIndex(最后)` 排下延迟滚动，
  紧接着 `deleteDockWidget()`（标签随之销毁），再让事件循环跑完：**不得崩溃**，
  且 `count()` 减 1、`currentTab()` 非空且不是被删的那个。

**验证**：`tst_qxdock` 通过；qt6 全量构建 0 warning、`ctest` **12/12**；`clang-format 21.1.8 --style=file` 干净。

#### 顺带记一个测试基础设施的坑：新增测试文件后 AUTOMOC 不会重新扫描

`file(GLOB QXDOCK_TEST_SOURCES ...)`（无 `CONFIGURE_DEPENDS`）本身可以靠手动重跑 `cmake --preset`
补上，但**重跑之后 AUTOMOC 依然不认新文件**：`<target>_autogen/timestamp` 的 make 依赖只有
`moc.exe` / `uic.exe` / `compiler_depend.ts`，**不含 `AutogenInfo.json` 与源文件清单**，
所以源列表变了它也不重跑，`#include "xxx.moc"` 直接报 `No such file or directory`。
本轮的绕法是 `rm build/qt6/tests/tst_qxdock_autogen/timestamp` 后再构建。

**这不该是"记在脑子里的步骤"**，两条低成本修法记在这里，随 C1 一起办：

1. 给 `tests/CMakeLists.txt` 的 `file(GLOB ...)` 加 `CONFIGURE_DEPENDS`——至少省掉手动重跑 configure；
2. 若 1 不足以带动 AUTOMOC，就在 `add_qtc_test()` 里给 autogen 目标补一条对源文件清单的依赖
   （`set_property(TARGET <t>_autogen APPEND PROPERTY OBJECT_DEPENDS ...)` 之类的写法需实测）。

在此之前，新增/删除测试文件后**先删一次 autogen 时间戳**，否则报错信息（缺 `.moc`）会把人引到
"是不是没写 `Q_OBJECT`"的错误方向上去。
