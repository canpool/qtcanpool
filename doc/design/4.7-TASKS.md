## 一、版本定位与约束

### 1.1 一句话

**4.7 是第一个把「控件观感」当交付物的版本**：补齐令牌轴，新增控件基座库与 `qxfluent` /
`qxmaterial` 两个控件库，让 qtcanpool 从「Ribbon + Dock + Window 三类 chrome」变成
「+ 第四个选择：控件集」。**同时**，4.6 证明测试没能覆盖住库的行为场景——`qxribbon` /
`qxdock` 要做深做全（重构、重写、测试全面覆盖），这条与控件集同为 4.7 的交付（I 组，
作者 2026-10-21 定向）。

**新库数量不以「两个」为界**：作者的授权是「需要就加」，本计划只把**此刻看得见需要的**
（基座 + 两个控件库）立进来；执行中若冒出第四个（例如动效基建长到值得独立），照常勘察、
照常立项，不必回到这一版重新授权。

### 1.5 与 ribbon 的关系：三个选项，不是一套的三种皮肤（作者 2026-10-21 定）

fluent / material / ribbon 是**三个并列的选项**：命令密集的工具类应用选 ribbon，
设置 / 表单 / 现代工具类应用选 fluent 或 material。互补的含义是**用户可三选一**，
不是「ribbon 有什么，两库就避开什么」：

- **不因避让而砍件**：ribbon 有命令条，fluent 的 `CommandBar` **照做**——二者表达的不是
  同一件事（Ribbon 是按页组织的功能清单，CommandBar 是随上下文浮动的命令集合），
  选了 fluent 的应用没有 ribbon 可用，砍掉 CommandBar 等于砍掉它唯一的命令入口。
  同理 material 的 app bar / rail 也照做。
- **自成体系**：每个控件库都要能**独立撑起一个应用**——骨架件（导航、命令条、内容容器）、
  输入件、反馈件三层都要有。第一批清单按这个原则补齐了骨架件（见 §七.3），
  更远处的件在台账里滚动追加。
- **共用才下沉**：只有当两个库对「同一件事」的答案**真的是同一个**时（几何计算、状态层
  叠色、焦点环、动效驱动、无障碍骨架），才沉到公共依赖库 `qxcontrols`；答案不同的
  （Switch 的两副形态、Card 的三档 elevated）各自实现。**判据是「答案是否相同」，
  不是「名字是否相同」**——共享同名不同形的控件，正是「两套观感差异落到色板上」的
  最短路径。

### 1.2 与前三个版本的分野

| 版本 | 性质 | 对 API 的态度 |
| :--- | :--- | :--- |
| 4.4 | 不破坏 API 的内部重构 | 不改签名 |
| 4.5 | 功能升级（大破一轮：主题 id、`qxtheme` 接口、ribbon 样式名、`QxNavBar`） | **可破坏** |
| 4.6 | 体验与基建收口，**只做加法** | 仅 `RibbonGalleryGroup` 一处换基类 |
| **4.7** | **控件观感 + 新库** | **作者授权可破坏**：重构、重写、新增功能、改签名都允许（K26 只要求破坏进 minor，4.7 是 minor） |

⚠️ **可破坏 ≠ 可断裂（作者 2026-10-21 补）**：4.7 的每一处破坏都要**留兼容通道**，
判据是「应用按迁移指南改完后行为等价，且没改到的代码**仍然编译、仍然运行**」：

- **删除 / 改签名**：先走弃用——`QX_<LIB>_DEPRECATED_SINCE` 宏家族就是为此预留的闸门
  （4.3 A8 修成可用 + 回归，永不删除），声明期一版以上再删；
- **改名 / 换基类**：能留别名就留别名（先例：4.5 的 `RibbonStyle` 新旧值并到了映射）；
  唯一允许不留别名的情形是「别名本身就是混淆」（4.5 `QxNavBar` → `QxNavTabBar` 的先例），
  走这条要单独说明理由；
- **行为变更**：能加开关就加开关、默认保持旧值（4.6 `setBorderOwnsCursor()` 的先例），
  默认值翻转属于破坏，同样进弃用流程；
- 申报义务不变：每一处破坏同笔进 `doc/pages/migration.md` §4.7。4.5 的教训是破坏面写漏了
  两处事后补记——4.7 的破坏比 4.5 多得多（见 §六），靠记忆补不住。

### 1.3 硬约束（不可协商）

1. **双腿**：Qt 5.15.2 + Qt 6.8.1 各 100% 构建 + ctest（`QT_QPA_PLATFORM=offscreen`）。
   新库必须在 Qt 5 上也能编译、也能跑测试——这是 4.7 最现实的成本项，理由见 §七.6。
2. **Qt 6 独有 API 必须先问**：`QPalette::Accent` 是 6.6+、`QStyleHints::setColorScheme()` 是 6.8+、
   `QDragEnterEvent` 的 `QPointF` 构造器是 6.12+。新库对这三类一律走 `qtcompat` 或版本分叉，
   不允许出现「qt6 编得过、qt5 编不过」的写法。
3. **源文件**：不带 BOM 的 UTF-8、行尾 LF、SPDX `MulanPSL-2.0` 写在文件最顶部。
4. **图标**：只用单色 + alpha 重染（`qxtheme` 的四个入口），新库的每一枚图标进
   `scripts/icons-policy.txt`，由 `scripts/check-icons.py` 门禁。
5. **主题族 id 按形态命名**（硬规则）：`fluent` / `material` 是**库名、命名空间与类前缀**
   （`FluentSwitch` / `MaterialChip`，§七.9 已定），可以直呼其名（它们指代要实现的是
   哪一套设计语言）；**主题族 id 仍然只能用形态或几何词**——见 §七.4 的候选。
6. **不引入第三方控件库源码**：最成熟的 Widgets Fluent 实现是 GPL + 商业双授权，与
   MulanPSL-2.0 不兼容。只能读规范与公开文档，不能读代码搬代码。
7. **敏感信息**：按 `contributing.md` §11 的既有约定执行，本文件不展开。

### 1.4 判据（为什么必须先做令牌轴）

4.5 的核心教训：四套亮和四套暗「风格完全一样」，根因是**只有色板不同、结构没差异**；
后来靠「四轴判据」（条与页的明暗 / 选中态 / 分隔与盒子 / 文件按钮）才把家族拉开。

同理，**4.7 的成败判据不是「有没有 fluent 和 material 两个库」，而是「两套观感的差异落在
结构上而不是色板上」**。所以 A 组（令牌轴）是 C/D 组的**前置**，不是可并行的兄弟：

- 形状（圆角阶梯 vs 4/8 两档）
- 状态层（ripple + overlay vs reveal + 描边）
- 阴影（五级 elevation vs 描边 + 窗口材质）
- 动效曲线（emphasized vs fast-out-slow-in）

这四条每一条都要有**名字可取**，否则两个库会写成「同一套绘制代码，换个颜色常量」。

## 二、任务分解

### A 组 · 令牌轴（`qxtheme` + `tools/themes/`，4.7 的前置）

现状量化（`WIDGETUI-STUDY.md` §四的实测）：22 个令牌**全部是颜色**，五条轴全缺。
其中 shape 硬编码 33 处 `border-radius`（`0`×17 / `2`×10 / `3`×4 / `6`×2），
type 几乎空白（模板零条 `font-weight` / `font-family`，`font-size` 只有 3 条且**只在暗色骨架**——
亮暗两侧不对称本身就是缺陷），motion 全库只有 2 个文件用动画。

- **A1 · shape 轴**：引入 `corner-{none,sm,md,lg,pill}` 五档令牌，33 处硬编码收敛到令牌；
  两套骨架 × 五族重新生成 10 张表。判据：`grep 'border-radius: [0-9]'` 在生成表里零命中。
  **✅ 已落地（2026-10-21）**：勘察修订一处——硬编码实为 **24 处**（0px×14 / 2px×6 / 3px×4，
  勘察的 33 处含当日已改的量）。五档取值 `0/2/3/6/9999px`（前四档即现状值，lg/pill 暂无
  用户、为后续预留）；判据由生成器**新门禁**执行（raw 表里 `border-radius: [0-9]` 即拒写，
  比 grep 更前置）。`base.css` 的 1 处走令牌后，运行时 `render()` 增加 `kGeometryTokens`
  解析（与生成器 SHAPE 表互为对照、须同步）；**10 张表重生成后字节一致**（`git diff` 为空），
  即「未改令牌的应用观感不变」成立。
- **A2 · type 轴（已完成，2026-10-21）**：`type-{caption,subtitle,body,title}` 四档令牌
  （10/13/15/18px，前三档即暗侧现状：密码字符 / 日历栅格 / 组合框弹层条目，title 预留），
  生成器加 `TYPE` 表 + `FONT_SIZE` 门禁（raw 表出现数字字号拒写）。
  **拉平的实际含义（勘察后修正）**：亮暗骨架的选择器集本就不同——亮表只描述 ribbon、
  暗表额外重绘标准控件（docstring 写明的设计，非缺陷）——所以拉平＝字阶的值只定义一次、
  取暗侧现状，两骨架引用同一份档位；给亮表补规则反而会改亮色观感。判据达成：
  10 张表重生成字节一致（`git diff` 空）；`base.css` 无字号规则，运行时无需变化。
- **A3 · spacing 轴（已完成，2026-10-21）**：`space-{xs,sm,md,lg}` 四档（4/8/12/16px，全在
  4px 网格上，xs/lg 预留），生成器加 `SPACING` 表 + `PAD` 门禁（**只对 chrome 文件**——
  骨架与 menu.css 的数字 padding 目前合法，门禁跑到合并表会替别的文件背锅）。五个 chrome
  文件的 tab padding 上令牌：flat/slate 8→`sm`、soft 12→`md`（字节不变）；classic/accent
  的 10px 不在网格上，**吸附** classic→`sm`（8px，本就更密集的 boxy 风格）、accent→`md`
  （12px，accent 色块需要呼吸感）——§六.3「细微但不为零」的一次兑现，其余六张表字节一致。
  density 两档（comfortable / compact）：QSS 表是静态的，只说 comfortable；compact 是
  控件库的运行时开关（B 组），沿用同一套档位名而非另起一套。
- **A4 · elevation 轴（唯一需要新机制的一条）**：QSS 没有 `box-shadow`，而
  `QGraphicsDropShadowEffect` 是**每实例一个 effect**（开销大、且与 `QWidget::grab()` 有交互问题）。
  建议机制：`QxShadowPainter`——把阴影参数预渲染成一张小图，按 9-slice 拉伸，按参数缓存；
  QSS 侧只能用「边框 + 两层背景」伪造一档，其余靠自绘控件自己画。
  **令牌**（阴影有几级、每级多大）归 A 组 / `qxtheme`，**画法与缓存**归 B 组 /
  `qxcontrols`（B2）——机制落在哪已随基座单独成库定了，剩下的只是 A4 把「级数与尺寸」
  这几个值定下来。
- **A5 · motion 轴**：`QxMotion`——时长与曲线令牌 + 一个全局 `reduceMotion` 开关
  （QWidgets 没有读系统「减少动效」偏好的 API，只能由应用显式设；`QxThemeManager` 记住它）。
  令牌名如 `motion-fast` / `motion-emphasized`，值成对（时长 + `QEasingCurve` 类型）。
- **A6 · 令牌进注册结构**：`QxThemeInfo` 增加度量/字阶/动效字段。**这是一处破坏**（结构体变了），
  4.7 允许，进 `migration.md`。

判据（A 组整体）：**每轴一个像素探针** + 十张表逐表同色 / 同几何比对。A 组不新增控件、不新增库。

### B 组 · 公共依赖库（**作者已定：单独成库**，不进 `qxtheme`）

两个控件库**自成体系**（§1.5），但它们对一部分事情的答案确实是同一个：状态层叠色、焦点环、
圆角裁剪、命中区域、动效驱动、`QAccessible` 骨架。这些**共用的内容**沉到公共依赖库，
不在 `qxfluent` 和 `qxmaterial` 里各写一份，也**不进 `qxtheme`**
（作者 2026-10-21 裁定：`qxtheme` 是主题引擎，塞进控件基座会让它的概念失焦）——**单独成库**。

⚠️ 下沉的判据是 §1.5 的「答案是否相同」，不是「名字是否相同」：`qxcontrols` 装的是
**机制**（怎么画状态层、怎么算命中区域），不是**形态**（Switch 长什么样）——形态永远
属于各自的设计语言库。

- **B1 · 库骨架**：**已定（作者 2026-10-21 采纳 §七.9）**：库名 **`qxcontrols`**
  （命名空间 `QxControls`，`QX_CONTROLS_EXPORT`）。论证与被排除的候选见 §七.9。
- **B2 · 基类与原语**：`QxControl`（基类：令牌读取、状态机、焦点环、命中区域）、
  `QxStateLayer`（状态层叠色）、`QxRingPainter`（焦点环）、`QxShadowPainter`（A4 的阴影机制
  落在这里，不在 `qxtheme`——阴影是绘制，不是令牌）。
- **B3 · 依赖方向**：`qxcontrols` 依赖 `qxtheme`（读令牌与调色板），`qxfluent` / `qxmaterial`
  依赖 `qxcontrols`。单向，禁止反向——`qxtheme` 不认识任何控件，这条边界是「引擎 / 底座 /
  控件集」三层能站住的前提。
- **B4 · 无障碍骨架**：`QAccessible*` 接口在基类做一次，控件只填 role 与 state
  （先例：4.5/4.6 给 painted 容器补的 Pane / Grouping 工厂）。

与 A 组的关系：A 组产出**令牌**（名字与值），B 组产出**读令牌的绘制原语**。A 在 `qxtheme`
与 `tools/themes/`，B 在新库——两层分开，正因如此基座进不进 `qxtheme` 才是一个真问题，
而作者的答案是分开。

### C 组 · `qxfluent`（新库，0.1.0）

**目标**：WinUI 3 / Fluent 2 的 Widgets 版。**不是**把 Qt 控件换个颜色，而是做 Qt 缺的那些件。

- **C1 · 库骨架**：`qxfluent_global.h`（`QX_FLUENT_EXPORT`、`QX_FLUENT_NAMESPACE QxFluent`）、
  `add_qtc_library`、命名空间 `QxFluent`；依赖 `qxcontrols`（B 组）。
  类名与文件名照 §七.9：类 `Fluent<Name>`，文件 `fluent<name>.{h,cpp}`（如 `FluentSwitch`
  ↔ `fluentswitch.h`），私有头 `fluent<name>_p.h`。
- **C2 · 设计令牌映射**：Fluent 的 Type Ramp、4/8 圆角、`ControlFill` 状态层映射到 A 组的令牌名。
- **C3 · 窗口材质接线**：Mica / Acrylic / Mica Alt 在 `qxwindow` **已有实现**（`windowkit_win_p.h`
  的 `_DWMSBT_*` 三档）⇒ `QxFluent::applyWindowMaterial(window, Material)` 只是包一层，
  这是本仓库在这一方向上少见的领先项，**不要重写**。
- **C4 · 第一批控件（11 项）**：`Switch`、`Slider`、`Badge`、`Card`、`ProgressRing`、
  `CommandBar`、`InfoBar`、`BreadcrumbBar`、`Expander`、`Rating`、`TeachingTip`。
  - `CommandBar` 是骨架件——选了 fluent 的应用没有 ribbon 可用，它是唯一的命令入口，
    **不能因 ribbon 存在而延后**（§1.5）。
  - `Slider` / `Badge` 与 material 侧同名不同形，各自实现（§七.3）。`Slider` 补的是
    「自成体系」的**输入层**——此前输入件只有 `Switch` 一个，撑不起一个控件集。
  - `Rating` 是勘察清单（`WIDGETUI-STUDY.md` §八第 8 项）里在两库分配时**漏掉又补回**的件：
    Qt 完全没有评级控件，半星与键盘导航都无处可放。
  - `SegmentedButton`（SelectorBar）**只在 `qxmaterial` 做**（七.3 已定）——同一个名字
    两库形态不同，两库之间最不该共享的恰恰是「同一名字、不同形态」的控件。
- **C5 · reveal hover**：指针位置驱动的径向高亮（Fluent 的标志性观感，也是「结构差异」的一条）。
- **C6 · 滚动追加池（`stretch`，4.7 内按此序补，前提是 Switch 样板链路已通）**：
  1. 骨架层：`NavigationView`（Fluent 的导航骨架）、`TabView`——它们属于「自成体系」
     要补的骨架层（§1.5），优先级最高。
  2. 输入层：`NumberBox`（带校验与步进器的数值输入，QSpinBox 缺的形态）。
  3. 命令层：`DropDownButton` / `ToggleSplitButton`（`CommandBar` 的两个组成件，
     先在 `CommandBar` 内部实现，值得独立导出时再拆出）。
  4. 反馈层：`ContentDialog`（模态内容对话框，Qt `QDialog` 缺的观感与动作布局）。

### D 组 · `qxmaterial`（新库，0.1.0）

**目标**：Material 3（含 2026 的 M3 Expressive，只取形状与动效，不追全部）。

- **D1 · 库骨架**：同 C1，命名空间 `QxMaterial`；类 `Material<Name>`，文件
  `material<name>.{h,cpp}`（§七.9）；依赖 `qxcontrols`（B 组）。
- **D2 · 设计令牌映射**：M3 的 corner scale（7 级 → 收敛到 5 档，因为 A1 只有五档）、
  state layer（8% / 12% 不透明度叠色）、五级 elevation。
  风险点（开工时验证）：A1 的五档够不够用——M3 的 7 级里有几档差值只有 4px，视觉上分不开。
- **D3 · 第一批控件（10 项）**：`Switch`、`Slider`、`Badge`、`SegmentedButton`、
  `Chip`（assist / filter 两态）、`Card`（elevated / filled / outlined 三档）、`FAB`、
  `ProgressRing`、`Snackbar`、`Skeleton`。`Slider` 与 `Snackbar` 是本版新进的：
  `Slider` 补输入层（同 C4 的理由）；`Snackbar` 补反馈层与 fluent 的 `InfoBar` 对位
  （`WIDGETUI-STUDY.md` §2.3 点名、qxapp 的 `QxToast` 只有部分对应）。
- **D4 · ripple**：Material 的标志性反馈，需要 A5 的动效基建 + 命中区域裁剪。
- **D5 · 滚动追加池（`stretch`，口径同 C6）**：M3 的骨架是 **top app bar + navigation rail +
  FAB**，FAB 已在第一批；app bar 与 rail 是骨架层最高优先（§1.5）。其后：
  `TextField`（浮动标签 + 填充/描边两态，`QLineEdit` 缺的形态）、`Dialog`（M3 的
  basic / full-screen 两档）。
- **D6 · 两库共享 vs 各自实现**：`Switch` / `Slider` / `Badge` / `Card` / `ProgressRing`
  五个名字两边都有，**但形态不同**（Fluent 的开关是滑块 + 描边，M3 的开关是轨 +
  状态层 + 弹簧曲线；Fluent 的滑块带 tick 与分段，M3 的滑块是轨道 + 手柄 + 把手形态）——
  按 §1.5 的判据「答案不同不下沉」，各自实现，共享的只有 `qxcontrols` 里的机制。

### I 组 · `qxribbon` / `qxdock` 做深做全（**作者 2026-10-21 定向**，非建议）

> 作者原话的依据是 4.6 的实测：**测试没能覆盖库的场景，有些问题没有被发现**。这条不是
> 「补几个用例」，而是把 4.6 暴露的盲区逐个变成可执行项。

**现状盘点（2026-10-21 实测）**：类级骨架并不缺——`qxribbon` 23 个 tst 文件、`qxdock`
20 个，对着 58 个导出类、1759 条断言。**缺的是行为场景层**，4.6 的三个未结案就是证据：

1. **切主题后 dock 内 17px 尺寸停留**（pane 分配按旧度量分完、切换不重算）——只能以
   「dock 内 8% 预算 + `QEXPECT_FAIL`」收住（`tst_demoscreenshot` 的
   `kMaxDockSwitchDiffPercentKnownShift`），**真因没修**，用例是带伤通过。
2. **`DockWindow` 的 QSS 只认 `.QFrame`**：类型选择器 / 属性选择器 / id 选择器 / 通配
   全部不命中，七种写法试过、查不清、代码回滚，1px 内缩留在原处。
3. **不导出的内部类无法写独立链接的单元测试**（`.workbuddy` 已记坑）——一批逻辑只能
   透过公开类间接测，路径覆盖上不去。

- **I1 · 可测性基建（其余各条的地基）**：
  - 内部类可测化：照 Qt 惯例给 `_p.h` 里的类加测试可见性（`Q_AUTOTEST_EXPORT` 或
    friend test），或把可独立验证的逻辑抽成可导出的纯逻辑类；逐库盘点哪些内部类
    值得这样做。
  - 探针设施化：`--inspect`（4.6 在 dockdemo 里补了 resize 与事件排水）泛化成
    **库级**几何/树转储设施，ribbon / dock 的场景测试共用，不再各写各的。
  - offscreen 已知限制清单化（半透明 tool window `grab()` 空、平台度量随 style 变），
    能绕的写进测试基建，不能绕的写进 `limitations.md`。
- **I2 · `qxdock` 行为场景覆盖**：
  - **布局重算**：tab 高度变化、分割树增删、主题切换——每处都要断言「切完即重算、
    无旧度量残留」。4.6 那个 17px XFAIL 的场景**反向变成真用例**，修掉后摘掉 QEXPECT_FAIL。
  - **交互状态机**：drag & drop、浮动、auto-hide、pin/close 的多步序列测试
    （现状多为单步 API 断言，序列组合基本空白）。
  - **QSS 响应矩阵**：每个导出类 × {类型 / 类 / id / 属性} 选择器 × 属性挂载点，
    系统性生成用例——先复现 `DockWindow` 之谜的边界，再决定是查因还是重写。
- **I3 · `qxribbon` 行为场景覆盖**：`RibbonButton` 的 `paintEvent` 分支图像比对
  （三分支逐一）、customize 全流程序列、四值样式切换下的样式选项传播。
- **I4 · 重构 / 重写勘察**：以盲区为线索列候选——`DockWindow` 的样式路径、
  dock 布局的度量重算机制、`RibbonButton` 的绘制复杂度是三个已知入口；范围开工前勘察，
  与 4.4 的口径不同（**允许破坏**），破坏照 §1.2 走兼容通道并进 migration。
- **容量裁决**：I1–I3 **硬性进 4.7**；I4 的范围与控件滚动追加池（C6 / D5）**共享弹性**
  ——冲突时**深化优先于新库第二批**，这是作者定向给出的优先序。

## 三、执行序

```
A 组（令牌轴，qxtheme + tools/themes）───┐
                                         ├─→ B 组（qxcontrols 公共依赖库）─→ C 组（qxfluent）─┐
                                         │                                                   ├─→ E 组（gallery + 回归）→ F 组（迁移）
                                         └───────────────────────────────→ D 组（qxmaterial）─┘
G 组随各笔落地（不是收尾阶段）
I 组（ribbon / dock 深化）：I1 可测性基建可与 A/B 并行开工；I2 / I3 不依赖 A/B，随时可进
```

**A 组不做完不进 B/C/D**。这条不是流程洁癖：B2 的原语读令牌，C4 / D3 里每一个控件的圆角、
字阶、阴影、动效曲线都要有令牌可取，先写控件再补令牌等于每个控件改两遍。

C 与 D 可并行（两库互不依赖，都只踩 `qxcontrols`）。**下沉要克制**：只有两个库对同一件事
的答案相同才进 `qxcontrols`（§1.5 的判据），宁可在两库各留一份形态代码，也不为省行数
把「fluent 的样子」写进公共库。

## 六、预计的破坏面（初判，具体到条要等对应任务开工；每条都要按 §1.2 留兼容通道）

1. `QxThemeInfo` 增加度量 / 字阶 / 动效字段（A6）——注册结构变了。**通道**：新字段全给默认值
   （构造时补齐），旧调用点的注册代码不改也编译、行为不变。
2. `tools/themes/` 的令牌源换名与扩容 ⇒ 生成表全量变化，任何自己写过 QSS 的应用都会受影响。
   **通道**：旧令牌名保留一个版本、生成器继续替入（弃用先行），迁移页逐名给对照。
3. 33 处硬编码 `border-radius` 收敛到令牌 ⇒ 现有五族的观感会有**细微但不为零**的变化。
   **通道**：令牌的默认值取各族现状值，收敛后「未显式改令牌的应用看到的观感不变」。
4. 亮色骨架补字阶 ⇒ 亮暗两侧文字尺寸会有差异（现在是不对称）。
   **通道**：字阶默认值取暗色骨架现状，亮色对齐它，而不是另起一套。
5. `qxdock` / `qxribbon` 若跟随令牌化，它们的度量常量会动（`DockStyleColors` 是否要扩成
   `DockStyleMetrics` 是个具体问题）。**通道**：扩字段给默认值 + 旧构造函数保留一个弃用期；
   `QX_<LIB>_DEPRECATED_SINCE` 闸门照常走。
6. 新库自身为 0.1.0，**没有**兼容义务——0.x 的语义本来就是接口未稳（K11）。

## 七、评审决策记录（全部已定，作者 2026-10-21）

### 七.1 令牌轴是否作为 4.7 前置 —— **已定（作者 2026-10-21 采纳）：是**

不做的话，两个库的每个控件都要先自己造一遍圆角 / 字阶 / 阴影 / 动效常量，之后再统一，
等于写两遍。**影响面**：A 组占 4.7 工作量的一大块，但它**不新增控件、不新增库**，
是能在 4.7 内交付的（`WIDGETUI-STUDY.md` §五的 S 档）。

### 七.2 控件基座放哪 —— **已定（作者 2026-10-21）：单独成库，不进 `qxtheme`**

原提案是放进 `qxtheme`（省一个库）；作者裁定**单独成库**——`qxtheme` 是主题引擎，
塞进控件基座会让概念失焦，且作者明确「需要新增其它库肯定没问题」，第三个库的授权疑虑不存在。
落点见 B 组：库名 `qxcontrols`、类名 / 文件名约定均已定（§七.9，作者 2026-10-21 采纳），
依赖方向 `qxtheme ← qxcontrols ← {qxfluent, qxmaterial}`。
**遗留**：无——本条的三个子问题（放哪 / 库名 / 命名约定）全部落定。

### 七.3 第一批控件清单与分配 —— **已定（作者 2026-10-21 采纳）：共享 5 个名字、其余各自实现**（v4 扩充）

| | 控件 |
| :--- | :--- |
| 两边都有、**各自实现**（形态不同） | `Switch`、`Slider`、`Badge`、`Card`、`ProgressRing` |
| 只 `qxfluent` | `CommandBar`、`InfoBar`、`BreadcrumbBar`、`Expander`、`Rating`、`TeachingTip` |
| 只 `qxmaterial` | `Chip`、`FAB`、`Skeleton`、`SegmentedButton`、`Snackbar` |

⇒ `qxfluent` 11 项 + `qxmaterial` 10 项（合计 **21 个控件、16 个类**）。

**为什么首批是这个数，能不能再加**（v4 作者问，回答写死在这里）：

1. **加件的闸门不是数量，是全链路成本**。一个控件交付 = 状态机 + 自绘 + 动效 +
   `QAccessible` role/state + 自动化测试 + gallery 条目 + 基线截图 + `zh_CN` 目录 +
   icons-policy 登记，按 `RibbonButton` 的体量是**每控件数千行**（它的 `paintEvent`
   已经要分三条分支）。首批 21 个已经是 A（令牌轴）+ B（`qxcontrols` 基座）之外
   一个版本能扛满的量。
2. **首批的选法**：§1.5 三层（骨架 / 输入 / 反馈）每层至少一件 + 勘察清单
   （`WIDGETUI-STUDY.md` §八）里「Qt 完全没有」的件优先。v4 的扩充正是按这个判据：
   `Slider` 补输入层（此前输入件只有 `Switch`）、`Snackbar` 补 material 反馈层、
   `Rating` 补回勘察清单第 8 项（两库分配时漏掉）。
3. **还能加，走滚动追加池（C6 / D5）**：池子已点名 `NavigationView` / `TabView` /
   `NumberBox` / `DropDownButton` / `ToggleSplitButton` / `ContentDialog`（fluent 侧）与
   top app bar / rail / `TextField` / `Dialog`（material 侧），**优先级高于第二批装饰件**。
   进台账的前提只有一个：`Switch` 样板已把「令牌 → 几何 → 状态层 → 动效 → 无障碍 →
   回归」整条链路跑通——链路没通之前铺开更多控件，等于每个控件都要返工一遍。

⚠️ `CommandBar` 进了第一批：fluent 选了就没有 ribbon，它必须自带命令入口（§1.5）——
这条是 v3 对 v2 的一个**反向修正**（v2 曾建议不做）。

⚠️ `SegmentedButton` 是唯一一个「两边都该有但只做一次」的：M3 的形态更标志性（轨道 +
滑动指示条 + 弹簧曲线），Fluent 的 SelectorBar 是它的一种退化形态。**建议** 4.7 只在
`qxmaterial` 做，`qxfluent` 侧延后；反过来做的话要写两遍，而两库之间最不该共享的恰恰
是「同一名字、不同形态」的控件——那是「两套观感差异落到色板上」的最短路径。

⚠️ 勘察清单（`WIDGETUI-STUDY.md` §八）12 项与本表的对账：**12 项全部进了首批**
（v3 时 12 项里只有 `Rating` 在两库分配时漏掉，v4 补回；`Slider` / `Snackbar` 不在勘察
清单里，是按 §1.5 三层判据本版新增；`Flyout / TeachingTip` 按 fluent 侧收录、
`SegmentedButton` 只在 material 做）——勘察清单不再有丢件，后续加件都走 C6 / D5
的滚动追加池。

### 七.4 新观感的主题族 id —— **已定（作者 2026-10-21 采纳）：`rounded`（material 观感）/ `layered`（fluent 观感）**

硬规则是「主题族 id 按形态或几何命名、不用产品名」，现有五族（`classic` / `soft` / `flat` /
`slate` / `accent`）就是按这条起的名。候选：

| 观感 | 候选 id | 理由 |
| :--- | :--- | :--- |
| material | `rounded` | 大圆角阶梯是它最直观的几何特征 |
| fluent | `layered` | 分层（elevation + 窗口材质）是它最直观的几何特征 |

备选：`squircle` / `laminar` / `onion`（分层洋葱皮）。**影响面**：改名要查新词是否被占用（硬规则）。

### 七.5 三个新库的初始版本号 —— **已定（作者 2026-10-21 采纳）：`0.1.0`**

`qxcontrols` / `qxfluent` / `qxmaterial` 三个都从 `0.1.0` 起，照 `qxplugin` 在 4.0 首次出现的
先例。**影响面**：`versions.md` 的表要加三列；`index.md` 的库清单表要加三行。

### 七.6 新库是否支持 Qt 5 —— **已定（作者 2026-10-21 采纳）：支持到 5.0**

`ROADMAP` 的版本序（K34）是「… → 5.0 移除 Qt 5」。若 4.7 的新库一出生就只支持 Qt 6，
那就等于**提前执行 5.0 的决议**，而且会让「双腿」这条 CI 约束对新库失效——两者的代价都是
长期的。**影响面**：Qt 5 上没有 `QPalette::Accent`（6.6+）与 `QStyleHints::setColorScheme()`
（6.8+），自绘控件对这两个都要分叉；`qtcompat` 可能要扩。

### 七.7 demo 形态 —— **已定（作者 2026-10-21 采纳）：一个 gallery 装两套风格**

备选是两个 demo（一个 fluent、一个 material）。一个的好处是**切换本身就是回归面**
（`--style a,b` 的等价断言），两个 demo 则要维护两份基线。

### 七.8 `qxribbon` 是否要跟随 4.7 的令牌化 —— **已定（作者 2026-10-21 采纳）：跟随，但只跟 shape/type 两条轴**

elevation 与 motion 对 ribbon 的收益小（它的 chrome 已经是自绘 + 读 palette），
而 shape/type 不跟会让「同一个窗口里 ribbon 圆角 6px、控件圆角 12px」。**影响面**：
ribbon 的 10 张表要重跑门禁，观感有细微变化。
（`qxdock` 不在本条讨论——它 QSS 驱动、跟随是自动的，见 H 组的不对称说明；
`DockStyleColors` 是否扩成 metrics 随本条一并裁定。）

### 七.9 公共依赖库名与新库的类名 / 文件名 —— **已定（作者 2026-10-21）：`qxcontrols`；类 `Fluent*` / `Material*`**

**库名**：仓库八库（含新三库）的命名规则是「`qx` + 这个库供给的域名词」。这个库供给的域
名词就是 Controls——设计语言规范（Fluent / M3 的文档）与 Qt Quick Controls 都用这个词指
「可交互控件」这一层，基类 `QxControl` 落名也自然。它有一个真实代价：**八库里唯一的复数**
（qxtheme / qxdock / qxribbon / qxwindow / qxapp / qxplugin / qxcore 全是单数形态的域名词）。
复数在这里是有意的——它名字指一个集合（kit），不是一类东西；真要保单数只能 `qxcontrol`，
但那会让基类撞成 `QxControl::QxControl`。

**类名 / 文件名**（C1 / D1 已引用本条）：

| | 取值 | 先例 |
| :--- | :--- | :--- |
| 类名 | `Fluent<Name>` / `Material<Name>`（`FluentSwitch`、`MaterialChip`） | `QxDock::DockButton`、`QxRibbon::RibbonBar`——「命名空间 + 域前缀类名」的既有双例 |
| 文件名 | `fluent<name>.{h,cpp}` / `material<name>.{h,cpp}`，与类同名小写 | `dockbutton.h` ↔ `DockButton` |
| 私有头 | `fluent<name>_p.h` | 全仓惯例 |
| 基座库类 | `QxControl` / `QxStateLayer` / `QxRingPainter` / `QxShadowPainter`，文件 `qx<name>.{h,cpp}` | `qxtheme` 的 `qxthememanager.h` ↔ `QxThemeManager` |

**为什么类名带设计语言前缀、不用裸名**（裸名即 `QxFluent::Switch`）：
1. **两库都会有同名控件**——`Switch` / `Card` / `ProgressRing` / `Badge` 四个名字两边都有
   （§七.3），裸名意味着这两个类名在两个库里重复，应用同时链接两库时 `using namespace`
   两个一起用会直接撞名；前缀从源头消灭这个问题。
2. Switch / Card / Chip 都是英文常用词，裸名在 IDE 补全与全局搜索里噪声极大；
   `FluentSwitch` / `MaterialChip` 一眼可辨。
3. 命名空间与类名的轻度重复（`QxFluent::FluentSwitch`）仓库已有先例且已接受
   （`QxRibbon::RibbonBar`）。
4. §1.3 第 5 条说「fluent / material 可以直呼其名」，本条把它的适用面**从库名与命名空间
   扩到类前缀**——**已随本条采纳**（作者 2026-10-21），§1.3 第 5 条的适用面照此扩写。
