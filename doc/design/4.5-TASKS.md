# QtCanpool 4.5 任务规划

> 4.5 是功能升级版本（可能破坏 API），在 4.4（不破坏 API 的内部重构，已发布 4.4.2）基础上做能力增长与破坏收尾。本文档为 4.5 的权威任务分解。

## 一、版本定位与约束

- 功能升级：允许移除/改签名（K26）；引入成熟的功能性改进与超出同类的能力。
- 双支持：保留 Qt 5 / Qt 6 双支持（K30）。
- 验证腿：Qt 6.12 验证已在 4.4.2 提为门禁（K31），4.5 复用不重建。
- 进号：因可能移除/改签名 → minor；破坏项需 migration 文档（K11 / 附录 B）。
- 弃用闸门：`QX_<LIB>_DEPRECATED_SINCE` 家族保留不清理（预留机制，非死代码）。
- ⚠️ **台账动态追加（作者 2026-10-17 订）**：4.5 的任务在开发期内**持续追加**——已有组一律保留、新任务按所属组的序号续编（B12、C9、D3…）。**不存在"某组已完成故封闭"或"整版做完"的中间状态**；只有发版结算时才做一次性汇总。⇒ 本文件里各组的进度一律记为「当前已完成」，不再写「已封闭 / 已完结」。

### K 组 · 架构纠偏（不合理设计推翻）

> 本组是 4.5「彻底升级改造」主线的**总纲**（作者 2026-10-17：可以把一切不合理的设计推翻，不要小修小补）。**落点分散在 B/C/D/E/G 各组**，此处只立判据与指针，不复制正文。

**判据（一项值得推翻，须至少命中一条）**

1. **越界**：库把本属应用层的职责（视觉资源 / 主题 / 外观决策）打包进自己，使应用无从替换或覆盖。
2. **双轨**：同一件事在库里有两套互不相干的实现，且彼此不通气（典型＝两套主题系统）。
3. **隐式压制**：库的行为在**没有对外 API 表达**的前提下压过应用的设置（典型＝widget 级样式表盖掉 app 级）。
4. **开关错配**：非外观的开关（配置旗标 / 调试宏）改变外观或行为。

## 六、追加：架构纠偏 · 主题归应用（2026-10-17，作者提出）

作者先后提出两条裁定，合并成 4.5 的一条改造主线（**K 组**）：

1. 「`qxtheme` 内置的主题耦合了 ribbon 里的主题，不是一个通用的模块；主题信息应该由使用者负责设置或注册，`qxtheme` 应该作为一个独立的模块」。
2. 「`qxribbon` 不应该自带主题，主题应该由应用负责，`qxribbon` 主要做库本身的功能」。

### 根因（实测确认，非推测）

- **两套互不相干的主题系统**：`qxribbon` 内 grep `qxtheme` **零命中**。`RibbonTheme::setTheme()` 是 **widget 级** `widget->setStyleSheet()`；`QxThemeManager::apply()` 是 **app 级** `app->setPalette()` + `app->setStyleSheet()`。两者**从不通信**。
- **Qt 样式表级联赛制**（Qt 6.8.3 离屏实测）：只在 app 级出现的规则**仍生效**；两边都匹配时 **widget 自己的 sheet 赢**。
- **`demos/qxapp/appshell` 暗色锁白的机制**：`RibbonMainWindow` 构造第 91 行 `setRibbonTheme(ribbonTheme())`，`m_theme` 初值 `LightOffice2013Theme` ⇒ 主窗口自身贴 `light_office2013.css`；而该 CSS 473 行里 **111 处命中 Ribbon、非 ribbon 的顶层规则 0 条**（以 `/* start ribbon set*/` 打头）⇒ **只有 ribbon 被锁白**，其余区域吃 app 的 dark sheet + palette 正常变暗。
- **像素证据**：app 设 `dark_wps.css` 且构造 `RibbonMainWindow` ⇒ ribbon bar 像素 `#ffffff`；清掉窗口自带 sheet ⇒ `#404244`（正是 `dark_wps.css` 的 `QxRibbon--RibbonBar{background:#404244}`）。

## 七、追加：预置主题整套重做（2026-10-17，作者提出）

作者先指出「`light_fluent2016` 与 `light_fluent2019` 看效果没啥区别」，核查确认两套只是**同一色阶取相邻一档**
（85 个色令牌 34 个不同、最大通道差 30，全落在近白区；2016 另有 9 处 `#a9d3f5` 非令牌手调色）。
随后裁定：**`ribbondemo` 自带的 `office2016blue` 去掉，`res/themes` 重新提供几套标准主题**
（当时按四个产品名给家族起名，后来改为中性形状词，见下），「原来的 css 都是历史产物，我们不要背负历史」；
又指出「四套亮和四套暗风格完全一样」，并要求「主题生成工具也可以进仓库」。

- **"四套一样"的根因**：第一版是**一套骨架 + 四份色板**，只换颜色。相邻灰阶肉眼分不出，
  与 Fluent 2016/2019 同一个病放大四倍。⇒ **家族差异必须落在结构上**：选中态怎么表示、
  圆角、页签条与页面之间有没有分隔线、强调色用在哪。
- **生成方式（工具入仓）**：`tools/themes/` 下 `build_themes.py`（4 家族 × 2 方案色板 + 生成器）、
  `skeleton_light.css`（浅色只描述 Ribbon）、`skeleton_dark.css`（暗色另重画标准控件，
  因为暗色下平台样式会忽略调色板）、`chrome_<family>.css`（结构差异层，追加在骨架之后靠层叠覆盖）、
  `README.md`（做一套主题的方法 + 20 个颜色角色表）。产物是 `res/themes/<family>_<scheme>.css`，
  即**生成物不入 lint、手改会被覆盖**。
- **四家族的结构身份**（每条都是一眼可见的差异，不看名字也能分）：
  | | 条与页的明暗 | 选中态 | 分隔与盒子 | 文件按钮 |
  | :--- | :--- | :--- | :--- | :--- |
  | classic | 条灰、页白 | 抬高的白卡片（直角、带边） | 分组竖线 + 大按钮有框 | 实心强调色方块 |
  | soft | 条白、页灰（**层次反过来**） | 开进正文的圆角开口（无边框） | 全无 | 实心强调色、圆角 |
  | flat | 同色，一层 | 强调色 2px 下划线 + 文字取强调色 | 全无 | 实心强调色方块 |
  | slate | 条深灰、页白 | 留在条上，只加顶部 1px 强调线 | 分组发丝线、无框 | 无填充，仅强调色文字 + 下划线 |
- **为此新增 `body` 颜色角色**：原先 `surface` 同时充当"页签坐在上面的条"与"条下面的页"，
  于是任何家族都**无法把条与页的明暗反过来**——这正是四套读起来一样的根因之一。
  现在 `body`＝正文档位，两份骨架的页/分组/分隔符/滚动按钮都取它；`surface` 只作 chrome。
  RibbonBar 自身的背景改由各族设置，因此"条"覆盖到快速访问行，而不只是页签那一条。
- **命名改为中性形状词**：`classic` / `soft` / `flat` / `slate`。原先四个名字是别家的产品名，
  以「预置主题」名义分发会被读成官方移植（实际只是气质近似），而 id 是写进配置的对外契约，
  发出去再改成本更高。改名只动生成器的 `FAMILIES` / `FAMILY_NOTES` / `PALETTES` 键，8 个文件重新生成。
  实测四套的条/页：classic `#f3f3f3`/`#ffffff`、soft `#ffffff`/`#edebe9`、
  flat `#ffffff`/`#ffffff`、slate `#e5e5e5`/`#ffffff`。
- **删除**：旧 7 套样式表 + `ribbondemo` 自带的 `office2016blue.css`（连 `ribbondemo.qrc` 的 `/theme` 资源块）。
  新 id：`classic-light` / `classic-dark` / `soft-light` / `soft-dark` / `flat-light` / `flat-dark` / `slate-light` / `slate-dark`。
- ⚠️ **一个被测试抓到的设计问题**：soft 家族第一版做成"全白"后，`tst_demoscreenshot` 的
  **空白窗口判据**（单一颜色占比须 < 90%）直接报 **93.5%** —— 这不是测试误报，而是说明那个版本
  过于纯白、整窗几乎没有层次。改成"白条 + 米白身"后通过。**判据留着，别为迁就主题去放宽它。**
- ⚠️ **金色截图**：`ribbondemo` 默认主题换成 `soft-light`，旧 baseline 已无意义，已删
  `tests/demo/golden/Windows/Qt6/ribbondemo.png`；金色比对本身是 opt-in（不加 `QTCANPOOL_VISUAL_BASELINE` 就 SKIP），
  不拦门禁。**需在有字体的机器上用 `QTCANPOOL_UPDATE_GOLDEN=1` 重建**（离屏本机无字体，重建会把方框烤进基线）。
