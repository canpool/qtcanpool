## 一、为什么 4.2 要换一个做法

### 1.1 3.x / 4.x 一直在动「别的东西」

| 版本 | 主题 | 动的是什么 | 用户看到的窗口变了多少 |
| :--- | :--- | :--- | :--- |
| 3.0 | 骨架与命名 | `qx*` 统一命名、`qxwidget` → `qxapp` | 变（改名，需迁移） |
| 3.1 | 偿还欠账 | legacy ribbon 物理移除、`fancy*` 处置、质量门禁（覆盖率/tidy/消毒器）、`qxwindow` 首个单测、脚手架 | **几乎不变** |
| 3.2 | 能力增量（一） | `qcanpool` 整库删除、i18n、Toast、属性编辑器、设置对话框 | 变（新增常用件） |
| 3.3 | 能力增量（二） | 命名工作区、状态栏百分比进度 | 小变 |
| 4.0 | **换骨架** | 全树 qmake 归零、新库 `qxplugin`、`src/modules` + IDE 样板、行尾归一 LF | **不变** |
| 4.1 / 4.1.1 | **修肉** | 处置 16 条自写欠账、建已知限制页、修 3 个行为缺陷 | 只有 3 个缺陷被修 |

**6 个版本里，4 个的主语是「别人怎么用它」**（构建方式、行尾、插件体系、门禁），而不是「它自己好不好用」。
`qxribbon` 从 3.0 到 4.1.1 只动过一次 `.h`（一处 `enterEvent` 签名），`qxdock` 一次都没有。
这不是没做工作——是**工作全花在了地基上**。

### 1.2 一句话定位

> 4.2 不再动地基，**把三个"用户每天盯着"的库做深，并把项目本体剩下的半成品收口**。

主题名随 K25 定为「**三库做深、项目收口**」。

### 2.2 三个主库的细分

**`qxwindow`（0.1.2）—— API 面最窄，但它是 Qt6 唯一的无边框路径**
- 公开面只有 `WindowAgentBase` + `WindowAgentWidget`；`WindowStyleAgent` 条件编译且**默认关**。
- 无边框能力实际由 Win32 后端提供（`WM_NCCALCSIZE` + 保留 `WS_THICKFRAME | WS_CAPTION`），
  这正是 `RibbonAppWindow` 在 Windows+Qt6 上「启动即最大化」不受影响的原因（限制页已记）。
- 8 条 `TODO`/`FIXME` **全部是从 Qt 上游继承的**（`windowcontext_win.cpp` + `windowsystem_p.h`，
  写着 `### TODO:` / `### FIXME FIXME FIXME`，文件里还留着 Qt 源码的 GitHub 链接）；
  另有 2 条 `hack` 注释（`windowcontext_cocoa.mm:333`、`windowcontext_win.cpp:212`）。
  4.1 把「不认领从 Qt 继承的注释」写进了非目标，所以这 8 条**至今没有归宿**。
- 测试只有一个文件、8 个用例，且文件头**明文声明**「拖动、系统菜单、Win10 边框 workaround 测不了」。
- ⚠️ **`WindowStyleAgent` 是一个悬案**：它提供 `systemTheme() → {Unknown, Light, Dark, HighContrast}`，
  按平台有原生实现。但它 **默认不编译**（`option(QX_WINDOW_CONFIG_STYLE_AGENT "Config style agent" NO)`）、
  **全仓无人 `#include`**（只有它自己的目录）、**文档里一个字都没提**。
  而 `qxtheme` 已有自己的系统深浅色探测（`detectSystemDark()`，Qt 6.5+ 走 `QStyleHints::colorScheme()`，
  更早版本回退到调色板亮度，Qt 6.5+ 还接了 `colorSchemeChanged` 信号）——**功能重叠，但 qxtheme 的探针更完整**。

**`qxribbon`（0.10.2）—— 功能面最宽，但接口卫生与观感没被照顾**
- 26 个公开类；`res/` 下 6 套内置样式表 + 两套图标。
- ⚠️ **接口卫生问题**：`ribbongallery_p.h` 是 `_p.h`（私有实现头的命名约定）**却含导出类**
  `RibbonGalleryViewport`（`QX_RIBBON_EXPORT`）。约定与实际不一致。
- ⚠️ **`FramelessHelper` 的定位长期悬着**：它是 `qcanpool` 时期沿下来的类，
  **不在任何命名空间、没有导出宏**，被 `RibbonWindow` 无条件使用（无 `QT_VERSION` 分支）。
  它在 Windows+Qt5 走原生后端（`FRAMELESS_USE_NATIVE`），Qt6 走纯 Qt 模拟路径——
  而 Qt6 上「启动即最大化」的缺陷正落在这条模拟路径上。限制页已把**改法与代价**写清，
  但「到底改还是废弃」没有定论，于是它既不算欠账也不算能力。
- 2 条自写 `todo`（都是小写，`grep -i` 才扫得到）：`ribbonbutton.cpp:742`（字体改变需重算）、
  `ribbonstyleoption.h:26`（`@todo 后续开发通过配置文件定义 ribbon 的尺寸布局`）——后者其实是**用户可见的能力**。
- 12 个示例自 **2023-10-24** 起未动（4.0 只是把它们从 qmake 迁到 CMake）。

**`qxdock`（0.2.0）—— 改得最多，号却几乎没动过**
- 25 个公开类；含 X11 专用子树 `linux/`（仅在 `UNIX AND NOT APPLE AND NOT WASM` 编译，额外链 `Qt5::GuiPrivate` + `xcb`）。
- **3.x 以来它的 `.h` 改动最多**（4.1.0 到 4.1.1 之间唯一被修的行为缺陷也在它身上），
  但版本号停在 `0.2.0`，且 `CHANGELOG` 顶端挂着 `Unreleased` —— **账一直在记，就是没结算**。
- 已知待跟进（`TOPIC-known-issues.md`）：两处 `autoHideContainer()->toggleView()` 要**独立判断**
  能不能删（A2 删的是另一处，别照搬结论）。

### 2.4 一句话结论

**能力面不缺——缺的是「把已有能力收成可交付的形」**：
`qxwindow` 的 API 太窄且有一件悬案，`qxribbon` 的接口卫生和「延迟 resize」那条链没动，
`qxdock` 的账记了没结算，而项目本体的半成品（脚手架不同步、示例陈旧、文档口径错、没有发布流程）
恰好都落在**外部用户最先看到的地方**。

### A9 · `FramelessHelper` 标 deprecated（2026-10-11，K27）

**动手前先核了本仓的弃用工具是否可用，结果顺手查出一件事**：`QX_<LIB>_DEPRECATED_SINCE`
**七个库都定义着、全仓却从未被用过**，而且默认截止点是 `QX_<LIB>_VERSION`（本库当前版本）、
宏体是 `(major,minor,0) > 截止点`——对任何**已经发生过**的弃用都返回假。实测：当前 `0.10.2` 下
`DEPRECATED_SINCE(0,10)` 为假、`(0,11)` 为真，而版本号一旦升到 `0.11.0` 又变回假。Qt 自己的默认值是
`QT_VERSION_CHECK(5,0,0)`，本仓把默认值换成了"当前版本"，于是这套机制在本仓**恒不回真**。
⇒ 登记为 **D11**（本期不改：它牵扯七个库，且要先定"默认截止点该是什么"，属独立一笔）。
A9 因此用标准 `QT_DEPRECATED_X`——不依赖版本号，一定生效。

**标法**（`FramelessHelper` 没有命名空间、没有导出宏，且编译库自身时会被 `RibbonWindow` 用到）：

| 做了什么 | 为什么 |
| :--- | :--- |
| `framelesshelper.h`：`class QT_DEPRECATED_X("...") FramelessHelper` | 类级标注，消息直接给出"Qt 6 用 `QxApp::RibbonAppWindow`"。属性放在 `class` 之后是否可用**单独验过**（两个 GCC 13.1 / 8.1，告警在使用点正常触发） |
| `ribbonwindow.cpp`：`QT_WARNING_PUSH` / `QT_WARNING_DISABLE_DEPRECATED` / `QT_WARNING_POP` 包住用到它的那段实现 | `RibbonWindow` 是**有意**使用一个已弃用的类。**不能**给 `RibbonWindow` 挂标注：它被 11 个示例 + 1 个 demo + 测试在用，而"两侧构建 0 warning"是门禁，挂上当场红 |
| `components.md` 加 `RibbonWindow` 行、`limitations.md` 第七条补代码结论、`migration.md` 新增「4.2 起弃用」 | K27 要求「文档里『Qt6 上用哪个类』有唯一答案」 |
| 库级 `CHANGELOG` 加 `Unreleased / Deprecated`（K24） | 只加标注、不改行为 ⇒ **不落号**，留在 `Unreleased` |

**作者补充的一条关键前提**（本次一并落进文档）：`FramelessHelper` 存在的理由是**让 qxribbon 的无边框
实现自包含**——`qxribbon` 只链 Qt、不依赖 `qxwindow`，而更好的 `qxwindow` 实现之所以能落地，是因为
`qxapp` 里另开了 `RibbonAppWindow`。所以"删掉 `FramelessHelper` 之后 `RibbonWindow` 何去何从"必须
一并回答。**核出来的结构性事实**：`RibbonWindow` 与 `RibbonAppWindow` 是**兄弟不是父子**——都继承
`RibbonMainWindow`，只是无边框后端不同；`RibbonWindow` 相对基类**只多一个无边框**（主题、
`ribbonBar()` 全在基类里）。⇒ 结论、三条候选做法与"时机 = Qt 5 下线日"全部写进
`migration.md` 的「`FramelessHelper` 删除之后，`RibbonWindow` 怎么办」。

### A3 · `qxwindow` 补测试：把 resize 几何抽成纯函数（2026-10-11）

**W3 的原文**是"39 条断言是 7 个库里最薄的，且现有测试**明确排除**需要窗口管理器的部分"，
做法两条："把命中/尺寸的几何计算抽成可测的纯逻辑；需要 WM 的部分做成「有环境才跑」的可选用例"。

**勘察结论：可抽的就是 `windowcontext_qt.cpp` 里那两个 file-static 函数。**
`calculateCursorShape()` / `calculateWindowEdges()` 收一个 `QWindow*`，但只从中读**三样**东西：
`width()`、`height()`、`visibility()`——**前两样就是全部计算**，第三样是个守卫（不是 `Windowed`
状态就不谈 resize）。所以它们是"被窗口外壳包住的纯算术"。

**做法**：新建 `src/libs/qxwindow/windowgeometry_p.h`（私有头，已进 `CMakeLists.txt` 的 `SOURCES`）：

| 名字 | 形态 | 说明 |
| :--- | :--- | :--- |
| `kResizeBorderThickness` | `inline constexpr int` = 8 | 原 `kDefaultResizeBorderThickness`（原来是 `quint8`） |
| `resizeEdgesFor(const QSize &, const QPoint &)` | `inline`，返回 `Qt::Edges` | 完全照搬原比较链 |
| `resizeCursorFor(const QSize &, const QPoint &)` | `inline`，返回 `Qt::CursorShape` | 完全照搬原比较链 |

`windowcontext_qt.cpp` 里那两个函数**保留同名同签名**，只留 `Q_OS_MACOS` 分支与可见性守卫，
函数体各变成一行调用。**行为逐字不变**（`if (!window) {...} if (visibility != Windowed) {...}`
合并成一个 `if`，语义相同）。

⚠️ **平台细节**：`windowcontext_qt.cpp` **在 Windows 原生构建里根本不编译**（`CMakeLists.txt` 里
它只挂在 `UNIX AND NOT APPLE` 与 `NATIVE=OFF` 两支下）。而函数是 `inline` 定义在头文件里，
所以**测试在任何平台上都能编到同一份源码**——这正是"抽出来"的另一个好处。

**新增 `tests/qxwindow/auto/tst_qxwindowgeometry.cpp`（11 个用例 + 1 个可选用例）**：
中间点无边界 / 四条边 / 四个角（**含哪条对角线配哪个方向**：左上与右下是 `SizeFDiagCursor`，
右上与左下是 `SizeBDiagCursor`）/ **半开边界的非对称**（近侧 `x < t` 排除内边界，远侧
`x >= w - t` 包含内边界 ⇒ **远侧那条比近侧宽 1 像素**，这是原行为，**断言下来而不是悄悄"修正"**）/
比两个边界还窄的退化窗口 / 光标与边界**在整张 200×100 窗口的 20000 个点上逐一一致**（这是把两个
函数一起抽出来才测得到的性质）/ 边界条带的**总面积**（中间区 = `(w-2t)×(h-2t)`，用闭式算出来对）。

**可选用例（`windowFollowsTheBorder`）的判据换过一次，值得记下来。**
它走完整链路：真 agent → 真窗口 → 合成 `QMouseEvent`（`QCoreApplication::sendEvent` 发给
`QWindow`）→ 读 `widget->cursor().shape()`。第一版把它挂在环境变量
`QTCANPOOL_WINDOW_INTERACTIVE` 上（"opt-in"），但那样**在 CI 里永远不跑**，等于没有覆盖。
换成的判据是**两个后端本来就不一致的一个事实**：

> Qt 后端在 `WindowContextQt::winIdChanged()` 里 `| Qt::FramelessWindowHint`；
> 原生后端（`windowcontext_win.cpp` / `windowcontext_cocoa.mm`）**从不碰 Qt 的 window flags**。

于是"谁在管事"可以用 `window.windowFlags() & Qt::FramelessWindowHint` 判，**不能用平台名判**——
CI 的**每一腿**（含 Windows）都跑在 `QT_QPA_PLATFORM=offscreen` 下，`platformName()` 全是
`offscreen`。macOS 上 Qt 后端"故意不给 resize 光标"也是 `QSKIP`。

⚠️ **但"窗口映射不上"这条 `QSKIP` 只在"可能由原生后端管事"的平台（Windows / macOS）上成立**：
在**只有 Qt 后端**的平台（Linux），那里跳过就是**悄悄丢掉这条用例唯一的覆盖**，
所以同一条件下改成 `QVERIFY`——**在必须能跑的地方，跑不起来是失败而不是跳过**。
（判据不是平台名，而是 `Q_OS_WINDOWS`/`Q_OS_MACOS` 这个编译期事实：它回答的是
"这台机器**可能**用原生后端吗"，与运行期那个 flag 探测回答的问题正好互补。）

**这条判据两个方向都在本机验证过**：另配一个 `-DQX_WINDOW_CONFIG_NATIVE=OFF` 的构建
（Windows 上也能用 Qt 后端，因为 `NATIVE=OFF` 时 `CMakeLists.txt` 走 `else()` 分支）：
- `NATIVE=ON`（默认）：`SKIP ... the native backend is in charge here` ✅
- `NATIVE=OFF`：`PASS  : tst_QxWindowGeometry::windowFollowsTheBorder()` ✅

⇒ 所以 **ubuntu 的 CI 腿会真的跑它**，而 Windows / macOS 腿优雅跳过。可选用例不再是"死代码"。

**验证数字**：qt6 构建 **0 warning** / qt5 构建 **0 warning 且日志里 `Qt6` 出现 0 次** /
两侧 `ctest` **12/12** / clang-format **349 文件 0 违规**（新增 2 个文件已入库后再数）。
**无行为改动、无 API 改动** ⇒ 不落号，只在 `qxwindow` 的 `CHANGELOG` 下 `Unreleased / Cleanup` 记一行。

⚠️ **一条操作坑**：Windows 上测试可执行文件是 **GUI 子系统**，直接跑（含重定向到文件）**什么都
收不到**——`ctest` 能拿到是因为它自己重定向。要看报告用 QTest 的 `-o <file>,txt`；

### A14 · qxdock 尺寸/自动隐藏语义复核并落成测试（2026-10-11）

Q3 的原文："4.1.1 修了「空窗口反钉」，但 `updateResizeHandleSizeLimitMax()` 与 `isTopLevelArea()`
的语义在旧笔记里被写错过，值得按代码重读一遍并落成测试"。

**① `DockPanel::isTopLevelArea()` 的实际语义**（旧笔记写的是 `rootSplitter() == this`）：

```cpp
auto container = dockContainer();
if (!container) return false;
return (container->topLevelDockPanel() == this);
// 而 DockContainer::topLevelDockPanel() = openedDockPanels().count() == 1 ? panels[0] : nullptr
// 而 openedDockPanels() 只收 !isHidden() 的面板
```

⇒ 它回答的是"**我是不是我所在容器里唯一可见的停靠面板**"。名字按"通常所处的位置"起，
但**答案会在面板自己什么都不变的情况下翻转**（把邻居藏起来即可）。两个不直观的推论都落成断言：
- 两个可见面板时**两个都不是** top level；关掉其中一个后，**幸存者**变成 top level（`tst_DockPanel::topLevelArea()`）。
- **自动隐藏面板不是** top level，**哪怕它是窗口里唯一的面板**——它的 panel 是直接 `new` 出来的，
  从不走 `DockContainer::addDockPanel()`，所以容器的面板表里根本没有它（`dockPanelCount() == 0`）。
  这正是 `docktab.cpp:665` 那句 "It is the only panel that opens in the container" 的语境。

**② `updateResizeHandleSizeLimitMax()` 的实际语义**：

```cpp
auto rect = q->dockContainer()->contentRect();
const auto max = orientation == Qt::Horizontal ? rect.width() : rect.height();
m_resizeHandle->setMaxResizeSize(max - s_resizeMargin);   // s_resizeMargin = 30
```

上限 = **dock 容器内容矩形 − 30px**（那 30px 是留给停靠区的一丝可见量）。同一个数、同一个来源
也用在 `DockAutoHideContainer::updateSize()` 里（`qMin(m_size, rect - 30)`）。

**测试只能走公开门**：`DockResizeHandle` 有 `setMinResizeSize` / `setMaxResizeSize` 而**没有 getter**，
`updateSize()` 又是 `protected`；能用的只有 `DockAutoHideContainer::setSize()`。所以断言是这样写的：
- `setSize(100000)` ⇒ `width() == contentRect().width() - 30`（**被夹住而不是被照办**）。
  ⚠️ 断言写成**关系**而不是绝对数：首次布局前 `contentRect()` 还不是窗口尺寸（4.1.1 记过这点）。
- `setSize(1)` ⇒ `width() == 1`：**下限（resize handle 的 64）在这一路径上不生效**——它守的是
  **拖拽**，不是这个调用。这条不对称也写成断言，因为它不写下来就会被当成 bug。

**结论：本条没有改动任何库代码**（只加测试），所以 `qxdock` 的 `CHANGELOG` **故意不动**。

**验证**：同上（`ctest` 两侧 12/12；两个新用例用 `-o` 报告确认**真的执行并通过**：
`tst_DockPanel::topLevelArea` / `tst_DockAutoHideContainer::sizeObeysTheContentRectAndItsMargin`）。

### A15 · X11 路径的覆盖与验收（2026-10-11，Q4）

Q4 的原文：`linux/` 子树只在特定三元组编译，CI 的 ubuntu 腿未覆盖 `QX_DOCK_X11` 的实际行为。

**勘察结论**（逐条核对代码与 workflow，不靠印象）：

`QX_DOCK_X11` 是**编译期**宏（`qxdock_global.h:13-17`）：`Q_OS_UNIX && !Q_OS_MACOS && !Q_OS_WASM` ⇒ 1。

于是四条腿的真实覆盖是：

| 腿 | `QX_DOCK_X11` | `linux/` 是否编译 | xcb 调用是否真跑 |
| :--- | :--- | :--- | :--- |
| ubuntu × Qt 6.8.1 / 5.15.2 | 1 | ✅ | **❌** |
| windows / macos | 0 | ❌ | ❌ |

**「编译了」和「跑到了」是两件事**，分界点是一个**运行期**函数 `internal::is_platform_x11()`
（`dockutils.cpp:215`）——`QGuiApplication::platformName() == "xcb"`。CI 的 `Test` 步固定
`QT_QPA_PLATFORM: offscreen`（`ci.yml:44`，`quality` 腿同样），`platformName()` 是 `offscreen`
⇒ 所有 xcb 请求在 `is_platform_x11()` 处短路（`xcb_get_atom` 返回 `XCB_ATOM_NONE`、
`xcb_add_prop` 直接 return、`detectWindowManagerX11()` 返回 `"UNKNOWN"`）。

所以 Q4 的判断**成立，但要说准**：不是「`linux/` 子树没人编译」，而是
**「xcb 交互层在 CI 上一次都没被执行过」**——`DockFloatingTitleBar` 这个 widget 本身反而是被覆盖的
（`QX_DOCK_X11=1` 时 `dockfloatingcontainer.h:86` 无条件 `new` 它，offscreen 下照常构造、布局、绘制），
被跳过的只是它向 X server 发出的那些请求。

**顺带核掉的一处疑似缺陷（结论：当前不是缺陷）**：`xcb_update_prop()`（`dockutils.cpp:257`）是这组
辅助函数里**唯一**没有内置 `is_platform_x11()` 短路的那个（另外三个 `xcb_get_atom` /
`_xcb_get_props` / `xcb_add_prop` 都有）。单看实现像会在 Wayland / offscreen 下把
`x11_connection()` 的空指针喂给 `xcb_send_event()`，但查了它全部两处调用方
（`dockwindow.cpp:1122`、`:1135`）**都先判了 `platformName() == "xcb"`**，与 `is_platform_x11()`
是同一个条件 ⇒ 当前安全。记这一笔是因为该保护**只对现有调用方成立**：下一个直接调它的地方
不会自动获得保护，值得与三个兄弟函数对齐。

**为什么本笔不改 CI**：真正的 X11 覆盖要让 ubuntu 腿在 `xvfb-run` 下跑（使 `platformName()` 真成 `xcb`），
这会把「编译通过」变成「真的连上 X server 发请求」，而这一层从未被执行过，首次运行结果不可预测；
且本机是 Windows，**该分支在 Windows 上根本不编译**，任何改动都只能靠 CI 验证。
按「不拿没验证过的东西去撞发版闸门」，本笔落在**结论与记录**上，把一个模糊的「没人测」
变成可核对的边界。

**留给有 Linux 环境时**：① 给 CI 加一条**独立、非门禁**的 x11 腿（`xvfb-run ctest` +
`continue-on-error`），让这一层首次真正跑起来；② 补上 `xcb_update_prop()` 的内置短路。

**验证**：纯勘察与记录，未改任何代码 / CI ⇒ 无行为改动、无 API 改动，不影响构建与 `ctest`。

### C3 · AUTOMOC 绕法的去留（2026-10-11，D9）

D9 的疑问：`qtc_autogen_rescan()` 是对「新增源文件后 AUTOMOC 不重扫」的绕法，上游可能已修；
升级 CMake 后重验一次，决定去留。

**结论：保留。** 本机 CMake 是 **4.2.1**（仓库 `cmake_minimum_required` 只要求 3.10），
在 **Qt 6.8.3 与 Qt 5.15.2 两条腿上都做了 A/B，结论一致**。

**为什么值得怀疑**——新版 CMake 看起来已经修好了，三个假象都指向"已修"：

1. 多了一个专门的 `<target>_autogen_timestamp_deps` 目标；
2. `build.make` 里 timestamp 规则挂在 `compiler_depend.ts` 上；
3. 而 `compiler_depend.make` **真的列出了该目标的 34 个 `.cpp`**。

照这张依赖图，新增源文件理应让 timestamp 过期并触发重扫。**实测不成立。**

**实验**：`qxdock` 用 `file(GLOB DOCK_SOURCES CONFIGURE_DEPENDS "*.cpp")`，丢一个新 `.cpp` 进去就会被
自动收录，是最干净的试验场。放一个带 `Q_OBJECT` 且 `#include "自身.moc"` 的临时探针——
正是「moc 没跑」时必炸的那种写法（报错指向 `Q_OBJECT` 缺失或 include 目录不对，比真正的原因难查得多）。

| 绕法 | Qt 6.8.3 | Qt 5.15.2 |
| :--- | :--- | :--- |
| 关掉（`return()`） | ❌ `fatal error: zz_autogen_probe.moc: No such file or directory`；日志只有 `Built target qxdock_autogen`，**没有** `Automatic MOC` | ❌ **同一条消息**，同样没有 `Automatic MOC` |
| 恢复 | ✅ 出现 `Automatic MOC and UIC for target qxdock`，编译通过 | ✅ 同上 |

两侧**同一条报错、同一个「autogen 被判定为最新」的现象**；恢复绕法后同一棵树两侧都能编过
⇒ 绕法**仍然必需**，上游并未修好。

**落点**：`cmake/QtCanpoolAPI.cmake` 里 `qtc_autogen_rescan()` 上方**补一段注释**写明本次结论
（连同上面那三个"看起来已修"的假象），免得下一个人照依赖图判断又把它删掉。
**函数本身一字未改**。探针文件是临时的，已删除、**未提交**。

**验证**：树回到探针之前的状态后，两侧重新 configure + 全量构建 **0 warning**、`ctest` **12/12**。

### D2 · 补建四个库的库级 `CHANGELOG`（2026-10-11，D4）
