## 一、为什么 4.2 要换一个做法

### 1.1 3.x / 4.x 一直在动「别的东西」

| 版本 | 主题 | 动的是什么 | 用户看到的窗口变了多少 |
| :--- | :--- | :--- | :--- |
| 3.0 | 骨架与命名 | `qx*` 统一命名、`qxwidget` → `qxapp` | 变（改名，需迁移） |
| 3.1 | 偿还欠账 | legacy ribbon 物理移除、`fancy*` 处置、质量门禁（覆盖率/tidy/消毒器）、`qxwindow` 首个单测、脚手架 | **几乎不变** |
| 3.2 | 能力增量（一） | `qcanpool` 整库删除、i18n、Toast、属性编辑器、设置对话框 | 变（新增常用件） |
| 3.3 | 能力增量（二） | 命名工作区、状态栏百分比进度 | 小变 |
| 4.0 | **换骨架** | 全树 qmake 归零、新库 `qxplugin`、`src/modules` + IDE 样板、行尾归一 LF | **不变** |
| 4.1 / 4.1.1 | **修肉** | 处置 16 条自写欠账、建已知限制页、修 3 个行为缺陷 | 只有 3 个缺陷被修 |

**6 个版本里，4 个的主语是「别人怎么用它」**（构建方式、行尾、插件体系、门禁），而不是「它自己好不好用」。
`qxribbon` 从 3.0 到 4.1.1 只动过一次 `.h`（一处 `enterEvent` 签名），`qxdock` 一次都没有。
这不是没做工作——是**工作全花在了地基上**。

### 1.2 一句话定位

> 4.2 不再动地基，**把三个"用户每天盯着"的库做深，并把项目本体剩下的半成品收口**。

主题名随 K25 定为「**三库做深、项目收口**」。

### 2.2 三个主库的细分

**`qxwindow`（0.1.2）—— API 面最窄，但它是 Qt6 唯一的无边框路径**
- 公开面只有 `WindowAgentBase` + `WindowAgentWidget`；`WindowStyleAgent` 条件编译且**默认关**。
- 无边框能力实际由 Win32 后端提供（`WM_NCCALCSIZE` + 保留 `WS_THICKFRAME | WS_CAPTION`），
  这正是 `RibbonAppWindow` 在 Windows+Qt6 上「启动即最大化」不受影响的原因（限制页已记）。
- 8 条 `TODO`/`FIXME` **全部是从 Qt 上游继承的**（`windowcontext_win.cpp` + `windowsystem_p.h`，
  写着 `### TODO:` / `### FIXME FIXME FIXME`，文件里还留着 Qt 源码的 GitHub 链接）；
  另有 2 条 `hack` 注释（`windowcontext_cocoa.mm:333`、`windowcontext_win.cpp:212`）。
  4.1 把「不认领从 Qt 继承的注释」写进了非目标，所以这 8 条**至今没有归宿**。
- 测试只有一个文件、8 个用例，且文件头**明文声明**「拖动、系统菜单、Win10 边框 workaround 测不了」。
- ⚠️ **`WindowStyleAgent` 是一个悬案**：它提供 `systemTheme() → {Unknown, Light, Dark, HighContrast}`，
  按平台有原生实现。但它 **默认不编译**（`option(QX_WINDOW_CONFIG_STYLE_AGENT "Config style agent" NO)`）、
  **全仓无人 `#include`**（只有它自己的目录）、**文档里一个字都没提**。
  而 `qxtheme` 已有自己的系统深浅色探测（`detectSystemDark()`，Qt 6.5+ 走 `QStyleHints::colorScheme()`，
  更早版本回退到调色板亮度，Qt 6.5+ 还接了 `colorSchemeChanged` 信号）——**功能重叠，但 qxtheme 的探针更完整**。

**`qxribbon`（0.10.2）—— 功能面最宽，但接口卫生与观感没被照顾**
- 26 个公开类；`res/` 下 6 套内置样式表 + 两套图标。
- ⚠️ **接口卫生问题**：`ribbongallery_p.h` 是 `_p.h`（私有实现头的命名约定）**却含导出类**
  `RibbonGalleryViewport`（`QX_RIBBON_EXPORT`）。约定与实际不一致。
- ⚠️ **`FramelessHelper` 的定位长期悬着**：它是 `qcanpool` 时期沿下来的类，
  **不在任何命名空间、没有导出宏**，被 `RibbonWindow` 无条件使用（无 `QT_VERSION` 分支）。
  它在 Windows+Qt5 走原生后端（`FRAMELESS_USE_NATIVE`），Qt6 走纯 Qt 模拟路径——
  而 Qt6 上「启动即最大化」的缺陷正落在这条模拟路径上。限制页已把**改法与代价**写清，
  但「到底改还是废弃」没有定论，于是它既不算欠账也不算能力。
- 2 条自写 `todo`（都是小写，`grep -i` 才扫得到）：`ribbonbutton.cpp:742`（字体改变需重算）、
  `ribbonstyleoption.h:26`（`@todo 后续开发通过配置文件定义 ribbon 的尺寸布局`）——后者其实是**用户可见的能力**。
- 12 个示例自 **2023-10-24** 起未动（4.0 只是把它们从 qmake 迁到 CMake）。

**`qxdock`（0.2.0）—— 改得最多，号却几乎没动过**
- 25 个公开类；含 X11 专用子树 `linux/`（仅在 `UNIX AND NOT APPLE AND NOT WASM` 编译，额外链 `Qt5::GuiPrivate` + `xcb`）。
- **3.x 以来它的 `.h` 改动最多**（4.1.0 到 4.1.1 之间唯一被修的行为缺陷也在它身上），
  但版本号停在 `0.2.0`，且 `CHANGELOG` 顶端挂着 `Unreleased` —— **账一直在记，就是没结算**。
- 已知待跟进（`TOPIC-known-issues.md`）：两处 `autoHideContainer()->toggleView()` 要**独立判断**
  能不能删（A2 删的是另一处，别照搬结论）。

### 2.4 一句话结论

**能力面不缺——缺的是「把已有能力收成可交付的形」**：
`qxwindow` 的 API 太窄且有一件悬案，`qxribbon` 的接口卫生和「延迟 resize」那条链没动，
`qxdock` 的账记了没结算，而项目本体的半成品（脚手架不同步、示例陈旧、文档口径错、没有发布流程）
恰好都落在**外部用户最先看到的地方**。
