# QtCanpool 4.4 任务规划（草稿 v4）

> 状态：规划中，未开工。本文件是 4.4 的权威任务分解。
> v4 订正（2026-10-12 晚）：**4.4 = 不破坏 API 的内部重构**；**4.5 = 功能升级（可能破坏 API）**。4.x 是长生命周期主版本（类 Qt 5.0→5.15 可承载十余个 minor），4.4/4.5 只是连续两步（K34 在 4.3-TASKS.md 列的 4.3/4.4/4.5 仅为方向示意，非 4.x 上限）；**5.0.0 仅当 Qt 5 移除条件（K30/K32）触发时才发生，不是计划中的近-term 目标**。
> 本文档从项目自身视角描述工程动作与验收标准（内部重构 / 功能升级），不展开实现出处对照。

## 一、战略订正

用户 2026-10-12 的系列指示综合：

1. 4.x 不能只做 hygiene，要实质升级；但升级节奏要稳，不能「每版只动一点 + 很快跨大版本」。
2. 三个核心库（qxribbon/qxdock/qxwindow）应做实质性改进，但不必一步到位、不必一次破坏。
3. **4.4 = 不破坏 API 的内部重构**（下游可放心升级）；**4.5 = 功能升级（可能破坏 API）**（下游需看 migration）。

由此：

- **4.4 = 不破坏 API 的内部重构**：三个核心库 + 四框架库的内部现代化（拆大文件、删死代码、抽公共、整理实现），**公开 `.h` 一律不动**；可标 `QT_DEPRECATED_X`（非破坏弃用）。
- **4.5 = 功能升级（可能破坏 API）**：把成熟实现的修复/特性功能性移植进来、做超出同类的能力；**允许移除/改签名**（K26：4.4 已标弃用的在 4.5 移除）。同时承担 K31 的 Qt 6.12 验证腿。
- **5.0.0 = 远景触发事件（非 4.x 的终点）**：移除 Qt 5（K30）。**4.x 本身是长生命周期主版本**，可像 Qt 5 那样承载 4.4/4.5/4.6/…/4.15+ 大量 minor；5.0.0 只在 Qt 5 移除条件（K30/K32）真正成熟时才发生，不要预设 4.x 只有少数几个 minor。

这同时消掉「薄」与「大跳」：4.4 是安全的内部现代化，4.5 是带能力增长的可能破坏升级，5.0.0 是库现代化后的小步。

## 二、与硬约束的关系

- **K26**（移除留 ≥1 版本缓冲）：4.4 只标弃用不移除；4.5 移除 4.4 已弃用的 API。
- **K30**（Qt 5 一路留到 5.0.0）：4.4/4.5 及之后**所有 4.x minor** 均保留 Qt5/6 双支持，不能顺势丢弃 Qt 5。**5.0.0 的时点由 K30/K32 条件决定，不按版本号排定**；4.x 是长生命周期主版本，minor 数量没有上限（参照 Qt 5.0→5.15）。
- **K31**（5.0.0 移除前必须有 Qt 6.12 验证腿）：4.5 加 6.12 腿，4.4 不加（CI 基线冻结）。
- **K11 / 附录 B**（minor = 契约变化）：4.4 因加弃用标记（契约新增信息，非破坏）→ minor；4.5 因可能移除/改签名 → minor（破坏需 migration 文档）。
- **K34**：4.x 靠库深化填满——本版把「深化」升级为「内部重构（4.4）+ 功能升级（4.5）」。

> **A 组硬约束（4.4 红线）**：公开 `.h` 签名 / 导出宏 / 枚举 **一律不动**；只改 `.cpp` 实现与私有 `_p.h`。
> 任何「想摘导出宏 / 想改签名」的冲动，记为 `QT_DEPRECATED_X` 弃用标记（非破坏）或推到 4.5。
> 每库小步提交、两侧（qt6/qt5）全量重建 0 warning + `ctest` 全过 + 桌面 offscreen 冒烟无回归。禁止一次性巨 PR。

> **A 组补强（规划缺口补充）**：
> - **验证策略（最关键缺口）**：A 组是大改实现、不动契约，最怕"行为悄悄变了"。B 组已明写"补测试"、D2 补 `tst_qxwindow_native`，**A 组反而不能只靠"ctest 全过 + 冒烟"**——这两库导出类近乎零覆盖（见 4.3-TASKS.md §二素材），"全过"近乎空转。故每库动手前先补**表征测试（characterization test）**锁定当前可观察行为，重构后保持全绿；把"无回归"从冒烟提升到可证。抽取出的纯函数（如 A3 的命中测试/几何）直接进单测。
> - **4.4 不依赖功能对比**：功能对比留到 4.5 规划时做（见 §四）。A 组重构目标按文件体积/内部复杂度排序即可，无需先建分歧表。
> - **执行顺序建议**：A3（`qxwindow`，4.0 已动、风险最低）→ A1（`qxribbon`）→ A2（`qxdock`，docking 引擎状态机最重）。每库独立小步、独立验收，不跨库打包。
> - **跨组协调**：① A1 与 D1 同落 `qxribbon`——建议 D1 的 5 条限制结清排在 A1 布局重构之后（或并行但各自独立提交），且 A1 不得借"内部重构"顺手改 K21 三出路记账；② A3 从 `windowcontext_win.cpp` 抽出的纯函数是 D2（`tst_qxwindow_native`）的自然测试对象，两者共用一套几何/命中测试单测。
> - **分层（T1/T2/T3）**：T1 为 4.4 承诺范围；T2/T3 视带宽，未消化的"不破坏 API 内部重构"顺延 4.5/4.6（4.x 长生命周期，不须一 minor 吞下）。A 组文件清单现已按实测行数补全，不再只列巨石文件。

## 四、4.5 = 功能升级（可能破坏 API，占位）

- 功能性移植成熟实现的修复/特性 + 做超出同类的能力（具体 4.5 规划时再做功能对比）。
- 移除 4.4 已标弃用的 API（K26 缓冲满足）；允许改签名。
- 承担 **K31 验证腿**：加 Qt 6.12 验证腿、跑满绿。**5.0.0 是否紧随 4.5 取决于 K30/K32 条件——未必紧接**，可能先有 4.6/4.7。

## 六、风险

- **A 组大改**：必须小步提交、每笔两侧验证，避免一次性巨改把 offscreen/真实显示都带崩。
- **4.4 硬红线**：公开 `.h` 不变（弃用标记除外）。任何移除都违反 K26 与用户「4.4 不破坏」的指令。
- **不要为「有产出」而制造破坏**：4.4 的承诺是「内部现代化」，不是「动 API」。
