# QtCanpool 4.4 任务规划（草稿 v4）

> 状态：**已开工**（2026-10-13 起；A3 `qxwindow` 内部重构 T1/T2 已提交，见 §七）。本文件是 4.4 的权威任务分解。
> v4 订正（2026-10-12 晚）：**4.4 = 不破坏 API 的内部重构**；**4.5 = 功能升级（可能破坏 API）**。4.x 是长生命周期主版本（类 Qt 5.0→5.15 可承载十余个 minor），4.4/4.5 只是连续两步（K34 在 4.3-TASKS.md 列的 4.3/4.4/4.5 仅为方向示意，非 4.x 上限）；**5.0.0 仅当 Qt 5 移除条件（K30/K32）触发时才发生，不是计划中的近-term 目标**。
> 本文档从项目自身视角描述工程动作与验收标准（内部重构 / 功能升级），不展开实现出处对照。

## 一、战略订正

用户 2026-10-12 的系列指示综合：

1. 4.x 不能只做 hygiene，要实质升级；但升级节奏要稳，不能「每版只动一点 + 很快跨大版本」。
2. 三个核心库（qxribbon/qxdock/qxwindow）应做实质性改进，但不必一步到位、不必一次破坏。
3. **4.4 = 不破坏 API 的内部重构**（下游可放心升级）；**4.5 = 功能升级（可能破坏 API）**（下游需看 migration）。

由此：

- **4.4 = 不破坏 API 的内部重构**：三个核心库 + 四框架库的内部现代化（拆大文件、删死代码、抽公共、整理实现），**公开 `.h` 一律不动**；可标 `QT_DEPRECATED_X`（非破坏弃用）。
- **4.5 = 功能升级（可能破坏 API）**：把成熟实现的修复/特性功能性移植进来、做超出同类的能力；**允许移除/改签名**（K26：4.4 已标弃用的在 4.5 移除）。同时承担 K31 的 Qt 6.12 验证腿。
- **5.0.0 = 远景触发事件（非 4.x 的终点）**：移除 Qt 5（K30）。**4.x 本身是长生命周期主版本**，可像 Qt 5 那样承载 4.4/4.5/4.6/…/4.15+ 大量 minor；5.0.0 只在 Qt 5 移除条件（K30/K32）真正成熟时才发生，不要预设 4.x 只有少数几个 minor。

这同时消掉「薄」与「大跳」：4.4 是安全的内部现代化，4.5 是带能力增长的可能破坏升级，5.0.0 是库现代化后的小步。

## 二、与硬约束的关系

- **K26**（移除留 ≥1 版本缓冲）：4.4 只标弃用不移除；4.5 移除 4.4 已弃用的 API。
- **K30**（Qt 5 一路留到 5.0.0）：4.4/4.5 及之后**所有 4.x minor** 均保留 Qt5/6 双支持，不能顺势丢弃 Qt 5。**5.0.0 的时点由 K30/K32 条件决定，不按版本号排定**；4.x 是长生命周期主版本，minor 数量没有上限（参照 Qt 5.0→5.15）。
- **K31**（5.0.0 移除前必须有 Qt 6.12 验证腿）：4.5 加 6.12 腿，4.4 不加（CI 基线冻结）。
- **K11 / 附录 B**（minor = 契约变化）：4.4 因加弃用标记（契约新增信息，非破坏）→ minor；4.5 因可能移除/改签名 → minor（破坏需 migration 文档）。
- **K34**：4.x 靠库深化填满——本版把「深化」升级为「内部重构（4.4）+ 功能升级（4.5）」。

**E3 的事实**：13 个 README（12 个 `qxribbon/*` + `qxapp/ribbonappempty`）是**单行且无结尾 `\n`**，

另外 11 个 `qxdock/*` 是 `i/lf`（有结尾 LF）。修法就是补一个 LF，零行为影响。

**F2 的证伪是这一组的核心。** 这两个宏**没有加 `#ifndef` 守卫**、就写在 `.cpp` 顶层，
所以它们**不是**"以后可能会打开的开关"，而是**已经定死的事实**；把没被选中的那支留着，
等于让每个读者自己去证一遍它不可达。两条 `#if/#else/#endif` 一并拆掉，
**净删 26 行、净增 0 行** —— 这就是"没有动到任何会跑的东西"的最干净证据。
（F1 的死槽与 F2 的两个宏**都是 `d98a3635`（"add qxwidget library"）从上游整包导入带进来的**，此后无人碰过。）

**F7 的边界**：`QStringLiteral(u"中文显示测试")` 这类**字符串字面量故意保留** ——
那一页演示的就是中文显示，翻掉它等于删掉被演示的东西。

**F4 为何只改名、不把宏改成函数**：`COST_START()` 声明的是**局部变量**，两处测量作用域**天然各自独立**；
改成成员会把它们变成**共享状态**。"今天两者恰好顺序执行"不是把它变成**前提**的理由
⇒ **有意的最小改动**，不是漏改。

**F6 的编译期反证**：改名后 `dockdemo` **立刻编译失败** —— 构造函数末尾那处 `restoreState()`
现在解析到基类的 `restoreState(const QByteArray&, int)`（无参 ⇒ 无匹配）。这正是
"**基类重载真的被还回来了**"的证明，补上漏改的那一处即通过。**先构建后提交**这条规矩在此直接抓到了一个真错。

**否掉的项（各有理由，不是没查）**：

- **`appshell` / `ideshell` 的 Layout 组（约 16 行几乎逐字相同）不抽**：只有 2 个调用点，
  而 **demo 的价值就在于每个 demo 能独立从头读到尾**。`examples` 那次能抽，是因为 4 份 `main.cpp`
  **本来就是逐字节相同的同一份**、抽完仍是"每个样本自足"；把这两个 demo 的共同片段抽出去会
  **反过来把两个 demo 绑在一起**。要抽的正确位置是 `QxAppShell` 的**新公开 API** ⇒ 那是 **4.5（功能升级）**的事。
- **BOM 一律不动**：全仓 **57 个文件**带 UTF-8 BOM（`qxribbon` 50 + `qxwindow` 1 + `ribbondemo` 4 + css 2）。
  ⚠️ **BOM 是承重的**：MSVC 对**无 BOM** 的源文件按**系统 ANSI 代码页**解码，而 `ribbondemo/mainwindow.cpp`
  里有 `u"中文显示测试"` 这样的字符串字面量 —— 去掉 BOM 会让它在 MSVC 上变成乱码，**行为真的会变**。
  纯 ASCII 的那些（如 `mainwindow.h`）去掉无害，但收益为零 ⇒ **只记录，不动**。
- **许可证头不补**：仓库 **364 个 `.h`/`.cpp` 里有 122 个没有 SPDX 头**（多数 `tests/` 与不少 `examples/`）
  ⇒ **这不是全仓约定**，单给 `demos` 补不是"对齐"而是"半棵树"的改动。
- **`res/*.svg` 与 `ribbondemo.rc` 的 `i/none w/none` 不动**：63 个单行 svg + 1 个 `.rc` 没有结尾换行，
  与 E3 的 README **同类**，但 E3 的 13 个是**人读的文本**，这些是**单行数据文件**，
  补换行改变文件字节而收益为零 ⇒ **不动**。
- **`#ifndef QT_NO_DEBUG_OUTPUT fflush(stdout); #endif` 不动**：看着像写错（这个宏与 stdout 刷新无关），
  但它是**承重的** —— stdout 重定向到文件时是**全缓冲**，而 `QtFatalMsg` 分支会 `abort()`，
  没有这个 flush，**最后一行就丢了**。

**R12 · 已自动隐藏的 widget 再被 "Pin" 会 SIGSEGV（已修，`d9cdbdea`）**

`DockWidget::setAutoHide(bool, area = Qx::DockSideBarNone, int tabIndex = -1)` 与
`DockPanel::setAutoHide(...)` 是同一处逻辑的两份拷贝，**两边都只在一半路径上把 `None` 换算成真实侧边**：

| 路径 | 是否把 `None` 换算掉 |
| :--- | :--- |
| `!isAutoHide()` ⇒ `createAndSetupAutoHideContainer(location, …)` | **是**（`(None) ? calculateSideBarArea() : area`） |
| `isAutoHide()` ⇒ `moveToNewSideBarArea(area)` | **否** ← 缺陷 |

`DockSideBarArea` 只有 `Top/Left/Right/Bottom/None` 五个值，而
`DockContainer::autoHideSideBar(area)` 就是 `m_sideTabBarWidgets[area]`，那张 map **只对四条边建过条目**
⇒ 传 `None` 取回 **nullptr**，`DockAutoHideContainer::moveToNewSideBarArea()` 随即
`sideBar->addAutoHideWidget(this, tabIndex)`。
顶部那道 `if (enable == isAutoHide() && area == autoHideArea()) return;` 也挡不住：`None != Left`。

**可达入口**：`DockTab::contextMenuEvent()` 的 **"Pin"** 项（`docktab.cpp:674`）
⇒ `DockTab::autoHideDockWidget()` ⇒ `d->m_dockWidget->setAutoHide(true)`，**area 走默认 `None`**；
而它的 `setEnabled(isPinnable)` 只看 `DockWidgetPinnable` 特性、**不看是否已隐藏**
⇒ 右键一个**已经钉住**的 widget 点 "Pin" 即命中。

**证明手法（同 R8：先跑出崩溃再修）**：`tst_DockWidget::repinAlreadyPinned()` 与
`repinPanelAlreadyPinned()`（`tests/qxdock/auto/tst_dockwidget.cpp`）在旧代码上各自以 **RC=139（SIGSEGV）**
结束，且 `-o file,txt` 报告里**前面 4 个既有用例全部 PASS** ⇒ 崩的正是新用例，不是环境问题。
修一处跑一次：`repinAlreadyPinned` 转绿之后，进程才死在 `repinPanelAlreadyPinned`
⇒ **两个入口各自独立成立**，不是同一个崩溃的两种写法。

**修法**：两条路径都补「`None` ⇒ 用**当前**所在侧边」（而不是 `calculateSideBarArea()`）——对"已经钉住"的
widget，`setAutoHide(true)` 的语义就是"留在原处"；`moveToNewSideBarArea()` 自己还会在
`area == sideBarArea()` 时早退。⇒ **未动任何带导出宏的头**（`dockwidget.h` / `dockpanel.h` 只改了 `.cpp`）。

⚠️ 顺带记下**没动的一处**：`setAutoHide` 收着 `tabIndex` 却在那条分支上丢掉（`moveToNewSideBarArea(area)`
用默认 `-1`）。`-1` 在 `DockSideBar::insertTab()` 里是"追加"的正式哨兵，且当前**没有任何调用方**在那条路径上

属"为改而改"，不动。

### B 组 · 四框架库公开 API 面盘点（2026-10-14）

> 4.4 B 组 = 「公开 API 面评估（类似 4.3 A5）+ 补测试；该弃用的标 `QT_DEPRECATED_X`（非破坏）」。
> 四库各一笔：`fd1bf008`（qxcore）· `664907e8`（qxtheme）· `c9c0d384`（qxplugin）· `08b0025c`（qxapp）。

> ⚠️ 唯一例外是 **R15**（B3 的 `tst_qxplugin` 在 Qt 5 腿上编译不过、跑起来也读不到实参，见 §七）——
> 它是**测试自身的跨版本缺陷**，不改库代码，故不改变本句结论。
> 判据沿用 A5 原样：每个公开成员问两件事 —— **有没有人调用**、**有没有测试覆盖**。

**结论一 · 缺口的形状在四库里是同一个：访问器有人测，命令没人测。**
`qxcore` 缺的是 `QxLogger::init()` 的失败路径和 `write()` 的第二个重载、`QxSettings` 的版本键；
`qxtheme` 缺的是 `apply()` 与 `refreshSystemTheme()` 两个**公开 slot**；
`qxplugin` 缺的是 manager 的两个**信号**和 `extensionsInitialized()` 的**顺序契约**。
访问器（getter/setter）一眼看得出"读回刚才写的东西"，常被顺手覆盖；
而**命令**（做事、发信号、定顺序）恰恰是只有它们才承载的契约。
这与 A5 的结论二同型（那里零覆盖的也正是 `centralize()`/`raise()`/`showSystemMenu()` 三条**命令**）。
⇒ **同类盘点先看命令与信号，再看访问器。**

**结论二 · 「本仓没人调」不等于「没用」；四库都没有该弃用的项 —— 这是结论，不是漏做。**
弃用的正当理由是「**有替代品**」（同一件事存在更好或更少的写法），不是「本仓没人用」。
四库的公开面都是自洽的：`QxSettings`/`QxPluginManager` 的 set/get 成对，`QxTabBar`/`QxTabWidget`
是各自独立的 widget，`QxLogger` 是给使用者的日志设施。按 A5 的判据，唯一"差一点"的是
`QxAppShell::timeoutMs` 这类只有 getter/setter 的小成员 —— 它们**不是冗余**，只是没测，
⇒ 归「补测试」而非「标弃用」。
**`QT_DEPRECATED_X` 在 4.4 四库里一次都没用上**；闸门本身仍由 `tests/deprecated/` 两条用例把着
（4.3 A8 所建，本轮复核未动）。

**结论三 · 最大的缺口不在单个成员，而在整类：`qxapp` 有 7 个导出类零覆盖、零消费。** 见 B4。

#### B3 · `qxplugin` 公开 API 面评估（`c9c0d384`）

公开面 = 5 个类（`QxPlugin`/`QxPluginContext`/`QxPluginManager`/`QxPluginSpec`/`QxObjectPool`），~1670 行。
测试原已有 17 条，是全四库里最厚的（依赖排序、级联隔离、循环检测、版本拒绝全覆盖）。
补了 **4 处**，全是"库外调用方真正会依赖的东西"：

- **`pluginInitialized()` / `pluginFailed()` 两个信号零测试** —— 而 `QxObjectPool` 的两个信号各有一条。
  不对称就是缺口的形状。它们是一个 manager UI **唯一**能连的两样东西，所以断言的是**它们报什么**：
  每个启动的插件恰好一次、每个没启动的恰好一次，失败那条的 reason 与 `spec()->error()` 逐字相同，
  以及**被默认跳过的插件一次都不发**（"没跑"和"出错了"是两个答案，只有后者该被通知）。
- **`extensionsInitialized()` 的顺序契约** —— 它是**第二遍**遍历整个集合，不是逐插件回调，
  这正是它可以用来发布"依赖所有 peer 都就绪"的东西的原因。顺序因此是契约的一部分，
  且它是**初始化顺序**、而不是 Qt Creator 承诺的反序。新增 `OrderPlugin`（记录 init/extend/stop）
  让顺序可断言而非可假设。
- **`shutdownReversesOrder()` 加强** —— 原来只断言最终 state，那个断言**任何顺序都满足**；
  现在断言它的名字所声称的顺序。
- **4 个 getter**（`pluginPaths()`/`requiredInterfaceVersion()`/`hostVersion()`/`hasHostVersion()`）——
  它们**连库内都不读**（`loadPlugins()` 直接读 `d->m_hostVersion` 等成员），是纯外部 API。
  断言含 `requiredInterfaceVersion()` 的文档默认值 1，以及 `hasHostVersion()` 如何把
  "接受任何版本"与"接受到此为止"区分开。

### R15 · Qt 5 上 `tst_qxplugin` 编译不过、跑起来也读不到实参（2026-10-14，已修 `8627ceae`）

> **属 B3 补记**，不是新工作：B3（`c9c0d384`）新增的 `signalsReportTheRun()` 在 **Qt 5.15 腿**上**从未通过**。
> 定位依据：CI 上 `226a7a90`（本轮改动**之前**）该腿已是 failure，而 `15249889` 是 success
> ⇒ **肇因是 `c9c0d384` 自身**。B 组原文"无 `R<n>`"说的是**没有需要改库代码的发现**，
> 而这一条是**测试自身的跨版本缺陷**，故补记为 R15（编号不复用）。

**同一处代码，两个独立故障。**

1. **编译期**（Qt 5 必现、Qt 6 不现）：`QVariant::value<QxPluginSpec *>()` 要求该类型是**已声明的 metatype**。
   `QxPluginSpec` 不是 `QObject`，Qt 5 没有可推断的依据 ⇒ `qmetatype.h:1916`
   `static assertion failed: Type is not registered, please use the Q_DECLARE_METATYPE`，
   并连带 `qmetatype.h:1776: 'qt_metatype_id' is not a member of 'QMetaTypeId<QxPlugin::QxPluginSpec*>'`。
   Qt 6 不现：moc 为**每个见过的参数类型**生成 `QMetaType` 接口。
2. **运行期**（只加 `Q_DECLARE_METATYPE` 仍 FAIL）：`QSignalSpy` **不按类型找参数，按名字找** ——
   它拿 `QMetaObject` 里 moc 写下的参数类型名去查。信号声明在命名空间内
   （`qxpluginmanager.h:102` 写作 `QxPluginSpec *spec`），moc 写下的名字就是**未限定的 `QxPluginSpec*`**；
   而 `Q_DECLARE_METATYPE` 按**交给它的拼写**注册（`qRegisterMetaType<T>(#TYPE, …)` + `normalizedType`）
   ⇒ 写 `Q_DECLARE_METATYPE(QxPlugin::QxPluginSpec *)` 会注册成 `QxPlugin::QxPluginSpec*`，**永不匹配**，
   spy 读不到实参，于是 `QCOMPARE(…, okSpec)` 比出两个不同指针。
   且 `Q_DECLARE_METATYPE` 是**惰性注册**（首次索取 metatype id 时才注册），而"首次索取"正是
   `QSignalSpy` 构造本身 —— **太晚**。

**修法**（两处都必要，且都不动库）：声明改为**与 moc 同拼写**的 `Q_DECLARE_METATYPE(QxPluginSpec *)`；
在 `signalsReportTheRun()` 里、两个 spy **之前**显式 `qRegisterMetaType<QxPluginSpec *>();`，
用 `#if QT_VERSION < QT_VERSION_CHECK(6, 0, 0)` 圈住（Qt 6 从 meta-object 直接读类型，不需要）。
两处都写在测试里而不是 `qxpluginspec.h`：**是测试在过 `QVariant`**，且该头本版冻结。

⚠️ **症状会误导**：只加 `Q_DECLARE_METATYPE` 后**编译过了**，运行期却只报
`Compared pointers are not the same`，看着像"库发错了信号"；真相在同一份输出里的两条
`QWARN : … QSignalSpy: Unable to handle parameter 'spec' of type 'QxPluginSpec*' … use qRegisterMetaType`。
⇒ **运行期失败先读完 `QWARN` 再怀疑库。**

**验证**：`cmake --build --preset qt5` 0 error → `QT_QPA_PLATFORM=offscreen ctest --preset qt5`
**14/14**（此前 13/14）；Qt 6 同样 **14/14**（该用例在 Qt 6 上本来就过，改动不回归）；
`clang-format 21.1.8` 该文件通过。
