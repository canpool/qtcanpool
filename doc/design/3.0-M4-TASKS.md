## 二、M4.1 SDK 可消费性（本次执行）

### 2.1 背景

验收标准第 6 条要求"产出可被 `find_package` 消费的 **SDK 包**"。工程里其实**早就有**这套机制：
`add_qtc_library` 把目标 `install(TARGETS ... EXPORT QtCanpool)`，`src/CMakeLists.txt` 再
`install(EXPORT QtCanpool ... NAMESPACE QtCanpool::)` 并生成 `QtCanpoolConfig.cmake`。
但**从来没有人从外部消费过它**——于是两个缺陷一直躺着：

| 缺陷                                              | 后果                                                             |
| :---------------------------------------------- | :------------------------------------------------------------- |
| `QtCanpoolConfig.cmake` 里 `find_dependency` 要求 `Concurrent` 与 `Core5Compat` | 二者全树都没用到（随 Qt Creator 搬来的遗留）。`Core5Compat` 在 **Qt 5.15 根本不存在**，包直接不可用；Qt 6.8 下也要求装了该可选模块才能用 |
| `qxribbon_global.h` 不在 CMake 的 `SOURCES` 里        | **从未被安装**。`qxdock` 用 `file(GLOB *.h)` 把全部头收进去，`qxribbon` 是手写枚举，漏了它就等于漏了每个公开头都要包含的宏头 |

> 为什么之前没发现：仓库根目录的构建只**产出**这个包，从不**消费**它。任何一次 `find_package(QtCanpool)` 都会立刻暴露。

### 2.2 修复

- `src/CMakeLists.txt`：`find_dependency(Qt5 ... COMPONENTS Core Gui Widgets REQUIRED)`——只保留导出目标**真正**引用到的三个组件（`Qt6::Core/Gui/Widgets`；`Svg` 只出现在从未被链接的 `OptionalSvg` 上）。顺带把恒为真的 `if (NOT TARGET QtCanpool::Core)` 改成真实目标名 `QtCanpool::qxcore`。
- `src/libs/qxribbon/CMakeLists.txt`：`SOURCES` 补上 `qxribbon_global.h` 与 `ribbongallery_p.h`（后者同样是手写枚举时漏掉的 `_p.h`，与同文件里其它条目的写法一致）。

### 2.3 把"可消费"变成门禁

新增 `projects/consume/`：一个真正的下游工程，**只**做 `find_package(QtCanpool REQUIRED)` + `target_link_libraries(... QtCanpool::qxapp)`，
不引用源码树。它在 CI 的一个构建腿（`ubuntu-latest / Qt 6.8.1`）上执行完整往返：

```bash
cmake --install build --config Release --prefix "$RUNNER_TEMP/sdk"
cmake --install build --config Release --prefix "$RUNNER_TEMP/sdk" --component Devel
export CMAKE_PREFIX_PATH="$RUNNER_TEMP/sdk:$CMAKE_PREFIX_PATH"
cmake -S projects/consume -B "$RUNNER_TEMP/consume" -DCMAKE_BUILD_TYPE=Release
cmake --build "$RUNNER_TEMP/consume" --parallel
```

> ⚠️ 头文件与 `QtCanpoolConfig.cmake` 属于 **`Devel` 组件**且带 `EXCLUDE_FROM_ALL`，**必须显式 `--component Devel`**，否则前缀里只有可执行文件与运行库。

### 2.4 验证（本机：Qt 6.8.3 + MinGW GCC 13.1.0 + CMake 4.2.1）

- ✅ **配置**：`cmake --install`（默认组件）+ `--component Devel` → 前缀含 `lib/cmake/QtCanpool/{QtCanpoolConfig,QtCanpoolTargets}.cmake`、`include/qtproject/src/libs/**`、`bin/libqx*.dll`
- ✅ **消费**：`find_package` 配置 `CFG=0`、编译链接 `BUILD=0`，产出 `qxconsume.exe`
- ✅ **运行**：`QT_QPA_PLATFORM=offscreen` 下 `RUN_RC=0`（`pageCount()==2`）
- ✅ **无回归**：桌面构建 `BUILD=0`、`ctest` **7/7**
- ✅ **clang-format**：`projects/consume/main.cpp` 通过

## 三、M4.2 版本对齐（已完成）

- `cmake/QtCanpoolBranding.cmake`：`QTPROJECT_VERSION` / `QTPROJECT_DISPLAY_VERSION` → `3.0.0`。
- ⚠️ **`QTPROJECT_COMPAT_VERSION` 是"兼容版本"（库的 SONAME 基）**，与展示版本不同义：它给的是"二进制向后兼容到哪个版本"。3.0 明确**不保证**二进制兼容（决策 K6），故它跟随到 `3.0.0`，表示与自身对齐，而不是声称兼容 2.x。
- 各库自身的 `QX_*_VERSION` 宏（`qxcore`/`qxtheme` 为 `0.1.0`，`qxribbon` `0.10.1`，`qxdock` `0.2.0`，`qxwindow` `0.1.2`，`qcanpool` `2.0.2`）**保持不动**：它们是各库独立的演进号，与项目版本解耦，`CHANGELOG` 的既有条目也是这么记的。
- ✅ 验证：改动后 `cmake` 配置 `CFG_RC=0`、构建 `BUILD_RC=0`。

## 五、M4.4 包管理描述（已完成）

路线图方向 B5 要求"提供 vcpkg / Conan 描述，降低接入门槛"。本次给出**最小可用骨架**而不是完整 port：

| 文件                     | 说明                                                        |
| :--------------------- | :-------------------------------------------------------- |
| `ports/qtcanpool/vcpkg.json`   | vcpkg port 清单：名字、版本 `3.0.0`、依赖 `qtbase`                  |
| `ports/qtcanpool/portfile.cmake` | 从源码构建并安装，暴露 `QtCanpool` 的 CMake 包给下游                 |
| `conanfile.py`         | Conan 2 配方骨架：`CMakeDeps`/`CMakeToolchain`，导出 `QtCanpoolConfig.cmake` |
| `ports/README.md`      | 说明"骨架 + 未经 CI 验证"的状态与 `Devel` 组件的注意点                     |

> ⚠️ 这两者都是**骨架**：没有 CI 环境验证（vcpkg 的 `qtbase` 构建代价以小时计），因此文档里明确标注"社区可贡献、作者未在 CI 验证"，避免给出"已完整支持"的错误信号。这与路线图风险表"先出最简 port，社区可贡献"一致。
>
> 两者都已处理 `Devel` 组件陷阱：vcpkg 在 `portfile.cmake` 里对每个配置显式执行 `cmake --install --component Devel`；Conan 用 `cmake.install(component="Devel")`（普通安装会漏掉公开头文件与 `QtCanpoolConfig.cmake`）。
