### 1.1 不在本版范围

| 候选                  | 为何不做                                                       |
| :------------------ | :--------------------------------------------------------- |
| 出厂 / 内置预设（"恢复默认布局"） | 框架不知道应用何时算「建完」，捕获时机不可靠；应用自己起一个名为 `Default` 的工作区即可，且语义更清楚  |
| 每个工作区带窗口几何（位置 / 大小）  | 几何属于**窗口**、不属于**工作区**：切换面板排列却把窗口搬走 / 改尺寸，在多显示器和最大化场景下是惊吓 |
| 最近文件 / 最近打开          | 真实需求，但不属于方向 D（让 `QxAppShell` 能承重），留给后续版本单独评估              |
| 多窗口工作区（每个主窗口一套）      | 单个 `QxAppShell` 已经是当前模型的边界，多窗口需要另立所有权模型                   |
| 进度任务的取消 / 任务栈 / 并发进度 | 状态栏只表达「正在做、做到哪」；取消与并发是任务系统的事，不是状态栏的事                      |

## 二、D1 · 工作区 / 布局预设（`qxapp`）

### 2.1 现状与缺口

`QxAppShell` 已有 `saveLayout()` / `restoreLayout()`：几何、`QMainWindow::saveState()`、
qxdock 的 `DockWindow::saveState()`、当前页 id，一起存在 `ui` 组下，关闭时自动存一次。
它能让应用「下次打开长回上次的样子」，但**只有一份**，且用户没有名字可以叫它：

- 想留两套排列（写代码一套、看输出一套），只能靠手动覆盖那一份；
- 想「回到我刚才那套」，得先记住自己没动过；
- 菜单里「视图 ▸ 布局」永远只有一个条目。

缺口不是「不能持久化」，而是**没有命名**。命名是叠加便利性，不是缺口——这正是 K12 把它推到 3.3 的原因。

### 2.2 设计：`QxWorkspaceManager`

新类 `QxApp::QxWorkspaceManager : QObject`（`qxworkspace.{h,_p.h,cpp}`），与 3.2 的
`QxToastManager` 同一形态：**一个管事的 QObject + 外壳上的一个惰性访问器**，外壳本身不新增状态。

```cpp
QxWorkspaceManager *manager = shell.workspaceManager();   // 首次使用时创建
manager->saveWorkspace(QStringLiteral("Writing"));
manager->applyWorkspace(QStringLiteral("Review"));
```

外壳上的四个入口（均一行转发，不复制逻辑）：

| 方法                     | 说明                              |
| :--------------------- | :------------------------------ |
| `workspaceManager()`   | 惰性创建，外壳拥有；与 `toastManager()` 对称  |
| `workspaceNames()`     | 已存工作区的名字，按保存顺序                  |
| `saveWorkspace(name)`  | 以 `name` 存下当前排列；同名覆盖            |
| `applyWorkspace(name)` | 切到 `name`；未知名字返回 `false`         |

管理器自身的完整 API：

```cpp
QStringList workspaceNames() const;
int count() const;
bool contains(const QString &name) const;

bool saveWorkspace(const QString &name);      // 空名 / 纯空白 → false
bool applyWorkspace(const QString &name);     // 未知 → false
bool removeWorkspace(const QString &name);
bool renameWorkspace(const QString &from, const QString &to);
void clearWorkspaces();                       // 只删工作区，不动 ui 组的其他键

QString currentWorkspace() const;             // 最后一次 applied / saved 的名字，空 = 无
```

信号：`workspaceSaved(name)` / `workspaceApplied(name)` / `workspaceRemoved(name)` /
`currentWorkspaceChanged(name)`。改名发一次 `workspaceRemoved(old)` + 一次
`workspaceSaved(new)`（不另设 `renamed`，否则每个消费者都要写两个分支）。

### 2.3 一个工作区存什么

| 内容          | 存   | 理由                                     |
| :---------- | :- | :------------------------------------- |
| `dockState` | ✅  | 面板排列就是工作区的本体                           |
| `currentPage` | ✅ | 「写代码」和「看输出」往往是不同页，页属于工作区               |
| `windowGeometry`、`windowState` | ❌ | 属窗口不属工作区（见 1.1）；仍由 `saveLayout()` 单独管 |

存储布局（`QxSettings`，与 `saveLayout()` 同一个对象、同一个 `ui` 组）：

```
ui/workspaceNames            QStringList   保存顺序，枚举与菜单顺序的唯一来源
ui/currentWorkspace          QString       最后一次 applied / saved
ui/workspace/<name>/dockState      QByteArray
ui/workspace/<name>/currentPage    QString
```

- **名字直接进路径**，另用 `workspaceNames` 记顺序——因为 `QSettings::childGroups()` 的
  顺序由后端决定（ini 与注册表不同），而菜单顺序必须是保存顺序。
- 名字校验：trim 后非空；含 `/` 只会被 `QSettings` 当成分层路径，由于读取一律经由
  `workspaceNames`，分层无害；同名覆盖、大小写敏感（`QSettings` 键本身如此）。
- `removeWorkspace()` 后若它正是 `currentWorkspace()`，当前名清空并广播。

### 2.4 与 `saveLayout()` 的关系（这一段要写进文档页）

> `saveLayout()` 存的就是**那一份没有名字的工作区**，只不过它还顺带存了几何。
> 命名工作区是同一件事的「多份 + 可点名」版本。

因此两者不冲突、也不互相调用：关闭窗口仍自动存 `ui/*`，切换工作区只读写
`ui/workspace/*`。**启动时不自动套用上次的工作区**——要不要套、套哪个是应用的决定，
框架只保证 `currentWorkspace()` 被记住且可读。

### 2.5 验收

- `tests/qxapp/auto/tst_qxworkspace.cpp`（经 `tst_*.cpp` 通配自动进 `tst_qxapp`）：
  空管理器、保存与枚举、同名覆盖、应用后排列真的变回来（**改一个 dock 的位置 → apply → 位置回来**）、
  未知名字 / 空名字、`rename` / `remove` / `clear`、`currentWorkspace` 与信号、
  两个外壳共用一个 settings 文件（工作区是存在文件里的，不是存在对象里的）。
- 与 `QxAppShell` 的接线：`shell.workspaceManager()` 多次调用返回同一个对象。

## 三、D2 · 状态栏进度指示（`qxapp`）

### 3.1 现状与缺口

状态栏已有一行消息（`setStatusMessage()`）和一个忙指示（`setBusy()`）：
那个 `QProgressBar` 是 `setRange(0, 0)` 的走马灯，只能说「在忙」，说不出「做到 40%」。
真实应用里，「复制 128 个文件，第 57 个」这类进度几乎都要自己塞一个进度条进状态栏——
这就是 K10 说的「反复手写」。

### 3.2 设计：给同一个进度条加一种确定模式

不新增部件：忙指示与百分比进度**共用那一个 `QProgressBar`**，因为它们不会同时对用户有意义。

```cpp
void setProgressRange(int minimum, int maximum);   // 默认 0..100
int  progressMinimum() const;
int  progressMaximum() const;
void setProgress(int value);        // 夹到范围内；隐式显示并把忙指示关掉
int  progress() const;
void clearProgress();               // 隐藏 + 复位到 minimum
bool isProgressVisible() const;
```

语义（写进头注释）：

- **忙与进度互斥，最后一次调用生效**：`setProgress(v)` 关掉忙，`setBusy(true)` 关掉进度。
- `setProgress()` **隐式显示**（设了进度就等于想让人看见）；`clearProgress()` 是唯一的收尾动作。
- 确定模式下显示百分比文字，走马灯下不显示——`QProgressBar` 在 `min==max==0` 时本来也无字可显。
- 越界值夹到范围内，不报错（与 `QProgressBar` 自身行为一致）。
- 消息行不受影响：消息是「在做什么」，进度是「做到哪」，两者可以同时有内容。

`isBusy()` / `setBusy()` 语义不变。

### 3.3 不做

- 不做任务栈、取消按钮、暂停、并发进度（见 1.1）。
- 不引入 `QFutureWatcher` / `QtConcurrent` 依赖：`qxapp` 不该替应用决定用什么跑后台。
- 不做「进度 + 预计剩余时间」——框架没有任务的进度速率，算不出来。

### 3.4 验收

- `tst_qxapp.cpp` 的 `tst_QxAppShell::statusBar()` 扩写：默认隐藏、`setProgress(40)` 后
  可见且值为 40、`setProgressRange(0, 1000)` 后夹取、`setBusy(true)` 与 `setProgress()` 互相顶掉、
  `clearProgress()` 后隐藏且复位、消息行不受影响。
- 两套 Qt preset 均 0 warning。

## 四、D3 · demo 接线

`demos/qxapp/appshell` 是 `QxAppShell` 的样板，两项能力在那里有可点的入口才叫「可用」：

- 功能区 **View ▸ Workspace**：`Save As…`（`QInputDialog` 取名）、一个列出已存工作区的菜单
  （点了就 `applyWorkspace()`）、`Manage…` 里可删除；
- 状态栏：一个 `Run` 按钮走 0 → 100 的假进度（用 `QTimer`），中途 `setStatusMessage()`
  配合演示「消息 + 进度并存」。

> **不外扩到 `projects/template`**：模板是「新应用的起点」，3.2 已经为它接好了三件必备能力，
> 再加工作区菜单会让它不再是一个干净的起点。样板归 demo，起点归模板。

## 八、风险与注意

- **AUTOMOC 缓存陷阱**：新增 `tst_*.cpp` 不会被旧的 `tst_qxapp_autogen*` 扫到
  （3.2 踩过），落地时先删 `build/<preset>/tests/tst_qxapp_autogen` 与
  `tests/CMakeFiles/tst_qxapp_autogen.dir` 再重配置。
- **dock 状态恢复可能依赖窗口存在**：`DockWindow::restoreState()` 在部件没有
  platform window 时可能不完整；工作区测试要 `shell.show()`（3.2 的 toast 测试已证明
  没有窗口就收不到 `QEvent::Resize`）。
- **进度条宽度固定 140px**：确定模式要显示百分比文字，确认文字在该宽度下不被截断。
- **新文件一律 LF**（`qxapp` 源码与 `tests/` 都是 LF，`CHANGELOG` 是 CRLF）。
