## 一、背景与现状（2026-10-10 勘察）

M5（3.1）/ M6（3.2）/ M6b（3.3）已把 M7 的前置条件全部兑现：A（API 干净，`qcanpool` 已删）、
B（覆盖率/clang-tidy/消毒器/六库皆有测试）、D（`QxSettings`/`QxTranslator`/Toast/属性编辑器/
设置对话框/工作区/状态栏进度）均已落地。**4.0 不再是"在沙地上盖楼"。**

### 1.1 构建侧的 machinery 早已就位

`cmake/QtCanpoolAPI.cmake` 里的 `add_qtc_plugin()` 直接继承自 Qt Creator，已经具备：

- 从 `<name>.json.in` 生成 `plugin.json`（支持 `$$QTPROJECT_VERSION`、`$$dependencyList` 等占位符）；
- `PLUGIN_DEPENDS` / `PLUGIN_RECOMMENDS` / `PLUGIN_TEST_DEPENDS` 三类依赖，**自动写出 `Dependencies` 数组**
  （required / optional / test）；
- 动态库与**静态构建**两种形态（`QTC_STATIC_BUILD` 下自动加 `QT_STATICPLUGIN` 与静态导出宏）——
  这一点对 WASM（本仓已要求 `QTC_STATIC_BUILD=ON`）是硬需求；
- 输出到并安装到 `IDE_PLUGIN_PATH`；
- `QTC_PLUGIN_CLASS_NAME`（默认 `<Target>Plugin`）写到 target 属性上，供将来按类名定位入口；
- `src/plugins/CMakeLists.txt` 里留有 Level 0~8 的**分层注释**，即"上层插件只能依赖下层"的约定。

**结论：缺的不是构建，是运行时。** 没有任何 C++ 侧的东西去读这些 `plugin.json`、做拓扑排序、
按序实例化、或在某个插件炸掉时保住应用。4.0 的工作量全部集中在运行时这一层。

### 1.3 与命名讨论的关系

上一轮讨论过 `QxAppShell` 的名字（K14）。**它对 4.0 是阻塞性的**：如果插件一律直接依赖窗口类，
那么改名会波及所有插件；如果插件依赖一个薄的接口层，改名的波及面就被封住了。因此本清单把「插件的
宿主上下文」放在 B1 之前决定。

## 二、目标与非目标

### 目标

1. 插件**独立编译**、按元数据**按序加载**、依赖**可解析**、失败**可隔离**且有诊断；
2. `src/modules` 长出**可选业务模块**的样板（外：`qxapp` 不依赖它们）；
3. 存在一个**由模块拼装**、可运行的 IDE 式样板应用；
4. 插件接口有**版本化约定**与迁移说明（跟着 K6：不承诺二进制兼容，但必须能诊断）。

### 非目标（本版明确不做）

- **不做热插拔 / 运行时安装插件**：启用或停用后**重启生效**（Qt Creator 亦如此）；
- **不做插件市场、下载、自动更新**；
- **不做脚本化插件**（Python / Lua / QML 插件），只做 C++ 插件；
- **不做进程隔离 / 沙盒**：`QPluginLoader` 是同进程加载，插件崩溃会连带宿主——这是已知取舍，写进文档；
- **不做异步生命周期**：首版只有 `initialize()` → `extensionsInitialized()` → 关闭三步，
  Qt Creator 那种 `delayedInitialize()` / 异步关闭不做；
- **不恢复已删除的东西**：`qcanpool`、legacy 控件、qmake 都不回来（见 K13）。

### K18 · 分支模型（2026-10-10 定）

`master` 之前停在 2.x（`afeac4d6`），3.x 的开发一直在 `release-3.x` 上。4.0 切回 master 作主线：

- **`master` 是 `release-3.x` 的祖先**（`git merge-base` 正好等于 master 尖端），因此可以直接
  `--ff-only` 快进到 4.0 计划的提交，**不需要 force push**；
- **旧内容零丢失**：旧 `master` 与 `release-2.x` 是同一 commit，2.x 的完整历史由 `release-2.x`
  与 1.x/2.x 的 tag 保留；
- **CI 不用改触发条件**：`ci.yml` / `pages.yml` 本来就监听 `[ master, develop, 'release-*' ]`；
- ⚠️ **但站点要改**：`pages.yml` 的 `deploy` 任务原本限定 `refs/heads/release-*`
  （注释写明了「只有release 分支拥有站点」），master 成为主线后若不放开，**文档站会停更**。
  已改为 `master` 与 `release-*` 都能发布；
- **不再新建 `release-4.x`**：两个开发分支并存极易让人提交错地方。将来 4.0 若需要维护分支，
  从 `4.0.0` 的 tag 处再开。

### K14 的四个选项（一次性对比）

> **状态（2026-10-10）**：K14 本身仍**未定案**，但**已不再是阻塞项**。
> 组合做法按下面的"建议"执行了 —— `QxPluginContext` 已在 B1 引入、B5 又给它接上了对象池，
> 插件只面向 `QxPluginContext` 编程，宿主叫什么名字**对插件完全不可见**（连注释里都不许出现 `QxAppShell`）。
> 将来定案时只需一次性替换 `QxAppShell` 的引用（demo + 测试 + 脚手架模板），插件一行不用改。

| 选项 | 形态 | 代价 |
| :--- | :--- | :--- |
| 保留 `QxAppShell` | 不动 | 名字不带形态、不含粒度（详见 2026-10-10 讨论） |
| `QxRibbonMainWindow` | 形态清晰、符合 Qt 习惯 | 强调 ribbon，与实际可能无 ribbon 的用法有张力 |
| `QxAppWindow` | 改动最小 | UWP 语境里 ApplicationWindow 有既有含义；`App` 仍重复 |
| `QxWorkbench` | 语义最准（Eclipse RCP 语汇，与"工作区"概念对齐） | 中文读者陌生 |

**已执行的组合做法**：无论最后叫什么，都先在 B1 引入一个薄的宿主上下文（定名 `QxPluginContext`），
把插件会用到的能力（加页面 / 加面板 / 加设置页 / 状态栏 / Toast / 配置对象 / **对象池**）汇总到它身上。
**这样 K14 的最终决定被限制在单个类上，插件代码一行不用改。**
⚠️ 该接口的契约必须**自包含、宿主中立**——不许出现 `see QxAppShell::addPage for the contract` 这类
把契约推给具体宿主的话（作者评审时明确定过）。

### K19 · 对象池的归属（2026-10-11 定）

`QxObjectPool` 是 B5 新增的，写完之后自然会问：它该在 `qxplugin` 还是 `qxcore`？

**先看依赖图**（实测，见各库 `CMakeLists.txt`）：

```
qxcore    → 仅 Qt5::Core                    qxtheme → qxcore
qxplugin  → Qt5::{Core,Widgets} + qxcore    qxapp   → qxcore + qxplugin
```

池放 `qxplugin`：图**不变**；池放 `qxcore`：图也**不变**（qxplugin 本来就依赖 qxcore，不需要新边）。
**这是一道纯归属题**——没有任何机械理由替我们决定，也正因为如此才要现在定下来，别让它漂。

**判据是「库对用户承诺了什么」，不是「机制通用不通用」**：

- 池的**机制**确实通用（只用 `QObject`/`QPointer`/`QString`，十行就能自己写）；
- 但 `qxcore` 承诺的是「**每个应用无论如何都要用到的地基**」（配置 / 日志 / i18n），
  而池只在**两端不能链接**时才是必需品——不写插件的应用已经有对象树、信号槽、`qApp`、
  控制器对象，它不需要一个"按名字查匿名 `QObject`"的池。放进 qxcore 等于给每个用户发一件用不上的家具。

**旁证：Qt Creator 的先例在同侧**。它等价的东西是 `ExtensionSystem::PluginManager::addObject()` /
`getObject<T>()` / `getObjectByName()`，住在 **`src/plugins/extensionsystem/`**（插件框架层），
**不住** `src/libs/utils/`。我们引用过的那句 "useful for **soft dependencies** using pure interfaces"
本来就是扩展系统的语义——既然复制它的语义，落点的类比也该是扩展系统，而不是 core。

**版本层面的理由**：`qxcore` 是六个库里唯一"所有库都用"的地基。往里塞一个**插件专用**的类，
会让 qxcore 的版本号被插件体系的演进牵着走（K11 好不容易让各库独立演进）。

**反方最强论据（记录在案，不足以翻盘）**：池若进 qxcore，前面那条「`qxplugin` 为什么依赖 `qxcore`」
会显得更顺——qxplugin 就同时需要 `QxSettings` 与池了。但这是**倒着论证**：为了给一条既存依赖
找理由而把概念往上搬一层，不是设计。

**什么情况下答案会翻转**（三条具体条件）：

1. 出现**非插件**的消费者——例如将来 `qxdock` 要在自己几个独立编译的分区之间做服务注册，
   或者宿主想在**不走插件**的场合发布服务。今天没有这种场景；
2. 池**长大成通用服务注册表**（按接口取 + 优先级 + 命名空间 + 宿主注册）。那时它从"插件机制"
   变成"工具"——但注意，即便如此 Qt Creator 仍把它留在 ExtensionSystem；
3. 决定切掉 `QxPluginContext::settings()`（见下），从而**打断 `qxplugin → qxcore`** 这条边。
   那样 `qxplugin` 会成为只依赖 Qt 的独立层，本题就更加不用讨论。

> **关联的未决项**：`QxPluginContext::settings()` 返回 `QxCore::QxSettings *`，这是 `qxplugin → qxcore`
> 的**唯一**原因（qxplugin 自己的 `.cpp` 不引任何 qxcore 符号，qxcore 三个类只用了 1 个）。
> 它现在是"context 的固定承诺（never null）"，改成"宿主可选发布的能力"（走池）能切掉这条依赖，
> 代价是丢掉 never-null 保证、插件此后要自己 include qxcore 才能调 `value()`。
> **当前结论：保持现状**（省的是 qxplugin 的 CMake 一行，欠的是插件作者的心智）。

### A2 · `examples/` 的 CMake 支持（已完成）

22 个示例全部重新可构建，目标名沿用 qmake 时期的 `TARGET`（`Example_Ribbon_Simple` 等），
入口是新增的 `examples/CMakeLists.txt` + 根 `CMakeLists.txt` 的 `WITH_EXAMPLES`（默认 ON，
与 `WITH_DEMOS` 并列）。每个示例由一个 `add_qtc_example()` 产出，用到 `add_qtc_executable()`
的既有能力（PCH、AUTOMOC、`Qt5::Core` 形式的依赖），并 `SKIP_INSTALL`——示例只在构建树里，
不该被装进 SDK。

过程中两个值得记住的点：

1. **整份过去的 shared 关系要手工接回来**。qmake 靠 `include(../shared/shared.pri)` 把
   公共的 `main()` 与资源带进来；CMake 里是每个目标自己列出来源，所以第 4 个参数 `main_source`
   指明这个示例用哪个 `main()`（库内的 `qxribbon/shared`、通用的顶层 `shared`，或自带的 `none`），
   而 `shared/res.qrc` 无条件加入。
2. **有 5 个示例不自带 `mainwindow.h`**（`configflags` / `emptydockarea` / `widgettopanel` /
   `coloricon` / `ribbonquickaccessbar`），它们编译的是 `shared/mainwindow.h` 里那个通用
   `MainWindow`。AUTOMOC 只处理属于目标的头文件，这一份不在目标的源码列表里，于是
   `Q_OBJECT` 拿不到 `moc_*.cpp`，链接期报 `undefined reference to vtable for MainWindow`。
   做法是**仅对这一类**把 `shared/mainwindow.h` 加进目标源码——无条件加会与自带头文件的
   示例撞出两个 `MainWindow` 类。

- 验证：qt6 preset 构建 22 个目标 0 warning；22 个可执行文件在 `QT_QPA_PLATFORM=offscreen`
  下全部启动且不崩溃。

### B1 · 插件契约（阻塞于 K14）

元数据**不改格式**，直接用 `add_qtc_plugin()` 已有的 `<name>.json.in`：

```json
{
    "Name" : "Output",
    "Version" : "$$QTPROJECT_VERSION",
    "CompatVersion" : "$$QTPROJECT_COMPAT_VERSION",
    "Vendor" : "QtCanpool",
    "Copyright" : "$$QTPROJECT_COPYRIGHT_YEAR",
    "Category" : "Modules",
    "Description" : "An output pane that collects application messages.",
    "Url" : "https://canpool.github.io/qtcanpool/",
    "$$dependencyList"
}
```

运行时侧新增两个类（**建议放在一个新库 `qxplugin`**，理由见 K16 的反向约束：插件体系本身不该塞进
`qxapp`，否则每个插件都要链接整个应用框架）：

```cpp
class QX_PLUGIN_EXPORT QxPlugin : public QObject
{
    Q_OBJECT
public:
    explicit QxPlugin(QObject *parent = nullptr);

    // Dependencies are up; take everything you need from \a context and return
    // false with a human readable reason when you cannot.
    virtual bool initialize(QxPluginContext *context, QString *errorString) = 0;

    // The whole set is up now: finish setup that had to wait for it. Peers are
    // not reachable from a plugin - wiring them together is the host's job.
    virtual void extensionsInitialized() {}

    // Reverse order of initialization. Rollback on failure is not offered:
    // once you said yes, shutting down must always succeed.
    virtual void shutdown() {}
};
```

`QxPluginSpec` 是元数据的只读视图（从 JSON 读来），并提供状态与诊断：

```cpp
enum class QxPluginState { Invalid, Read, Resolved, Loaded, Initialized, Stopped, Disabled };

QString id() const;                    // "output", also the file base name
QVersionNumber version() const;
QVersionNumber compatVersion() const;  // 宿主在此区间内才兼容
QStringList dependencies() const;      // required, resolving order
QStringList optionalDependencies() const;
QxPluginState state() const;
bool isEnabledByDefault() const;
QString filePath() const;
QString error() const;                 // why it is not running - never empty when it is not
```

- **版本规则**：宿主声明它能接受的插件 `[compatVersion, version]` 区间；插件落在区间外时**确诊为
  "版本不符"并跳过**（不尝试加载），诊断串里给出双方版本。
- **接口版本**：`QxPlugin` 加 `virtual int interfaceVersion() const`（首版 `1`）；宿主要求不小于 1 才调用，
  为 5.0 改接口留门。

### B2 · 发现、依赖解析与加载顺序

```cpp
class QX_PLUGIN_EXPORT QxPluginManager : public QObject
{
    Q_OBJECT
public:
    void setPluginPaths(const QStringList &paths);   // search order matters
    void setDisabledPlugins(const QStringList &ids); // persisted elsewhere, see QxSettings
    void setEnabledPlugins(const QStringList &ids);  // the other half: starts a plugin whose
                                                     // metadata says EnabledByDefault=false
    QStringList pluginPaths() const;

    void loadPlugins();                              // read -> resolve -> load -> initialize

    QList<QxPluginSpec *> specs() const;             // dependency order - the ones that load
    QList<QxPluginSpec *> allSpecs() const;          // + skipped and failed; what a UI lists
    QxPluginSpec *spec(const QString &id) const;
    bool hasError() const;
    QString errorString() const;                     // everything that went wrong, once

Q_SIGNALS:
    void pluginInitialized(QxPluginSpec *spec);
    void pluginFailed(QxPluginSpec *spec, const QString &reason);
};
```

- **遍历/目录规约**：沿用 `IDE_PLUGIN_PATH`（ macOS 是 `<App>.app/Contents/PlugIns`，其它是 `lib/qtcanpool/plugins`），
  与 `add_qtc_plugin()` 的 `LIBRARY_OUTPUT_DIRECTORY` 保持一致——**因此开发者/config 都不用告诉它在哪**。
- **拓扑排序**：Kahn 算法；**循环依赖**报错并给出环上的完整 id 链（不是"检测到循环"四个字）；
  **缺失依赖**同理，列出缺哪个。
- **静态构建**：直接读 `Q_PLUGIN_METADATA` / Qt 静态插件注册表，跳过 `QPluginLoader`，
  但**所有其它逻辑（排序、诊断、状态机）完全一致**——这一条保证 WASM 在线 demo 能演示插件。
- 单测要求：**用一个临时目录 + 一组测试态插件**（互相依赖、循环、缺失、版本不符、enableByDefault=false、
  initialize 返回 false），把这些诊断串断言出来。

### B3 · 生命周期与失败隔离

- 顺序：`Read → Resolved → Loaded → Initialized`，关闭时逆序 `shutdown()`；
- **`initialize()` 返回 false** → 该插件标记 `Disabled`，其**反向依赖**连带跳过（按顺序传递），
  并各自带上"因依赖 X 未就绪"的诊断；宿主继续启动，**不弹窗、不崩**；
- `dlopen`/符号缺失（`QPluginLoader` 层面失败）与业务逻辑失败是**两类**诊断，不要合成一句；
- 非目标里的"同进程"要写进插件作者文档：插件里的崩溃就是应用的崩溃。

### B4 · 补齐 UI 注入点

现状（1.2 表）里缺两处，且都是插件形象绑定的"能看见"的地方：

1. **功能区**：`RibbonAppWindow` 需暴露 ribbon 本身（目前只有 `updateWindowFlags()`），`qxribbon` 侧需要
   一个稳定的"帮我取到 ribbon bar"的入口。这是**唯一需要动 `qxribbon` 的地方**。
2. **应用菜单 / 快速访问栏**：给出最小却足够的 API（追加条目 + 分组），不做命令框架。

关键约束：**`qxapp` 不认识具体插件，插件也拿到的是上下文而不是窗口类**（见 K14 的建议做法）。

### B5 · 对象池：插件间软协作

B1 把「插件拿不到同伴句柄」做成了运行时事实，代价是**两个插件之间无法协作**——`filetree` 想把一行字
交给 `output`，除了宿主替它们连，没有别的路。而宿主一旦替它们连，就必然在宿主里写下两个模块名，
D1 的命题（空壳主程序不认识任何模块）就打了折。B5 是补上这个缺口的那一块。

调研了 Qt Creator 的做法（`ExtensionSystem::PluginDependency` / `PluginManager` 对象池），结论：

| | Qt Creator | 4.0 采纳 |
| :--- | :--- | :--- |
| 硬依赖 | `required`：解析 + 排序 + **可以链接调用** | 同（`PLUGIN_DEPENDS` 本就是 PRIVATE link） |
| 软依赖 | `optional`：能解析则**仍先加载**，不能则当成没声明；**不可链接** | 同（补上排序语义，见下） |
| 同伴访问 | 对象池 `addObject()` / `getObject<T>()` / `getObjectByName()` | `QxObjectPool`，经 `QxPluginContext` 暴露 |

**落点**：

- 新类 **`QxObjectPool`**（`qxplugin`）：`addObject` / `removeObject` / `objects` / `objectByName` /
  `object<T>()`，加 `objectAdded` / `aboutToRemoveObject` 两个信号。**不持有对象**——条目是
  `QPointer`，对象一死条目自动消失，所以被卸载的发布者留不下野指针。
- `QxPluginContext` 只是**转发**：`addObject` / `removeObject` / `objects` / `objectByName` / `object<T>()`。
  池子是宿主交进来的（构造参数），不是每个宿主各写一遍；没交的宿主这几个调用就是空操作。
- `QxAppShell` 懒创建自己的池并加 `pluginPool()`，`QxAppShellContext` 在构造时把它交给基类。
- **不引入 `Q_DECLARE_INTERFACE`，也不做 `QObject` + 虚接口的多重继承**：前者要求后者，而后者是我们
  自己踩过并记进 `TOPIC-pitfalls.md` 的堆破坏坑；跨 DLL 用 `qobject_cast<T*>` 查头文件里声明的接口
  也不可靠（`staticMetaObject` 每个模块各一份）。所以样板走**按名字 + 元对象**——这也正是 Qt Creator
  给软依赖推荐的那条路（"you may not link against the dependency ... use QMetaObject functions"）。

**可选依赖的排序语义**（原实现是死的：`optionalDependencies()` 只有管理器对话框在读）：

- `qxpluginspec.cpp` 原来把 `optional` 和 `test` 一起塞进 `optionalDependencies`；现在只有 `optional`
  进去，`test` 读完即丢（全树没有 `-test` 模式，且它按定义不参与排序）。
- `qxpluginmanager.cpp` 的 Kahn 建图多一条边：**能解析到活的候选的可选依赖，照样排在前面**；
  缺失／被关／已失败的**不建边**，而这个「不」只体现在两个地方——步骤 2 的缺失判定和步骤 3 的级联
  判定**只读 `dependencies()`**。
- `cycleChain` 同步跟着可选边，否则环路报告里的链在元数据里找不到。

⚠️ 顺带纠正 B4/C2 的一句：我们曾把 `extensionsInitialized()` 说成"不是接线点"。Qt Creator 的生命周期
文档里它是，方向相反——`initialize()` 正序（消费方伸手），`extensionsInitialized()` 逆序（供给方收尾）。
我们目前**按正序**调用它（不提供 Qt Creator 那种"依赖我的人都走完了"的保证），已在 `qxplugin.h` 的
注释里写明，不改行为。

### C2 · `src/modules` 业务模块样板

每个模块 = 一个 `add_qtc_plugin()` 目标 + `<name>.json.in`，放在按 Layer 分的子目录里
（`src/plugins/CMakeLists.txt` 的 Level 0~8 注释给了现成的分层约定）。样板：

| 模块 | Level | 演示什么 |
| :--- | :--- | :--- |
| `output` | 1 | 停靠面板 + 状态栏；把**自己发布到对象池**（`addObject`），供同伴按名字找到 |
| `notebook` | 1 | 页面（`addPage()`）+ 导航条条目 + 配置持久化 |
| `filetree` | 2 | 另一个面板 + 在池里找 `output` 并自行接线；依赖声明为**可选**（`PLUGIN_RECOMMENDS`） |

另写**一个故意坏掉的模块**（`broken`，缺依赖）留在外面，供文档与截图使用——**不进构建**。

> 目录归属由 **K16** 决定：`src/modules` 是「样板与时兴能力的收容所」，正式稳定的能力进 `src/libs`；
> `src/plugins` 相反，是框架**自己的功能插件**目录（Level 0~8 分层约定的出处，目前为空）。
> 这里只借用它的分层规则，不放业务样板。

⚠️ 原文把 `filetree` 写成「与 `output` 的跨插件接线（`extensionsInitialized()`）」，这条**已按事实纠正**：
插件拿不到同伴句柄（见 B4 与 `qxplugin.h` 的注释），`extensionsInitialized()` 在当时的实现里不是接线点。
这句话**已由运行时兜住**：静态实例不再挂到管理器名下（见下节补丁），因此「拿不到句柄」在静态构建下
也成立，而不只是一句注释。
**接线机制后来由 B5 补齐**：`filetree` 声明的是**可选**依赖（`PLUGIN_RECOMMENDS output`，不是
`PLUGIN_DEPENDS`），并在自己的 `initialize()` 里从对象池取 `"output"` 自行连接——所以「关掉输出面板
就连带关掉文件树」这个副作用不复存在，而宿主仍然一个模块名都不用写。

### B1 / B2 / B3 落地（2026-10-10 起）

把 K14 的「建议的组合做法」真正落地：先上薄宿主上下文 `QxPluginContext`，把插件会用到的能力
（加页面 / 加面板 / 状态栏 / 进度 / Toast / 配置对象）汇总到它身上，**插件只面向这个接口编程**，
宿主改名（K14）因此被封死在单个类上，插件代码一行不用改。

**落点**：新建库 `src/libs/qxplugin/`（只依赖 `qxcore`，不依赖任何 `qxapp` 之上的东西），含：

- `QxPlugin`：插件基类（`QObject`），`initialize(context, *errorString)` /
  `extensionsInitialized()` / `shutdown()` 三步生命周期，`interfaceVersion()` 留门；
- `QxPluginSpec`：元数据的只读视图（从 `plugin.json` 读来），带状态机
  `Invalid → Read → Resolved → Loaded → Initialized → Stopped/Disabled` 与诊断串；
- `QxPluginContext`：薄宿主上下文（见 K14 决策）；**注释保持宿主中立**——不复述某个具体宿主类，
  每个方法的契约自包含（不要写「见 QxAppShell::xxx」这种把契约推给具体宿主的话）；
- `QxPluginManager`：发现（`setPluginPaths`）、依赖解析（Kahn 拓扑）、加载顺序
  （`Read → Resolved → Loaded → Initialized`，关闭逆序）、失败隔离。

**B2 的依赖解析**：Kahn 拓扑排序；循环依赖给出环上的完整 id 链（如 `a -> b -> a`），缺失依赖列出缺哪个。
静态构建（K17）走 `registerStaticPlugin` + `Q_PLUGIN_METADATA` 注册表，跳过 `QPluginLoader`，
但排序/诊断/状态机逻辑与动态完全一致。

**B3 的失败隔离**：`initialize()` 返回 false → 该插件标记 `Disabled`，其**反向依赖**按拓扑序连带跳过，
各自带上「因依赖 X 未就绪」的诊断；宿主继续启动，不弹窗、不崩。加载层失败（`QPluginLoader` 找不到
实例 / 缺少 `Q_PLUGIN_METADATA`）与业务逻辑失败（initialize 返回 false）是**两类**诊断，不合成一句。

**宿主侧（解耦的关键一步）**：`QxAppShell` **没有**继承 `QxPluginContext`。最初尝试过
`class QxAppShell : public RibbonAppWindow, public QxPluginContext`，但 `QxPluginContext` 带虚函数表、
而 `RibbonAppWindow → QWidget → QObject` 也是 QObject 派生——多重继承一个带虚函数的接口会破坏 QObject
的内存布局，在 `tst_qxapp` 退出释放阶段触发 **堆越界（heap corruption，40 字节块尾部被改写）** 崩溃。
改法是用**组合**：`QxAppShell` 持有一个 `QxAppShellContext : public QxPluginContext` 适配器，把它每个
虚函数转发到 `QxAppShell` 的公开 API；`pluginContext()` 懒创建并返回该适配器（宿主拥有其生命周期）。
这样既解耦、又绕开了多重继承的内存布局陷阱——这也是「宿主实现接口用适配器而非继承」的实证理由。

**单测**：`tests/qxplugin/auto/tst_qxplugin.cpp` 13 例，覆盖 spec 读元数据、依赖顺序、缺失依赖、
可选依赖可缺、循环依赖（断言诊断串含 `a -> b -> a`）、版本不符、默认禁用跳过、
`initialize` 失败级联与隔离、接口版本过旧拒绝、`hostContextAdapter`（经 `shell.pluginContext()`
把适配器交给管理器）、关闭逆序。全树 `ctest` 10/10 通过（含 `tst_qxapp` 12 例、`tst_qxplugin` 13 例）。

**版本结算（E2 部分）**：依 K11，本期动了 API 的库结算一次——`qxplugin` 新库从 `0.1.0` 起；
`qxapp` 因新增公开 API `pluginContext()` 且新增对 `qxplugin` 的 PUBLIC 依赖，`0.0.1 → 0.1.0`。
其余四库（qxcore/qxribbon/qxdock/qxtheme）未动 API，不动。

**偏离计划的点**：原 B1 说「新建库放 `qxcore` 或新 `qxplugin`」，最终选新 `qxplugin`——与 K16 的反向约束
一致（插件体系不该塞进 `qxapp`，否则每个插件都要链接整个应用框架；`qxplugin` 只依赖 `qxcore`）。

**核实到一个真缺陷（B1 遗留）**：`qxplugin.h` 原本写着
`Q_DECLARE_INTERFACE(QxPlugin::QxPlugin, QX_PLUGIN_IID)`。`QxPlugin` 不是纯接口而是 `QObject`
派生类，这条声明会把 `qobject_cast<QxPlugin *>` **改道**走 `qobject_iid_cast()` →
`object->qt_metacast(IID)`，而后者只对**自己**列了 `Q_INTERFACES(QxPlugin)` 的类成立；moc 不会把
接口列表继承给派生类。后果很隐蔽：**按本头文件文档写出来的插件加载成功、却永远 cast 失败**，
管理器报 "could not be instantiated"，而 `QPluginLoader` 一路 `load true` / `inst true`。
**删掉该声明即修复**——`QxPlugin` 是 `QObject` 派生类，`qobject_cast` 会自动退回 meta-object 链，
任意继承深度都成立；插件与库的绑定是 `Q_PLUGIN_METADATA` 里的 IID 字符串，与
`Q_DECLARE_INTERFACE` 无关。C2 的模块是第一批真正过加载器的插件，`tests/qxmodules` 直接把它逮住。

⚠️ **第二个坑**：`add_qtc_plugin()` 在 **configure 期**读 `<name>.json.in`，改它**不会**触发重新配置，
生成的 `plugin.json` 会停在旧值（本次表现：`Vendor` 改了，跑出来还是旧值）。改完要手动
`cmake -S . -B build/qt6`。

⚠️ **第三个坑**：在**继承自 `QxPlugin` 的类内部**，`QxPlugin` 这个名字被继承来的类名遮蔽，
`QxPlugin::QxPluginContext` 会被解析成"类 `QxPlugin` 的成员"而报错——模块头文件里要用
`::QxPlugin::QxPluginContext`（前导 `::`）。命名空间名与其中的类名同名，这是必然踩到的地方。

**测试**：新增 `tests/qxmodules`（`tst_qxmodules`，4 例）：元数据落库 + 依赖边、依赖排序

### 补丁 · 封住静态插件的 `parent()` 后门（2026-10-10）

**背景（D1 之前的一次复核）**：「插件拿不到同伴句柄」这句话在 C2 写进了 `qxplugin.h`、`4.0-TASKS.md`
与三个模块的头文件里。复核时逐条对着代码走了一遍句柄路径，发现**契约成立、实现留了一条缝**：

| 插件能摸到的对象 | 核对结果 |
| :--- | :--- |
| `QxPlugin` 自身 | 唯一成员 `m_context`，唯一访问器 `context()`；**没有** `manager()` |
| `QxPluginContext` | 只有宿主能力（页面 / 面板 / 状态栏 / 进度 / Toast / `settings()`）；**没有**管理器、**没有**取同伴的入口 |
| `QxPluginSpec` | `plugin()` 确实能给出同伴的 `QxPlugin*`，但 spec 只由管理器交给**宿主**，插件手里没有 spec |
| 插件之间唯一共享的东西 | `context()->settings()` 返回的同一个 `QxSettings*`（数据通道，不是同伴对象句柄） |
| ⚠️ **静态实例的 `parent()`** | `createInstance()` 里 `instance->setParent(q)`，`q` 就是 `QxPluginManager` → `qobject_cast<QxPluginManager *>(parent())` 拿回管理器，再 `plugin(id)` 拿到任意同伴 |

即：**动态构建下注释完全成立，静态构建（含 K17 的 WASM）下是过度声明**。

**改法**（保留清理语义，一行）：`QxPluginManagerPrivate` 增加一个普通 `QObject pluginOwner;` 成员，
静态实例挂到 `&pluginOwner` 而不是管理器。它不是管理器的子对象，`pluginOwner->parent()` 为 `null`，
所以没有回到管理器的路；实例仍随 `delete d_ptr` 一起析构，与动态实例（由
`qDeleteAll(dynamicLoaders)` 在析构体内销毁）时机一致，比原来（`~QObject` 里销毁）更整齐。

**测试**：`tst_qxplugin` 新增 `pluginCannotReachTheManager`（第 15 例）——断言实例**仍有所有者**
（`parent() != null`，防止有人用「干脆不挂父对象」糊过去而漏掉清理）、该父对象不是管理器、
整条祖先链上也没有管理器，并且它得到的唯一句柄就是宿主交出的那个 context。
**反向验证过**：临时恢复 `setParent(q)` 后这条新例**失败**（`ctest` 红），恢复修复后全绿——
是回归测试而不是装饰。qt6 全量构建 0 warning、`ctest` **11/11**、clang-format 门禁绿。

**版本**：本次**不动** `qxplugin` 的号（`0.2.0` 不变）——改的是所有权实现，公开 API 一行未增未减；
按附录 B「只前进本期动了 API 的库」，没动就是没变。

**提交**：`3269a1f3` fix(qxplugin) keep the manager out of a plugin's object tree、本文档。

#### D1 的第二个产出：K17 的答案（静态构建 / WASM）

**结论：4.0 不支持"静态构建下的运行时插件发现"**，并把这句写进代码与文档（K17 落案）。四条依据都是实测：

1. **预设本身缺一个环境变量**：`wasm` 预设只设了 `QTCANPOOL_EMSDK`，而 Qt 的 wasm 工具链读的是
   `EMSDK`（`QtPublicWasmToolchainHelpers.cmake` 里 `file(READ "$ENV{EMSDK}/.emscripten")`）——
   干净的 `cmake --preset wasm` 直接失败于 `file failed to open ... /.emscripten`。已补 `EMSDK`。
2. **硬伤：插件根本进不了可执行文件**。`QTC_STATIC_BUILD=ON` 时 `add_qtc_plugin()` 走
   `add_library(${name} STATIC)` + 定义 `QT_STATICPLUGIN`，而**全树没有任何东西把它拉进去**：没有
   `Q_IMPORT_PLUGIN`、没有 `qt_import_plugins()`，连内部清单 `__QTC_PLUGINS` 也没有消费者
   （它只服务于 `qtc_plugin_enabled()` 的存在性检查）。实测两条：
   `output` 在 wasm 下的产物是 `build/wasm/lib/qtproject/plugins/liboutput.a`——一个躺在"插件目录"里、
   谁也不会去加载的静态库；`IdeShellDemo.wasm`（14 MB）里**没有**模块元数据串（`Sample module` 是
   `output.json` 的 `Description`，链进去就会在，实测 absent）。所以 WASM 版会是"0 个插件"，
   D1 的效果一点不剩。
3. **补它的代价落在最不该动的地方**：静态插件只能由**应用**导入（`Q_IMPORT_PLUGIN(类名)` /
   `qt_import_plugins()`），也就是主程序必须写出一份"我导入了哪些模块"的清单（手写或由 CMake 生成）。
   这与 D1 的命题**正面冲突**：D1 的价值就在主程序里没有一个模块名。
4. **买不到验证**：插件体系真正值得测的逻辑（元数据解析、Kahn 拓扑、循环/缺失诊断、失败级联隔离）
   `tst_qxplugin` 15 例**全部**走 `registerStaticPlugin()`，也就是编译期组合那条路；再叠一条 WASM 腿
   不会多覆盖任何东西。而 `wasm` 预设本身 `WITH_TESTS=OFF`；`pages.yml` 里那条 wasm 作业（CI 的
   `ci.yml` 没有 wasm 作业，只有四条 `build` + `clang-format` / `quality` / `tidy`）**只构建
   `AppShellDemo` 一个目标**（`cmake --build build-wasm --target AppShellDemo`），插件从来没被它构建过，
   也就谈不上覆盖。

**据此定下**：

- 静态构建**不支持运行时插件发现**；`QxPluginManager` 的发现路径是"目录 + 元数据"，天然属于动态构建；
- 静态构建里把模块组合进应用的支持方式是**编译期** `registerStaticPlugin()`——已有、已测、够用；
- WASM 在线 demo 演示**框架本身**（Ribbon / Dock / Theme / Shell / Settings / 工作区 / Toast / 进度），
  **不演示插件**；`QxPluginManagerDialog` 不受影响（它只读元数据）；
- 代码里把误导线剪掉：`QTC_STATIC_BUILD` 下不构建 `IdeShellDemo`（它在那里必然装不出东西）；
  `src/modules/CMakeLists.txt` 注明静态构建下这些是"没人导入的静态库"。

**顺带的收获：这次 WASM 试跑抓到一个真的可移植性缺陷**（已单独修掉）：`qxapp` 的
`qxappshell.h` / `qxpluginmanagerdialog.{h,_p.h}` 用 `QxPlugin::QxPluginContext` 这类**限定名**引用插件
类型，而 `QxPlugin` 既是命名空间又是命名空间里的类——**任何在 `using namespace QxPlugin;` 之后**才包含
它们的 TU 都会在两义上，clang 直接报 `reference to 'QxPlugin' is ambiguous`，GCC 取命名空间、放过。
是否踩到取决于**头文件包含顺序**，所以已有的绿 CI 并不能证明什么。已按仓库既有写法
（`src/modules/*` 自 C2 起就是 `::QxPlugin::QxPluginContext`）在 `qxapp` 里补前导 `::`，
并用 emscripten 的 clang 编译验证通过。

`enterEvent hides overloaded virtual function`（Qt 6 的 `QWidget::enterEvent(QEnterEvent*)`）——
GCC 不报，是既有代码的潜在问题，本次未动。wasm 全量构建**只有**这一条 warning，0 error。
