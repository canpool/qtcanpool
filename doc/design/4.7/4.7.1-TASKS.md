## 一、这一版做什么

**一句话：五个千行 `.cpp` 按职责拆开（A 组），再把滚动追加池点名的六件控件造出来（B 组），
最后把 fluentdemo / materialdemo 按参考站的形象重做（D 组），别的一个字都不动**（新界面风格库
原拟进本版，作者 2026-10-22 裁定移出、4.7.2 引入两家，见 §二 C 组）。

两半的产物性质不同——A 组是**搬家**（源码行数不变、行为不变、公开面不变），B 组是**增量**
（全新文件，只加不改）——所以判据分两套（§四），互不污染。

### 1.1 为什么这两半能放进同一个 patch

1. **作者口径。** 2026-10-22 明确定范围：重构**放进** 4.7.1 但不**限于** 4.7.1；滚动池
   （C6 / D5）的组件**也要实现**。初稿「只做重构」已被作者否决。
2. **K36 的表两半都覆盖得到。** 「内部重构，公开面与默认行为不变 ⇒ patch +1」管 A 组；
   「新增能力（加类 / 加函数）⇒ patch +1」管 B 组。两半都到不了 minor 的三个触发器
   （改签名 / 删 API / 改名——行为变更按 §1.5 走 patch，已不在这三项里），所以**这一版是 patch**，
   不需要为任何一半找陪衬、也不需要把哪一半推到下一个 minor。
3. **文件不重叠 ⇒ 可独立回滚。** A 组动 `qxribbon` / `qxdock` 的既有 `.cpp`，B 组只在
   `qxfluent` / `qxmaterial` 里加新文件。这是两半能放在同一版而不互相污染的原因，
   也是判据要分两套的原因：A 组的 ①（多重集相同）在 B 组面前没有意义，B 组的 ⑦（纯增量）
   在 A 组面前也没有意义。

### 1.2 为什么先拆后建（执行序的理由）

```
A 组（R1–R5）→ B 组（Y1–Y6）→ S8 重基线 → D 组（D1a–D2b + 金标）→ S6 + S10 文档 → S9 系列台账 → 结算
```

1. **① 的多重集比对在「只有拆分在动」的树上最干净。** B 组落过之后五个文件本身没动、
   ① 照样成立，但审阅者要在「新控件 + 搬家」混在一起的 diff 里找搬家证据。
2. **④ 的金标零差必须在 gallery 变化之前对齐。** B 组必然给 gallery 加行
   （`materialpage.h` 的注释写死了「one row for every control QxMaterial ships」），
   所以 A 组的 ④ 只能跑在 B 之前；反过来说，B 组落完 gallery 必然变，重基线是**计划内**
   动作（S8），不是失败。
3. **反证的用法。** A 组期间 `dockdemo.png` 与 `controlgallery.png` 都该零差；B 组期间
   `controlgallery.png` 必然变（重基线），而 `dockdemo.png` 仍必须零差——B 组不碰 dock，
   它变了就说明 B 组碰到了不该碰的东西。

### 1.3 口径澄清：4.4 的"拆分"不是拆文件

`4.4-TASKS.md:38` 把 `ribbonbar.cpp`（当时 1961 行）列为「单文件巨石拆分」，A1-T1「已收口」。
**实际落地的是抽公共块去重**（`placeCornerWidget()` / `layoutTabBar()` / `paintPageContextTabs()`，
见 `4.4-TASKS.md` §七 `0314c153`、`39a38c3f`），**没有拆成多个 `.cpp`**。文件因此从 1961 行
涨到 2385 行（4.7.0 又往里加了 QAB 晚到样式表、样式四值、KeyTips 等）。

⇒ A 组做的不是"把 4.4 没做完的补上"，而是**换一种拆法**：不合并重复、只搬移位置。
两者判据不同（去重要改代码，搬家不许改代码），所以不要拿 4.4 的提交当模板。

⚠️ 引用口径：`4.7-TASKS.md` §二 写的是「`ribbonbar.cpp` 2353」——那是 4.7.0 **收尾前**的数；

### 1.4 硬约束（4.7.0 §1.3 六条照旧，本版另加四条）

4.7.0 §1.3 的六条（双腿 / Qt 6 独有 API / 源文件不带 BOM / 图标 / 主题族 id / 不引第三方 /

  （`4.7-TASKS.md` §二），不改在拆分笔里。唯一允许的改动是 §2.0 列的三种"搬家必需"。
- ⚠️ **B 组只加不改**。既有源码文件（两库的 `.h` / `.cpp`）一行不碰；允许改的只有

⚠️ 第二条「只加不改」是**提交卫生**（新增笔里不夹带修复），**不是**「行为不许改」的政策禁令——
行为可改是作者 2026-10-22 定的政策（§1.5）；要改就单独一笔、单独验证，别混在新增笔里。

## 二、任务分解

### 2.0 A 组的三种"搬家必需"改动（除此之外一行不动）

搬移必然带来三类文本变化，**预先声明、审核时按这三类认**：

| 类别 | 内容 | 影响 |
| :--- | :--- | :--- |
| **N1 文件外壳** | 新 `.cpp` 的版权头、`#include` 清单、`QX_*_BEGIN_NAMESPACE` / `QX_*_END_NAMESPACE` 包裹 | 无（每个 TU 各一份） |
| **N2 助手换处** | 原本 `static` 在 `.cpp` 里的**常量 / 纯函数 / 宏**，若被两个以上的新文件用到，搬进该库的 `_p.h` 并改写成 `inline`（常量写 `inline constexpr int`，C++17 已开启，见根 `CMakeLists.txt:30`） | 无（仍是每个 TU 一份，链接期不冲突） |
| **N3 私有类头文件化** | qxdock 四个私有类**原本定义在 `.cpp` 里**，拆分要求两个 `.cpp` 看见同一份定义 ⇒ 原样搬进 `<class>_p.h`（**连同成员的默认值、内联函数体、声明顺序一起搬，一个字不改**） | 无 ABI 影响（私有类本就不导出，公开类经 d-pointer 的尺寸布局不变；`AUTOMOC` 不受影响，实测这五个 `.cpp` 里**没有** `Q_OBJECT`，也没有 `#include "*.moc"`）。⚠️ 但 `_p.h` **会被安装**——`set_public_headers` 把 SOURCES 里所有 `.h` 装进 Devel 组件（`cmake/QtCanpoolAPIInternal.cmake:222`，qxribbon 已有 14 个先例）⇒ 记录口径是「私有实现定义进入**已安装但不属导出 API** 的头」，architecture.md 的说明句按这个写（S6） |

⚠️ **`static` 变量不适用 N2**：带状态的 `static`（本批只有一个 `qxdock/dockcontainer.cpp:28`
的 `s_zOrderCounter`）**绝不能进头文件**——进了就是每个 TU 一份副本，z 序就不唯一了。它跟
唯一使用者 `DockContainer::event()` 走同一个文件（实测只有 `1666`/`1668` 两处引用）。

#### Y1 · `FluentNumberBox`（输入层）

- **台账原话**（C6 第 2 条）：「带校验与步进器的数值输入，QSpinBox 缺的形态」。
- **形态**：`QxControl` 子类，内嵌 `QLineEdit`（Qt 的文本编辑不自己造）。步进器是
  **右侧上下两枚 chevron**，不是旋转框——旋钮是「旧世界」的答案，Fluent 没有它。
- **校验**：非数字输入不进入 `value`；失焦把显示拉回 `value`（口径同 4.7.0
  `FluentCommandBar` 的「问的时候才算」——不缓存过期状态）。
- **接口方向**：`minimum` / `maximum` / `singleStep` / `value` + `valueChanged`。
- **键盘**：上下键一步、PageUp / PageDown 大步（档位实施时定）。
- **无障碍**：role `SpinBox` + `QAccessibleValueInterface`（`FluentSlider` 之后的第二个消费者）。
- **测试量级**：6–8 条（像素探针测步进按钮与焦点态；行为测校验与值域）。

**Y1 执行记录（2026-10-22）**：落地为 `fluentnumberbox.{h,cpp}`（头 105 行 / 实现 424 行）+
`tst_fluentnumberbox.cpp` 八条 + gallery `Input` 段一行 + `CMakeLists.txt` 一行 + 库 CHANGELOG
`Unreleased`。

三处实施中定下的事：

1. **焦点交给编辑器，控制本身靠 `setFocusProxy()` 拿答案**。按钮的键盘要落在 `QLineEdit` 上
   （否则选择、光标、输入法全得自己造），但基类的焦点环与 `hasFocus()` 是画在控制上的。
   `setFocusProxy(m_edit)` 让两者统一：`QWidget::hasFocus()` 会沿代理链走，编辑器有焦点时
   控制也回答 true —— 基类焦点环因此照常落在字段上，不需要绕过基类。
2. **键盘与滚轮必须过事件过滤器**。焦点在编辑器上，`keyPressEvent` / `wheelEvent` 到不了控制；
   上下键、PageUp/PageDown、Enter（提交）、Escape（丢弃）都在 `eventFilter` 里接。
   控制自己的 `keyPressEvent` 仍保留同一套处理，给"应用直接把焦点给了控制"那条路。
3. **「步进是控制说话，打字是用户说话」**。`setValue()` 在编辑器有焦点时不覆盖文本（不抢正在
   输入的内容），而 `step()` 在 `setValue()` 之后强制同步一次 —— 否则按上键值时值变了、框里还是

四处实施中定下的事：

1. **「整面即菜单」用不着自己接鼠标**：`QxControl::clicked()` 的语义已经是「按下并释放在本控件
   内」，正好就是「整面」，所以构造里一条 `connect(clicked → openMenu())` 就够，不必重写 press /
   release，也不必自己判 hitTest。这是 A/B 两组「复用基类机制」的又一次收益。
2. **空菜单不开**。`openMenu()` 先发 `aboutToShowMenu()`（应用趁这一下把菜单填成「现在为真」的
   样子），再判 `isEmpty()`：还空着就**不发愁地不开**。开一个空盒子是按钮兑现不了的承诺。
   测试因此用 `menu()->isVisible()` 而不是信号条数来验「没开」——信号照样发一次。
3. **chevron 画出来、不打印**（照 `FluentNumberBox` 与 `CommandBar` 的口径）：字体里的字形主题

4. **`sizeHint` 与 `minimumSizeHint` 用同一个 `qCeil`**。第一版 `sizeHint` 尾部 `+1` 防取整，
   于是空文本时两者差 1（45 vs 44），被测试当场抓住；改成两边都 `qCeil(width)`。
5. 文本即无障碍名（照 `FluentSwitch`：应用一旦显式 `setAccessibleName` 就不再覆盖）。

两件事」），各自有独立的判据与测试，合成一笔会让「谁坏了」不可定位。

**Y3 执行记录（2026-10-22）**：落地为 `fluenttogglesplitbutton.{h,cpp}`（头 113 行 / 实现 346 行）+

2. **缝画出来**。两半是两个东西，一条 1px、上下内缩 6 的分隔线就是这句承诺的写法；不画，读者要

#### Y4 · `FluentContentDialog`（反馈层）

- **台账原话**（C6 第 4 条）：「模态内容对话框，Qt `QDialog` 缺的观感与动作布局」。
- **实现选型**（见 Q8）：`QDialog` 子类 + 自绘 surface（投影走 `QxShadowPainter`，
  `FluentCard` 是第一个消费者）。**不用纯自绘 overlay widget**——Qt 的模态、ESC、
  `exec()` 返回值都是现成的，自己造一遍只会得到更差的那一个。
- **结构**：标题 + 内容（`setContent()`，口径同 `FluentNavigationView` 的内容区）+
  底部动作条（主 / 次 / 关闭，最多三个；按钮是「问不是做」，由应用去连——同
  `FluentTeachingTip` 的口径）。scrim 遮罩 + `FluentMotion` 淡入。
- **测试先例**：`tst_RibbonCustomizeDialog`（4.7.0 §⑧：编辑 → apply → 写文件 → 另一个窗口
  读回）已证明 offscreen 下对话框可测。本件测：结果码、按钮布局几何、reduce 时动效落位。
- **测试量级**：6–8 条。

**Y4 执行记录（2026-10-22）**：落地为 `fluentcontentdialog.{h,cpp}`（头 106 行 / 实现 340 行）+
`tst_fluentcontentdialog.cpp` 十条 + gallery `Feedback` 段一行（启动器按钮，同 teaching tip 的口径）
+ `CMakeLists.txt` 一行 + 库 CHANGELOG `Unreleased`。

六处实施中定下的事：

1. **窗口盖住它打开时所在的那一页**（`showEvent` 里 `setGeometry(owner->window()->geometry())`），
   scrim 画在自己整块区域上、卡片居中——而不是「卡片窗口 + 另一层蒙版窗口」。一个窗口、一条
   绘制路径、一处可测的地方；没有窗口可盖时（无 parent）它就按 `sizeHint()` 立在原地，scrim 变成
   卡片四周的一圈暗边——同一条代码路径，不特判。遮罩＝页面底色上压一层黑 31%，**卡片用页面本色**：
   把卡片抬起来的是遮罩而不是另一种漆，这正是画 scrim 而不画边框的理由。
2. **暗色下前景抬升靠表面、不靠投影**。第一版照 `FluentCard` 用 `textColor()` 当投影墨色，暗色
   主题的 `WindowText` 近白 ⇒ 卡片四周是一圈白光晕（截图当场看出）。改成两件事一起：投影用
   `QPalette::Shadow`（投影落在遮罩上、不落在页面上），表面用
   `QxStateLayer::layered(Window, white, 0.06)` 抬一档——浅色主题下这一档几乎看不出（那里遮罩
   本来就够了），暗色下卡片才和它盖住的页面分得开。
3. **按钮是工具包的 `QPushButton`，不是自绘**。它们由主题样式表画，`setDefault()` 把主按钮标成
   强调（描边）。理由是这一件的「自绘 surface」指卡片与遮罩；按钮的观感是**应用主题**的事，
   而且自绘按钮会丢掉无障碍与 Tab 序。代价：Fluent 的实心主按钮这里拿不到 ⇒ **若日后要
   FluentButton（实心主按钮 + ghost 次按钮），那是往滚动池补一件控件，不是改本件的理由**。
4. **「问不是做」落在「对话框不替你答复」**：按任一按钮只发它的 `clicked()`，不 `accept`/`reject`；
   结果码归应用。用例 `theDialogDoesNotAnswerForTheApplication` 钉的就是这条（按下后仍可见、
   `result()` 不变，应用 `accept()` 之后才变）。
5. **最多三个 = 惰性创建**：三个按钮各自第一次被要到时才造（同 `menu()` 的写法），位置由**角色
   顺序**决定而不是要被要到的顺序（`insertWidget` 数一遍前面的角色定槽位）——否则「先要 Close
   再要 Primary」会得到一个顺序反了的动作条。动作条本身没有按钮时 `hide()`，不占卡片高度。
6. **Entry 的落位**：`FluentMotion::Duration::Slow`（tier 2）；reduce 时 `duration <= 0` 直接
   `setWindowOpacity(1.0)` 返回——不是「更短的淡入」而是「没有淡入」。
   ⚠️ offscreen 平台不支持 `setWindowOpacity`（每次 show 一条 `This plugin does not support
   setting window opacity`），所以这条用例断言的是**对话框交给平台的那个值**，不是屏幕上的像素：
   offscreen 下没有用户可看，Windows/X11 合成器下才是真的淡入。

测试侧两条坑：① 换/删测试文件后**必须先重建再 ctest**——本轮把临时截图用例删掉后直接跑了 qt6 的
ctest，用的是仍含该用例的旧 exe（它改了 `qApp` 调色板），报出 3 个与代码无关的失败，重建即复绿；
② `tst_qxfluent` 这个套件的 stdout 是**吞掉的**（MinGW GUI 子系统），`-o -` 也不行，只能
`QTC_ONLY_TEST=<类名>` + `-o <文件>,txt` 一个一个看；想一次跑多个类得临时改 `tst_global.cpp`

#### Y5 · `MaterialTextField`（输入层）

- **台账原话**（D5 其后）：「`TextField`（浮动标签 + 填充/描边两态，`QLineEdit` 缺的形态）」。
- **两态**（M3 认它的地方）：
  - **filled**：填充容器 + 底部一根指示线；聚焦时线变粗变色、标签上浮；
  - **outlined**：描边容器，标签**嵌进描边**（在边框上「开窗」）。
- **浮动标签**：空且未聚焦 ⇒ 标签在位（读作占位）；聚焦或有内容 ⇒ 标签缩小上浮。
  `QLineEdit` 的 placeholder 替不了这个——placeholder 在输入后消失，标签不消失。
- **结构**：`QxControl` 子类内嵌 `QLineEdit`；无障碍 role `EditableText`。
- **测试量级**：8–10 条（浮动标签两态的几何是重点，像素探针）。

**Y5 执行记录（2026-10-22）**：落地为 `materialtextfield.{h,cpp}`（头 112 行 / 实现 347 行）+
`tst_materialtextfield.cpp` 九条 + gallery `Input` 段一行（两态并排成一格）+ `CMakeLists.txt`
一行 + 库 CHANGELOG `Unreleased`。

四处实施中定下的事：

1. **标签位置是一个函数，不是一份缓存**。第一版把「浮起到哪」存成 `floatProgress` 字段、由
   焦点/文本事件去改；结果 `show()` 时自动获得的焦点没有产生本控件看得见的 `FocusIn`，描边已经
   按 `hasFocus()` 画成 accent，标签却还站在原处 —— 同一帧里两个判据来自两个来源。改成
   `labelProgress()`：动画在跑就回答动画的中间值，否则**现场读**「有焦点或有文本」。只有「中途」
   值得缓存，因为它真的只存在于动画期间。`updateLabel()` 因此先取 `from = labelProgress()`
   再 `stop()`，被中断的移动从断点继续而不是从端点重来。
2. **outlined 的开窗按文字宽度，不按标签框宽度**。`labelRect()` 的宽度是整个可用宽度（给对齐
   用），第一版直接 `target.adjusted(-pad, 0, +pad, 0)` 去填底色，于是整条描边被擦光 —— 测试
   里「窗外的描边还在」那条当场抓住。改按 `metrics.horizontalAdvance(label) + 2 * pad` 开窗。
3. **`chromeRect()` 返回空**：文本框不画指针 wash，也不需要基类的焦点环（焦点由指示线/描边自己
   说）。这是基类给「我身上没有需要洗的那块」留的口子，不是绕过基类。
4. **编辑器即焦点**（照 Y1 的口径）：`setFocusProxy(edit)` + 事件过滤 `FocusIn/FocusOut` 驱动
   标签，`resizeEvent` 里摆编辑器（filled 从 22 起、outlined 还要加 8 的描边内缩）。

测试侧三条坑（本轮踩到，已进 `TOPIC-pitfalls`）：

- ⚠️ **`QWidget::grab()` 返回设备像素**：本机 125% 缩放，240×56 的字段抓出来是 300×70，而测试
  里每个数都是布局数。像素探针一律改成 `render()` 到 DPR=1 的 `QImage`（先按 page 色填充，
  再 `render()`），否则整组判据都偏 1.25 倍，症状是「描边出现在 y 10 而不是 y 8」。
- ⚠️ **Qt5 的 offscreen 平台没有字体**（Qt 5.15 起不再随附字体，日志是
  `QFontDatabase: Cannot find font directory .../lib/fonts`）⇒ 文字根本没被画，探针读到的
  「标签墨」是 0。需要量字形的三条用例因此带 `drawsText()` 守卫（用一张自己的画布画一个
  `Ag` 来判断，**不是**问 `QFontDatabase`：Qt6 的 offscreen 有字体但 `families()` 报空，
  问它会把 Qt6 腿一起误判成「无字」）。本机要把 Qt5 腿跑全，给 `QT_QPA_FONTDIR=C:/Windows/Fonts`
  （212 个族，11/11 全过）；不给则 8 过 3 跳过，不算失败。
- 探针选区必须避开描边与编辑器：带内的 x 收在左右描边之间，y 收在描边行之外、编辑器上沿之上；
  「描边是否开窗」这类判据改在**标签左边缘之外、擦窗之内**的窄条上探（x 13–15），否则读到的
  是标签自己的字形。

#### Y6 · `MaterialDialog`（反馈层）
- **台账原话**（D5 其后）：「`Dialog`（M3 的 basic / full-screen 两档）」。
- **两档**：
  - **basic**：居中卡（`MaterialShape` 28 档 = dialog 圆角），标题 + 内容 + 文字按钮
    （右下角，主按钮在最右）+ scrim；
  - **full-screen**：从顶部展开、占满，标题栏带关闭图标——「这是个地方」的屏幕要的
    （同 4.7.0 `MaterialTopAppBar` 112 / 152 两档高的道理：**更高而不是更粗**）。
- **实现选型**同 Y4：`QDialog` 子类 + 自绘 surface。
- **测试量级**：6–8 条。

**Y6 执行记录（2026-10-22）**：落地为 `materialdialog.{h,cpp}`（头 129 行 / 实现 470 行）+
`tst_materialdialog.cpp` 九条 + gallery `Feedback` 段一行（启动器按钮）+ `CMakeLists.txt` 一行 +
库 CHANGELOG `Unreleased`。

五处实施中定下的事：

1. **两档的差别不是尺寸，是「它是什么」**：basic 是「一个有答案的问题」（卡 + scrim + 最多两个
   答案），full-screen 是「一个办事的地方」（从页顶铺满、名字在 56 高的栏里、栏右端一个关闭叉、
   中间交给应用）。所以 `cardRect()` 在 full-screen 下**就是整块对话框**——那里没有颜色更深的页面
   可以被压暗，scrim 也就没有东西可做。
2. **答案是画的文字按钮，不是 `QPushButton`**（与 Y4 相反，这是有意的）：M3 的答案就是一段强调色
   文字，而样式表画不出「没有边框的 QPushButton」；`MaterialSnackbar` 早就用同一口径
   （`actionText` + `actionTriggered`），本件顺着家族自己的先例。代价是应用不能 `connect` 到按钮，
   只能连 `buttonClicked(role)`——「问不是做」照样成立。Y4 那边用 `QPushButton` 是因为 Fluent 的
   标准按钮恰好就是样式表能表达的那种（`setDefault()` 得到强调描边），**两件的差异来自两套样式表
   能表达什么，不是随手选的**。
3. **关闭叉不算答案**：它 `reject()`。理由不是「M3 这么做」，而是**无边框窗口本来就没有关闭按钮**
   ——不画一个，full-screen 那一档就只剩键盘能退出来。basic 没有叉（`crossRect` 为空，`contains()`
   对空矩形恒假），所以同一个坐标按下去什么也不发生（用例把这条钉住）。
4. **按下的归属按起点算**：`pressed` 记的是「按下落在哪个答案上」，释放时要求同一个答案才发信号；
   按下后拖到别处松手不算回答。返回键到主答案（`keyPressEvent`），Esc 归 `QDialog`。
5. **暗色下的抬升同 Y4 一个解法**（`QxStateLayer::layered(Window, white, 0.06)` + `QPalette::Shadow`
   当投影墨色），但这里的 card room 是从 `MaterialElevation::shadow(Level4)` 现算的（16 模糊 +
   8 偏移 ⇒ 25），不再手写常量——Y4 那边用的是 `FluentCard::shadowMargin()`，同一条纪律。

测试侧坑一条：**28 的圆角把矩形的角切掉了**——照 Y4 的习惯在「卡左上角 +4,+4」取"卡面"像素，
那条用例读到的是遮罩色（162 对 162 当场报错）；改成在**卡的竖直中线**上、左缘 +4 处取。半径大于
探针内缩时，必须避开角。

### D 组 · 旗舰 demo 重构（fluentdemo / materialdemo）

fluentdemo 对标 [WinUI Gallery](https://github.com/microsoft/WinUI-Gallery)，materialdemo
对标 [MUI 模板页](https://v4.mui.com/zh/getting-started/templates/)，两者都基于 qxwindow
定制标题栏。排在 B 组之后、结算之前。只用现有控件搭页面，不补组件缺口（缺口清单见
`4.7-TASKS.md` §二，4.7.2 起逐件补）。

#### 参考站抓取结果（2026-10-22，官网 / 仓库页）

| 参考站 | 结构事实 | 落到本仓的对应物 |
| :--- | :--- | :--- |
| **WinUI Gallery**（WinUI 3 / Windows App SDK 的伴生应用） | ① 演示 WinUI **全部控件**；② **每个控件页**展示该示例的 markup 与 code-behind；③ 导航是 **NavigationView**（左栏分类）；④ 有**设计原则**与**无障碍**指导页；⑤ 应用本身**响应式**；⑥ 顶栏有搜索与明暗主题切换；⑦ 窗口材质 Mica | ① qxfluent 现有 **14 件控件** + B 组 4 件 ≈ **18 个控件页**；② 每页＝标题 + 一句描述 + **可交互演示**（源码片段从略——demo 不是教学仓库）；③ 已有 `FluentNavigationView` 直接当左栏；④ 首页兼「这是什么 + 控件目录」；⑤ 单窗口暂不做响应式，记候选池；⑥ 标题栏（见拆法）承载搜索与主题切换；⑦ `FluentWindowMaterial` 已在库里（Windows 问得到 Mica，其余平台问不到就 none——它的 API 就是返回 bool 的「问」） |

**标题栏的两条硬规矩**（照范本，勿发明）：① `setTitleBar()` 之后栏内除系统按钮外的
部件都会被命中测试当成 caption（按下即拖动窗口），要交互的部件（菜单、搜索框）必须
`setHitTestVisible(w, true)`；② 系统按钮必须 `setSystemButton()` 交出去才保持可点——
不交就是「看起来是按钮、按下却拖动窗口」。macOS 分支（`setSystemButtonAreaCallback`）
照抄范本，不新增未验平台代码（CI 的 macos 腿不构建 demo，见 D③）。

**D1a 执行记录（2026-10-22，`feat(demo)` 一笔）**：落地为 `titlebar.{h,cpp}`（头 120 行 / 实现 330 行）+
`mainwindow.{h,cpp}` 改写（命令行从窗口顶栏迁进标题栏；左栏改成「目的地表 + 过滤结果」两段）+
`CMakeLists.txt` 加 `qxwindow` 依赖。

四处实施中定下的事：

1. **不复制 `TitleButton` 类，改成一个自绘的 `CaptionButton`**。范本那个子类只为「双击有个信号」而存在；
   而 Fluent 的 caption 按钮本来就是**平的矩形、悬停才显形**，用 `QToolButton` 会带进样式自己的画法。
   于是按钮与字形一起画（`QAbstractButton` 子类 + `Glyph` 枚举：App / Minimize / Maximize / Restore /
   Close），双击信号只对应用图标有意义、也只在那里发。
2. **44 高而不是 32**：搜索框住在标题栏里（WinUI Gallery 也如此），32 装不下一个能读的输入框；
   组件自身的 30 高命令条又在里面留出上下各 7。
3. **四个系统按钮 `setSystemButton()` 交出、搜索框与命令行 `setHitTestVisible()` 交出**——即上面两条硬规矩，
   一个字没改；macOS 的 `setSystemButtonAreaCallback` 照范本抄。
4. **明暗切换问引擎**（`systemLightTheme()` / `systemDarkTheme()`）而不写死 id：换一族主题后仍成立；
   Toggle 的勾与 Theme 菜单的勾都接到 `themeChanged` 回写——「点过什么」不许冒充「现在是什么」，
   否则恢复设置或系统跟随那条路一切换，两个控件就同时说谎。

两处与预案不同：
- **③ 左栏分类（全部控件 / 新增 / 设计原则）挪进 D1b**：分类的对象是「每控件一页」，页面还没有时先分类
  只得到三个空组。
- **搜索过滤＝重建左边栏**：视图不看 `QAction` 的 visible（实测，`fluentnavigationview.cpp` 里没有这个判断），
  所以按名字过滤只能 `clear()` + 重新 `addItem()`；当前屏不在结果里时**保留不回退**——搜索不该关掉正在
  读的那一页，栏里没有它就不标。

验证：双腿构建通过；`fluentDemoRenders` 与 `fluentThemeSwitchMatchesAFreshStart` 通过（后者是自绘 caption
完全走 palette 的证据：切主题后与「一开始就在那个主题」的窗口逐像素一致）；明/暗两张离屏截图肉眼确认。

**D1b 执行记录（2026-10-22，`feat(demo)` 一笔）**：`controlpages.{h,cpp}`（头 40 行 / 实现 740 行）建 **17 个
控件页**（每页＝标题 + 一句描述 + 一段说明 + 可交互演示），`inputspage` / `collectionpage` / `feedbackpage`
三页删掉、内容拆进对应的控件页；`homepage` 改成「这是什么 + 控件目录」；`DemoPage` 加 `title()`——页面的
名字只有一个来源，左边栏、首页目录、页面自己的标题三处都读它。

五处实施中定下的事：

1. **一页一控件，页序按「最新先」**：B 组四件（NumberBox / DropDownButton / ToggleSplitButton /
   ContentDialog）排最前，其余按 输入 → 集合 → 反馈 → 导航 → 容器。理由写在文件头：页面也是「一套控件
   新加了什么」被发现的地方。合计 19 个目的地（Home + 17 控件 + Settings）。
2. **`tr()` 在自由函数里不能用**：这些页由匿名命名空间的自由函数造，没有自己的 `tr()`，于是文件内写一个
   `tr()` 转发到 `QCoreApplication::translate("ControlPages", ...)`——上下文只一个名字，同一句话出现在两页
   上就是一条译文而不是两条。
3. **首页目录用按钮不用链接**：目录是「应用能显示的东西」的清单，按钮才是 Qt 放进键盘路径、并告诉读屏器
   「可按」的东西。**首版四列当场把页面撑宽**（无字体时按钮仍按最长名字要宽度）⇒ 整页出现横向滚动条、
   正文被切；改成三列 + `QSizePolicy::Ignored`（列宽随屏幕、长名字由按钮自己省略）。这是本版第二处
   「捕获尺寸把页面问题暴露出来」的地方，与 S8 第 3 条同型。
4. **对话框与教学提示每按一次新建**（`WA_DeleteOnClose`）：留一个复用实例会让下一次问答带着上一次的状态。
5. **只有窗口能做的事仍留在 Settings**（折左栏、窗口材质）；导航视图本身不单独成页——窗口自己就是它的
   演示，一页演示会变成第二个窗中窗。

验证：双腿构建通过；`fluentDemoRenders` / `fluentThemeSwitchMatchesAFreshStart` 通过；首页与控件页离屏截图
肉眼确认（目录三列、无横向滚动、控件页的标题/说明/说明段/行都在视口内）。

**D2a 执行记录（2026-10-22，`feat(demo)` 一笔）**：`titlebar.{h,cpp}`（头 105 行 / 实现 260 行）+
`mainwindow.{h,cpp}` 改写 + `CMakeLists.txt` 加 `qxwindow` 依赖。窗口从此不画系统边框：`MaterialTopAppBar`
整个就是 caption，右侧一列三枚系统按钮，rail 与屏幕照旧在它下面（`setMenuWidget()` 把它放在中央部件之上）。

四处实施中定下的事：

1. **按钮站在栏的右边一列，不叠在栏上**：MUI 的 bar 不带应用标记（没有窗口图标按钮，`setSystemButton()`
   只交三枚），空出来的角正好放按钮；叠在栏上的话，栏自己的 trailing 图标会和它抢同一个角，而 Medium /
   Large 变体把名字放到栏的下半部，叠上去的按钮还要和名字打架。
2. **caption 按钮自绘，但不用 `QToolButton`，也不抄 D1a 的类**：M3 里这些是 icon button——40 的圆盘、10 的
   字形、悬停 8% / 按下 12% 墨水，另加 `MaterialRipple` 的按压水波（库里已有，attach 一次 + 在 `paintEvent()`
   里 paint 一次）；关闭按钮悬停/按下时墨色换成 `HighlightedText`，与系统观感一致。
3. **整条 app bar 交给命中测试（`setHitTestVisible(m_bar, true)`），代价由 `TitleBar` 自己还**：栏是一个
   自绘控件、图标不是独立部件，agent 无从按像素分辨「这里是图标、那里是栏面」——要让图标可点，只能交出整块。
   代价是「按栏即拖动窗口」失效，于是 `TitleBar` 给栏装事件过滤器：按下后**位移超过平台拖动阈值**
   （`QApplication::startDragDistance()`）才 `QWindow::startSystemMove()`，所以「按图标、原地松手」仍是点击、
   「按住拖」仍是移动，两者不必二选一。**没做**双击栏最大化：栏面与栏内图标在命中测试上不可分，双击图标会
   连带把窗口最大化，比缺这一条更糟；最大化仍走按钮（Win11 的 Snap 布局照常，因为按钮是交出去的）。
4. **caption 的墨色取自 `m_bar->palette()`，不自己定颜色**：栏知道自己是哪个 surface，切主题后按钮跟着走——
   由 `materialThemeSwitchMatchesAFreshStart` 逐像素证明（切换后与「一开始就在该主题」的窗口一致）。

`materialThemeSwitchMatchesAFreshStart` 通过；明/暗两张离屏截图 + 一张真窗（windows 平台、真实字体、无边框）
截图肉眼确认。**真窗最小高度**由 775 升到 831（多出的就是 56 的 caption），故构造里的 `resize(1100, 760)`
在真窗平台上被布局抬到 831；离屏捕获固定 1280×800，不受影响（`materialDemoMatchesGolden` 本版没有金标，

**D2a 补记（2026-10-22，`fix(demo)` 一笔）**：两窗（fluent + material）的 caption 有一处说谎——`main.cpp`
的交互模式走 `showMaximized()`，而最大化按钮的字形只跟着自己的点击走，于是「启动即最大化」的窗口戴着
「最大化」字形。两个 `MainWindow` 各加 `changeEvent()`：`WindowStateChange` 时把 `isMaximized()` 交给按钮
（字形跟着勾走），这样系统菜单、双击边框、键盘这些不经过按钮的路径也一并说对。验证：临时把 material 的
截图分支改成 `showMaximized()` 离屏抓一张，第三枚按钮画的是 Restore 双框（还原该行后重新构建，改动不入库）；
双腿 21/21 复跑通过。

**D1a 补记（2026-10-23，`fix(demo)` 一笔）**：作者报「fluentdemo 在 Qt 6.8 上编译失败」，复现即中——
`titlebar.cpp` 的 `QPen inner(QColor(Qt::white));` 在 MSVC 上是**编译错误**（C2751「无法限定函数参数的
名称」紧随 C2665 `setPen` 无匹配重载）。原因是那行被读成**函数声明**（most vexing parse：
`QColor(Qt::white)` 的括号被当成形参表、`Qt::white` 被当成形参名），而不是「用一个临时 `QColor`
构造一支笔」。MinGW/GCC 把它判成表达式，所以两条腿一直是绿的，MSVC 才红——**这正是「本机两腿
绿 ≠ 作者的 kit 绿」的一个实例**（作者用 Qt 6.8.3 + MSVC2022）。改法：`QPen inner{QColor(Qt::white)};`
（花括号初始化，无歧义）；全仓只此一处这种写法，`materialdemo` 的同一段用的是先赋 `QColor` 再造笔。
验证：MSVC Debug 整棵树 exit 0（不是只编 FluentDemo）；两条 MinGW 腿重建后各 21/21。

看见但本笔不做：**CI 没有 MSVC 腿**，这类只在 MSVC 现形的写法（most vexing parse）目前只能靠人
在作者 kit 上撞见。可行的低成本闸门是 clang 的 `-Wvexing-parse`（Clang 默认开、GCC 不报），
属构建接线改动，留候选池。

**D1a/D2a 补记二（2026-10-23，`fix(demo)` 一笔）**：作者看真窗报「fluent 四个 caption 按钮很高、
material 三个很矮」，外加 material 关闭按钮该变红。前两条都不是审美问题，是两处尺寸约定各自缺一条：

1. **fluent：按钮等于整条 bar 高**。`CaptionButton::sizeHint()` 的高度直接取 `kBarHeight` ⇒ 按钮就是整条
   bar，悬停时整块变色，看着像色块而不是按钮。改 **46×32**（WinUI 给 caption 的尺寸）居中，bar 里 8 上 8 下。
   同时 bar 从 44 提到 **48**，并删掉 `m_bar->setFixedHeight(30)`——Fluent 命令条按 **40 高一行、32 高的
   命令**排版（`fluentcommandbar.cpp` 的 `kBarHeight` / `kItemHeight`），压到 30 就是把每条命令的底边切掉
   （作者报的「Fold the pane / Dark / Theme 下面显示不全」即此）。
2. **material：按钮比 bar 自己的图标小八像素、还顶对齐**。`kButtonSize` 是 40，而 bar 的 trailing 图标是
   **48 居中**（`materialtopappbar.cpp` 的 `kIconButton`，`top = (56 - 48) / 2`）；列布局又是
   `addWidget(buttons) + addStretch(1)`，三个圆就挤在 56 高的顶上、下面空一截。改 **48×48、上下各加一条
   stretch 居中**，与 bar 自己的图标同尺寸同基线。
3. **关闭按钮改红**：与 fluent 用同一对色（悬停 `#C42B1C`、按下 `#A22216`），glyph 白。两个 demo 的 caption
   是**窗口的**、不是某一族设计语言的，颜色不该各写一套。
4. **「material 标题栏拖不动窗口」没复现**。用真实输入（Win32 `SendInput`，不是合成 Qt 事件）在两份本机
   构建（MinGW qt6、MSVC Debug）上拖：x = 60 / 200 / 500 / 900 / 1500 / 1900、y ≥ 16 全部移动；连拖三次
   也移动；慢速小步（4 px × 40 步）同样移动。y < 16 拖不动是**窗口自己的 resize 边框**
   （`windowgeometry_p.h` 的 `kResizeBorderThickness = 8`，加最大化时那 8 px 不可见边框 ⇒ 物理 16 px），
   横向拖它本来就不该动，fluent 在同一位置同样不动。⇒ **不改代码**，等作者说明抓的位置。

**D1a 补记三（2026-10-23，`fix(fluent)` 一笔，库）**：作者报「fluent 的系统按钮比普通按钮整体偏下」。
量了才看出方向是反的——**偏的是命令条，不是 caption**。离屏截图按 x 区间量墨迹行范围：caption 三枚
glyph 中心 **23.5**（46×32 在 48 高的栏里居中，几何正确），logo 也 23.5，而 `Fold the pane` / `Dark` /
`About` 的文字中心只有 **19.0**，整条命令比旁边高 **4.5 px**，眼睛读到的是「按钮掉下去了」。

根因在库里，不在 demo 的尺寸：`fluentcommandbar.cpp` 的 `centeredVertically()` 用**常量** `kBarHeight`
（40）算垂直居中——
```cpp
return QRectF(left, (kBarHeight - height) / 2.0, width, height);
```
`kBarHeight` 是「这条 bar 自己理想的高度」，而布局可以给它更多：标题栏把命令条放进 48 高的行里，
widget 就被拉到 48，命令仍按 40 的坐标系排 ⇒ 全部贴顶（32 高的命令落在 y 4..35，中心 19.5，与实测
19.0 吻合）。改成按**实际高度**居中（`centeredVertically(const QWidget *bar, …)`，两个调用点传 `q`），
任何高度都对。

⚠️ 同一个缺陷还有第二半：`relayout()` 的缓存只比宽度（`laidOutWidth == q->width()`），高度变了**不重排**。
只改居中函数会留下「先按旧高度排过、再被拉高」的旧偏移，所以加 `laidOutHeight` 进判据。
修后实测：`About` / `Dark` 文字中心 **23.0**，caption glyph **23.5**，差 0.5 是字形上下不对称（`Fold` 中心
25.5 是因为 `p` 有降部），同一光轴。

**D2a 补记五（2026-10-23，`feat(fluent)` 一笔，库）**：作者报「`FluentNavigationView` 不支持滚动，成员多了
下面看不到」。这个控件是**整块自绘**的（`FluentNavigationView` 只画，没有子部件列表），原来连一个滚动状态都
没有——目的地一律从 `kMenuButtonHeight` 往下排，超出就排到窗口外面。补五件：

1. **偏移**：私有 `offset`，`relayout()` 里 `top = kMenuButtonHeight - offset`。菜单按钮**不跟着滚**——它是
   面板的头（pane header），不是第一行；滚的是它下面那一列。
2. **裁剪**：`paintContent()` 里对目的地循环 `save()` + `setClipRect(视口)` + `restore()`。没有这一步，
   滚上去的行会画在汉堡按钮上，等于多一个头；`itemAt()` 同判 `pos.y() < viewportTop()` ⇒ 返回 -1。
3. **滚动条**：overlay 样式，3 宽、离分隔线 2、无轨道，长度按「可见比例」且不小于 24；有得滚就画
   （alpha 0.3，按住/悬停 0.55），因为它是「下面还有」的唯一提示。拖动按 `travel / span` 换算，
   抓取范围左右各放宽 3（3 宽是给眼睛的，不是给鼠标的）。
4. **滚轮**：先看 `pixelDelta()`（触控板给像素），否则 `angleDelta()/120 × kItemHeight ×
   QApplication::wheelScrollLines()`（一格 = 平台设置的行数），方向为 `offset - delta`。
5. **键盘与程序选中**：`Key_Up/Down` 与 `setCurrentIndex()` 都走 `ensureVisible()`，把目标行滚进视口。

⚠️ 发布前抓到两个坑，第二个是**真回归**：

- `relayout()` 里必须**夹取** `offset`：删除目的地、面板展开/折叠、视图变高都会缩小「还能滚多远」，
  而这三件事都不是滚轮。
- **`ensureVisible()` 在视口高度为 0 时会算错**。应用通常在构造函数里 `setCurrentIndex(0)`，那时视图还没
  被布局 ⇒ `viewportHeight() == 0` ⇒ 「底边 40 > 0」成立 ⇒ `setOffset(40)`，列表被滚掉整一行；等高度真的到了，
  第一行的矩形正好落在裁剪区上边界**之外**，于是**第一项连选中态一起消失**。修法：`view <= 0` 直接返回
  （没有高度就没有「可见」可言），高度到位后的 `setCurrentIndex()` 照常滚。

⚠️ **抓住这个回归的是截图测试，不是单测**：`tst_qxfluent` 全绿，Qt6 的 `tst_demoscreenshot` 也全绿；
失败的是 **Qt5** 那条 —— `fluentDemoRenders` 报 98.4% 一色（阈值 98%）。差分才看清：Qt5 离屏无字形，
pane 里能贡献非背景色的只剩那一块选中洗色，丢了它就从 ~96% 跳到 98.4%，而 Qt6 的图内容更密、还够得着阈值。
**教训：像「少画一块」这类回归，阈值型截图测试比断言型单测更容易撞上；两腿都要跑，且失败时先做像素差分定区域。**

判据分两套：**A 套**（①–⑥）只管搬家，**B 套**（⑦–⑩）只管增量。一套绿了不代表另一套。

### A 套 · 搬家判据

#### ① 纯搬移（笔级，每笔必跑）

```bash
# 基线取上一次发版的 tag（4.7.1 期间用 4.7.0；拆第二笔起用上一笔的 SHA 也行，判据相同）
git show 4.7.0:src/libs/qxribbon/ribbonbar.cpp > build/move/ribbonbar-before.cpp
python build/check_pure_move.py build/move/ribbonbar-before.cpp \
    src/libs/qxribbon/ribbonbar.cpp src/libs/qxribbon/ribbonbarlayout.cpp \
    src/libs/qxribbon/ribbonbarpaint.cpp src/libs/qxribbon/ribbonbarprivate.cpp \
    src/libs/qxribbon/ribbonbarstackedwidget.cpp src/libs/qxribbon/ribbonbar_p.h
```

脚本做的事：两侧都**丢掉**版权头注释块、`#include` 行、`#pragma once`、`QX_*_BEGIN/END_NAMESPACE`、
空行，然后把剩下的行**排序成多重集**比。期望输出：`only-before` 与 `only-after` 两栏**都为空**
（`N2` 的 `inline` / `inline constexpr` 修饰符在脚本白名单里等价归一）。

#### ② 公开面零变化（库级，一个库拆完跑一次）

```bash
git diff --stat 4.7.0..HEAD -- \
    'src/libs/qxribbon/*.h' 'src/libs/qxdock/*.h' \
    ':(exclude)src/libs/qxribbon/*_p.h' ':(exclude)src/libs/qxdock/*_p.h'
# 期望：空输出（一个字节都没有）
```

⚠️ 三个坑，都实测过：

1. **不能用 `[!_]` 之类排除 `_p.h`**——`_p.h` 是**后缀**不是前缀（`ribbonbar_p.h` 以 `r` 开头），
   要用 `:(exclude)` 或 `*_p.h` 的模式。
2. **不能写成 `'src/libs/qxdock/**/*.h'`**：`**` 会吃掉一层目录名，**紧贴库目录的头文件匹配不到**
   （`release.md` 已记这个坑）。
3. **花括号不能省**：`'src/libs/qx{ribbon,dock}/*.h'` 在引号里**不会**展开成两个模式，git 也不认
   brace expansion——要么写两遍，要么不引号（后者会被 shell 展开成两个参数，也行但容易看错）。

#### ③ 双腿（笔级 + 库级）


`ctest --preset` 已自带 `QT_QPA_PLATFORM=offscreen`（`CMakePresets.json` 的 `base` test preset），
不必再手工设。⚠️ **两腿都要跑**，别只跑 qt6。B 组不新增测试可执行文件（新 `tst_*.cpp` 进既有
