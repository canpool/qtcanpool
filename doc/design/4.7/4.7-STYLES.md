   **纯自绘**，不做窗口材质类、不做窗口类（§二）。
3. **作者裁定（2026-10-22）**：**两家都做，4.7.2 引入**——不进 4.7.1（那一版是五个千行

## 一、现状盘点

仓库的"观感"分两族：

| 族 | 库 | 回答的问题 |
| :--- | :--- | :--- |
| **结构族** | `qxribbon`（命令组织）、`qxdock`（窗口管理） | 界面怎么**摆** |
| **平台族** | `qxfluent`（Fluent / Windows）、`qxmaterial`（Material / Google） | 单个控件长**什么样** |

平台族目前只有两家，`controls.md` §一 把它们与 ribbon 并列为"三个选项"。gallery 的存在理由
就是"同一件事几种做法并排放着"——再开两族，并排从两种变四种。

## 二、约束：作者环境可验证（先于选型，是本次调研的前提）

作者两句原话：「**不碰平台 API，不然验证困难**」「**不是新约束，macos 的我没有环境，
如果依赖平台 API，我没法验证**」。⇒ 约束的**性质与理由**要记准：

- **规则**：新库**纯自绘**——`QPainter` / `QStyle` / `QStyleOption` / QSS / `QProxyStyle` /
  `QVariantAnimation`；**不碰平台 API、不做窗口类**（无边框窗要原生事件做热区）。
- **为什么不是「平台 API 一律禁止」的政策**：作者环境是 Windows，DWM 那半是能编能验的；
  验不了的是 macOS 那半（无环境）。但平台材质效果天生是**双平台**的（Windows 接 DWM、
  macOS 接 `NSVisualEffectView`），**半边不可验 = 整体不可验收**，而金标又只有 Windows 一套
  ⇒ 操作结论与「一律不碰」相同，**理由不同**：不是政策禁令，是这一版没有验证手段。
- **直接后果**：**不做窗口材质类**。`qxfluent` 的 `FluentWindowMaterial` 靠横连 `qxwindow`
  （`#include "qxwindow/windowagentwidget.h"`，背后是 DWM 与 `NSVisualEffectView`，
  `CMakeLists.txt` 里还为这一个文件开了 `QXFLUENT_WINDOW_DEPENDS` 条件依赖）——「有现成
  范式可抄」在这条约束下**作废**：抄它就是抄一个作者验不了的东西。
- **零 `Q_OS_*` 分支是目标不是规定**：`qxfluent` / `qxmaterial` 现状就是 **0 处**（实测），
  新库照这个来；万一不得不有平台分支，先开 Q 项说清那半边怎么验。
- **验证收益**（作者要的就是这个）：全部效果落在标准 Widgets 绘制上 ⇒ ④ 的金标零像素差
  在 Windows 上就是完整判据，CI 只需要现有的编译腿，不需要真机。

## 三、候选判据（五条都要过）

① 平台级设计语言，不是某家公司的产品套件；② 有**桌面**规范（qtcanpool 是 Widgets 桌面库）；
③ Qt Widgets 侧空白（QML 侧有了不算，Flutter 有了也不算）；④ 与现有四族形态不重叠；
⑤ **纯自绘可行**——每一件都能用 `QPainter` 独立画完、在 Windows 上截出金标（§二 的直接后果）。

## 五、够格的两家

### 5.1 Cupertino（Apple HIG）

- **为什么够格**：Fluent 与 Material 之外唯一同级的平台设计语言；"给 Qt 应用一张 Apple 的脸"
  是跨平台 Qt 最常见的第二平台诉求。官方在 Widgets 侧没有（Qt 只提供平台原生 style——
  Windows / Fusion / macOS，那不是 HIG 控件集），QML 侧也没有官方对应物（Flutter 有
  `cupertino` 包，Qt 没有）。
- **形态特征**：大圆角、分段控件（segmented control）、iOS 细轨开关、sheet 对话框、
  push button / slider、工具栏与侧栏的排布；2026 的 HIG 新增 **Liquid Glass** 材质。
  （交通灯窗口按钮归窗口类，**不做**——见 §二。）
- **技术难点（已被约束化解，不再是难点）**：材质依赖平台 API，而作者环境验不了 macOS
  那半 ⇒ 材质整体不做。去掉材质后，Cupertino 在 Widgets 侧剩下的仍是一套**完整控件集**。
- **已知代价（写在这里，免得动工后当成缺陷返工）**：Apple 最有辨识度的部分（vibrancy /
  Liquid Glass）只能用「纯色 + alpha 的 `QPainter` 近似」表达——做得像**形制**（分段控件
  有分段的行为、开关有开关的手感、圆角半径与字阶对得上），不像**像素**。这不是缺陷，
  是这一版验证手段划的边界；要像素级那天，先解决 macOS 验证环境再说。
- **命名**：`qxcupertino` / 类 `Cupertino*`——Flutter 的先例（`cupertino` 包、
  `CupertinoButton`…），且 Cupertino 是地名不是商标。类名前缀照 4.7.0 已立的体例
  （`Fluent*` / `Material*` 都是设计语言名）。

### 5.2 HarmonyOS（鸿蒙设计语言）

- **为什么够格**：中国市场的第三极；有**鸿蒙电脑规范**（桌面组件与模版），2026
  （HarmonyOS 7）仍在演进（空间美学 / 沉浸光感 / 可变字体）；官方实现是 ArkUI，
  Widgets 侧空白 ⇒ 价值主张与 4.7.0 给 fluent / material 写的完全同形。
- **形态特征**：卡片式布局、中等圆角、物理感动效曲线、开关与滑块的反馈手感、
  底部导航与工具栏排布。（沉浸光感把材质的光学行为当作独立界面物质 ⇒ 归材质，**不做**；
  HarmonyOS Sans 是字体文件 ⇒ 不带字体，用系统栈近似，照 4.7.0 §1.3「不引第三方」。）
- **对中文用户的额外价值**：作者与用户群在中文圈；gallery 的并排理由见 §一。
- **风险（仍高于 Cupertino，但比初稿低）**：规范演进快（已到第 7 代），跟不跟是长期负担
  ——这一项**没有**被约束化解。另一项「一批概念（分布式、碰一碰、闪控球）是系统能力不是
  控件形态」反倒被约束**自动化解**了：不碰平台 API 正好把它们整体排除，不用再手工划边界。
- **命名**：`qxharmony` / 类 `Harmony*`（`Harmony` 是通用词；**不用完整产品名** `HarmonyOS`，
  商标谨慎）。请作者定。

## 六、不够格的（一句一个理由）

- **Adwaita（GNOME）**：Qt 应用在 Linux 上本该用平台 style，自绘一套边际价值低；且浅色 +
  圆角 + header bar 与 fluent 重叠。
- **Ant Design / Element / TDesign 一族**：Web 优先、没有桌面规范，"桌面版 Ant 是什么"
  没有权威答案。
- **One UI / Carbon / Spectrum / Atlassian / Polaris / GOV.UK**：移动优先，或产品级品牌套件
  而非平台语言，做进 Qt Widgets 用户面窄。
