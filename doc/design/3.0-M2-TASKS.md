## 二、T2.1 `qxwidget` → `qxapp` 重定位

### 2.1 对照表（与《3.0-MIGRATION》§4 一致）

| 维度 | 2.x | 3.0 |
| :--- | :--- | :--- |
| 库目录 | `src/libs/qxwidget/` | `src/libs/qxapp/` |
| 全局头 | `qxwidget_global.h` | `qxapp_global.h` |
| qmake 片段 | `qxwidget-lib.pri` / `qxwidget.pri` / `qxwidget.pro` / `qxwidget_dependencies.pri` | `qxapp-*` |
| 命名空间 | `QxWidget` | `QxApp` |
| 宏族 | `QX_WIDGET_*` | `QX_APP_*` |
| 导出宏 | `QX_WIDGET_EXPORT` | `QX_APP_EXPORT` |
| CMake 选项 | `WITH_QXWIDGET` | `WITH_QXAPP` |
| 主类 | `RibbonAppWindow` | `RibbonAppWindow`（**不变**） |
| 示例目录 | `demos/qxwidget/`、`examples/qxwidget/` | `demos/qxapp/`、`examples/qxapp/` |

### 2.2 关于"转发兼容头"的最终决策

《3.0-MIGRATION》初稿曾建议提供 `compat/qxwidget_global.h` 转发头。**M2 决定不提供**，理由：

1. K6 已明确「不保证源码兼容，提供迁移指南即可」；
2. `qxwidget` 的公开面**只有 1 个类**，迁移成本 = 改 1 处 include + 改 1 处命名空间；
3. 转发头需要在两套构建（CMake/qmake）里各加一个额外 include 根，维护成本高于收益。

> 该决策已回写进《3.0-MIGRATION》§4。

### 2.3 影响面清单（实测）

改动文件共 **23 个**（不含纯文档），其中：

| 类别 | 文件 |
| :--- | :--- |
| 库本体 | `src/libs/qxwidget/**`（9 个文件，全部改名或改内容） |
| 库注册 | `src/libs/CMakeLists.txt`、`src/libs/libs.pro` |
| 示例注册 | `demos/CMakeLists.txt`、`demos/demos.pro`、`examples/examples.pro` |
| 消费方 | `demos/qxwidget/ribbondemo/{CMakeLists.txt,mainwindow.h,ribbondemo.pro}`、`examples/qxwidget/ribbonappempty/{mainwindow.h,mainwindow.cpp,ribbonappempty.pro}` |
| 不动 | `src/libs/qxribbon/CHANGELOG`（**历史记录，不改写**） |

> 注意：`demos/qxwidget/dockdemo` 并**不**引用 qxwidget 库（它只用 qxdock），仅随目录一起移动。

### 2.4 执行方式

- 目录与文件用 `git mv`（保留历史），再批量替换标识符；
- 替换顺序：`QX_WIDGET_` → `QX_APP_` → `QXWIDGET` → `QXAPP` → `QxWidget` → `QxApp` → `qxwidget` → `qxapp`（大写优先，避免二次改写）；
- `RibbonAppWindow` 类名与文件名**保持不变**。

## 三、T2.2 legacy ribbon deprecated 标注

### 3.1 现状

`qcanpool.h` 里 **已有** `QCANPOOL_DEPRECATED_SINCE(major, minor)` 宏，但**全仓库从未真正使用过**（只在宏定义处的注释里出现）。M2 是它的首个使用者。

```cpp
// src/libs/qcanpool/qcanpool.h（现存，无需改动）
#ifndef QCANPOOL_DISABLE_DEPRECATED_BEFORE
    #define QCANPOOL_DISABLE_DEPRECATED_BEFORE QCANPOOL_VERSION   // = 2.0.2
#endif
#ifdef QT_DEPRECATED
#define QCANPOOL_DEPRECATED_SINCE(major, minor) \
    (QT_VERSION_CHECK(major, minor, 0) > QCANPOOL_DISABLE_DEPRECATED_BEFORE)
#else
#define QCANPOOL_DEPRECATED_SINCE(major, minor) 0
#endif
```

按默认值 `QCANPOOL_DEPRECATED_SINCE(3, 0)` = `QT_VERSION_CHECK(3,0,0) > 2.0.2` = **true**，因此标注默认生效；用户若把 `QCANPOOL_DISABLE_DEPRECATED_BEFORE` 提到 3.0，这些 API 会按 Qt 惯例从声明中移除。

### 3.2 标注对象（8 个类）

| 头文件 | 类 |
| :--- | :--- |
| `ribbonbar.h` | `RibbonBar` |
| `ribbonpage.h` | `RibbonPage` |
| `ribbongroup.h` | `RibbonGroup` |
| `ribbonwindow.h` | `RibbonWindow` |
| `ribboncontainers.h` | `RibbonContainer`、`RibbonGridContainer`、`RibbonActionContainer`、`RibbonLoftContainer` |

### 3.3 标注写法（⚠️ 有坑，已实测踩过）

**第一版写法是错的，被编译器静默忽略。** 直觉写法：

```cpp
// ❌ 错误：GCC 报 "attribute ignored ... must follow the 'class' keyword"
#if QCANPOOL_DEPRECATED_SINCE(3, 0)
QT_DEPRECATED_X("use QxRibbon instead")
#endif
class QCANPOOL_SHARED_EXPORT RibbonBar : public QWidget
```

原因：`QT_DEPRECATED_X` 展开为 C++14 的 `[[deprecated("...")]]`，而**类的 attribute-specifier-seq 必须出现在 `class` 关键字（及导出宏）之后、类名之前**——放在 `class` 前面会被 GCC 直接忽略（只报一条 `-Wattributes` 警告，**不会报错**，极易漏掉）。

正确写法（Qt 自身对 `QGLWidget` 也是这么写的）：

```cpp
// ✅ 正确：属性位于 class 关键字与类名之间
class QCANPOOL_SHARED_EXPORT QCANPOOL_DEPRECATED_X("use QxRibbon instead") RibbonBar : public QWidget
```

为此在 `qcanpool.h` 中新增了统一入口宏（跟随 `QCANPOOL` 既有的版本门控惯例）：

```cpp
#if QCANPOOL_DEPRECATED_SINCE(3, 0)
#define QCANPOOL_DEPRECATED_X(text) QT_DEPRECATED_X(text)
#else
#define QCANPOOL_DEPRECATED_X(text)
#endif
```

> 选择 `QT_DEPRECATED_X` 而非裸 `QT_DEPRECATED`：前者能附上"改用 qxribbon"的提示信息。
>
> 与 Qt 官方惯例的**有意差异**：这里的类声明始终保留，`QCANPOOL_DISABLE_DEPRECATED_BEFORE` 只开关告警，不会让 API 消失。

### 3.4 已验证

用探针程序（`-fsyntax-only`，Qt 6.8.3 / MinGW GCC 13.1.0）实测：

- 修正前：**10 条** `attribute ignored in declaration of 'class QCanpool::Xxx'`，弃用告警 0 条 → 标注形同虚设；
- 修正后：`attribute ignored` **0 条**，弃用告警正常触发，形如
  `warning: 'RibbonBar' is deprecated: use QxRibbon instead [-Wdeprecated-declarations]`。


### 3.4 已知影响（可接受）

- 真实消费者**只有 `demos/qcanpool/fancyribbon`** 一个（实测：`ribbondemo` 用的是现代 qxribbon），因此只会产生少量编译告警；
- CI 未启用 `-Werror`，不会导致构建失败。

| 状态 | `attribute ignored` | 弃用告警 |
| :--- | :--- | :--- |
| 修正前 | 10 条 | **0 条**（标注形同虚设） |
| 修正后 | 0 条 | 正常触发 |

> 教训：给类加 `[[deprecated]]` 类标注后，必须**用一个真实消费方编译验证**，不能只看"能编过"。
