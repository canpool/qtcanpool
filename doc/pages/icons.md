# 图标规范

> 图标在本项目里不是「放上去就行」的资源：同一个文件会被两套语义完全不同的机制着色。
> 本页规定图标怎么分类、颜色怎么写、由谁判定；判定由 `scripts/check-icons.py` 执行，
> 分类登记在 `scripts/icons-policy.txt`。

## 为什么需要规范

两套着色机制对「图标里的颜色」的看法根本不同：

| 机制 | 位置 | 做法 | 与源颜色的关系 |
| :--- | :--- | :--- | :--- |
| `qxribbon` | `ribbonutils.h` 的 `tintedIcon()` / `tintedPixmap()` | 光栅化后用 `CompositionMode_SourceIn` 把整幅换成目标色 | 只保留 alpha，源颜色是什么都无所谓 |
| `qxdock` | `dockiconprovider.h` 的 `applyDockIcons()` | 替换 SVG 文本里的 `#ffffff` / `#fff` / `#a0a0a0` / `#000000` | 强相关：替换表没覆盖的颜色保持原色 |

⇒ 一个「看起来没问题」的图标，换到另一套机制下可能完全不跟着主题变。规范管的正是这件事：
每个图标都要声明自己走哪条路，并且真的符合那条路的要求。

⚠️ 三个外观库互不依赖（`qxribbon` / `qxdock` 都不依赖 `qxtheme`，只有 `qxapp` 同时看得见三者），
所以这份一致性**由规范与门禁保证，不靠共用一份代码**——共用会引入两条新的库间依赖。

## 三类登记

`scripts/icons-policy.txt` 里每个受管图标都要归到以下三类之一：

| 类别 | 含义 | 判定 |
| :--- | :--- | :--- |
| `tinted` | 参与主题着色 | 按消费者的规范色判定（见下） |
| `multicolor` | 多色图标，明确豁免着色 | 必须真的含两种以上颜色 |
| `plain` | 固定色，不参与着色 | 不做颜色判定 |

**未登记**本身也是问题：受管目录下没有归类的图标会被门禁报出来——「忘了归类」和「有意豁免」
在文件里看不出区别，登记就是把这个区别写下来。

## 规范色

- **alpha 消费者**（走 `qxribbon` 的换色）：单色，且一律 `#000000`。
  源颜色对结果没有影响，统一成一个值是为了让「这个图标可染」在文件里看得出来。
  没有显式颜色的图标等同黑色，同样可染（`qxribbon` 只取 alpha）。
- **dock 消费者**（走 `qxdock` 的文本替换）：图标里画出来的颜色必须落在
  `#000000` / `#ffffff`（或 `#fff`）/ `#a0a0a0` 之内，且至少要有一个。
  禁用态用 `#a0a0a0`、聚焦态用 `#ffffff`，正是替换表覆盖的那几种。

⚠️ **不要写 `currentColor`**：两套机制都不靠它，`qxdock` 更是只认具体字面值。
上游图标集（Tabler / Lucide 等）默认带 `stroke="currentColor"`，入库时一律改写为具体值。

## 门禁

```
python3 scripts/check-icons.py                  # 检查；有问题退出码非 0
python3 scripts/check-icons.py --policy <file>  # 换一份登记表
```

报四类问题：

1. 声明 `tinted` 却不符合规范色（混了多种颜色、或含消费者换不到的颜色）；
2. 受管目录下的图标没有登记归类；
3. 走 `qxdock` 换色却没有一个可被替换的颜色（换图标集后最容易整片失效的一类）；
4. 登记表本身腐烂：条目指向不存在的文件，或 `multicolor` 条目其实不含多种颜色。

## 入库新图标

1. 从上游取回时确认许可，并把许可声明一并带上；
2. 把 `currentColor` 改写成规范色，去掉上游工具留下的编辑器戳（如 `sodipodi:` / `inkscape:` 属性）；
3. 在 `scripts/icons-policy.txt` 里登记它所属的目录或文件——**能按目录登记就按目录登记**，
   单个文件条目只用于目录里的例外；
4. 跑一次 `python3 scripts/check-icons.py`。
