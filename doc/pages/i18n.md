# 界面语言（i18n）

库自己**带一套界面语言**：用户看得见的那些字符串已经有了译文，编译成 `.qm` 随目录产出，
应用说一句「用这门语言」就换了。在此之前，一个中文应用要让 dock 的右键菜单说中文，得自己对着本仓库
跑一遍 `lupdate`、自己维护译文、自己把产物塞进安装包——那是每个真实应用都要重抄一遍的活，
不该由每个应用各自抄。

## 谁带目录，带哪些语言

判据是**这个库有没有用户可见的字符串**。有，它就有一份目录，放在自己的源码目录里：

| 文件 | 作用 |
| :--- | :--- |
| `src/libs/<库>/<库>_<语言>.ts` | 译文，`lupdate` 产出、译者维护 |
| `<构建树>/share/qtproject/translations/<库>_<语言>.qm` | 编译好的目录，应用加载的就是它 |
| 安装后 `${IDE_DATA_PATH}/translations/<库>_<语言>.qm` | 同上，路径随平台（`share/qtproject`、macOS 包内的 `Resources`） |

目录跟着库走而不是合成一份：这是 K11 那条「库独立演进」的延续——改一个库的界面串，动不着的另一个库的目录。
而所有库的 `.qm` 最终落进**同一个目录**，因为 @ref QxCore::QxTranslator 只认一个路径。

目前只有 **zh_CN** 一门。

## 应用怎么装上

@ref QxCore::QxTranslator 负责这件事：给它一个路径，它把该路径下 `*_<语言>.qm` 全部装上，
顺带上 Qt 自己的 `qtbase_<语言>.qm`（Qt 把它自己的译文放在 Qt 安装目录里，不在应用边上）。

```cpp
QxTranslator translator;
translator.setTranslationPath(QStringLiteral("<...>/translations"));
translator.setLanguage(QStringLiteral("zh_CN"));
```

时机是要点：**在构造窗口之前装上**。一个目录影响的是「构造控件时读的那些串」，
不是仅影响事后重算的那些；先建窗口再装，第一批串已经读完了。

选择的持久化留给应用——它是一个值，而应用已经有 @ref QxCore::QxSettings 可以放它，
为一件两行就能办成的事引入依赖不值得。

`RibbonDemo` 有一份可以照抄的完整实现，`RibbonDemo --lang zh_CN` 就能看效果。

## 加一门语言

1. 在每个带目录的库的 `CMakeLists.txt` 里，把语言加进 `LANGUAGES`（例如 `LANGUAGES zh_CN fr`）。
2. 跑一次 `cmake --build <构建树> --target <库>_ts_<语言>`，`lupdate` 生成新的 `.ts`，把它提交进仓库。
3. 填译文。剩下的交给构建：`lrelease` 编译 `.qm`，安装规则把它放到 data 路径下。

没有 LinguistTools 也不会构建失败：届时 `.qm` 不产出，相关的测试自行跳过，
而不是假装通过。

## 为什么有些串故意不译

`qxribbon` 里那几条 `Ribbon Warning !!! ...` 的诊断保留英文。它们通过 `qDebug()` 抵达集成者手里，
而这种东西的价值有一半在于「无论界面跑什么语言，都能原样搜到」——译了反而丢掉这个性质。
`tests/common/tst_catalogue.cpp` 里的 `deliberatelyEnglish()` 是这份豁免的唯一登记处：
**除了它列出的前缀，任何没有译文的串都会让测试红。**

## 上下文这一关是最大的坑

Qt 的译文按「上下文 + 原文」取，而这个仓库有两类上下文是**取不到**的——它们也是本次唯一真正难住人的地方：

| 写法 | 运行时上下文 | `lupdate` 记的上下文 |
| :--- | :--- | :--- |
| 公有类里的 `tr("...")`（有 `Q_OBJECT`） | 公有类名 | 公有类名 ✅ |
| 显式 `QObject::tr("...")` | `QObject` | `QObject` ✅ |
| **私有类（继承 QObject、但没有 `Q_OBJECT`）里的裸 `tr()`** | `QObject` | 私有类名 ❌ |
| **私有类里的 `q->tr("...")`** | 公有类名 | 私有类名 ❌ |

后两行的两个名字永远碰不上：一个类没有 `Q_OBJECT` 就定义不了自己的 `tr()`，于是它要么继承 `QObject` 的
（上下文成了 `QObject`），要么显式 `q->` 指向公有类的。而 `lupdate` 是静态看的，它按**写在哪个类里**记。
结果是这类目录条目译者填了也永远查不到——它有译文，谁也要不到。

`tst_catalogue` 把这条守住了：任何名字以 `Private` 结尾的上下文都会让它失败，报错会直接说明
「私有类上下文，没有 `tr()` 能产出它」。要给一个这样的类加 `Q_OBJECT`，那才轮到改这条判据。

## 门禁

| 检查 | 位置 |
| :--- | :--- |
| 每条译文都能通过 Qt 自己的查找取得 | `tst_<库>Translations::catalogue`（三个库各一份） |
| 没有「忘了译」的串（诊断除外） | 同上 |
| 没有取不到的私有类上下文 | 同上 |

这套检查验证到的是一半：**它能证明「`.ts` 承诺的条目，`.qm` 里真的有」，
证明不了「这句中文译得对」**。译得对不对没有机器能判，那是译者的活。
